# Agentic RAG 改造说明（学习版）

> 这份文档讲「为什么这么改」，不是 API 手册。代码只保留必要的形状，
> 具体实现以源码为准；实施细节和文件清单见同目录的《Agent化改造实施计划.md》。

---

## 0. 先记住三句话

1. **RAG 从「一条固定流水线」变成了「一个循环」。**
2. **模型负责决策，工具负责执行；模型不直接接触数据库和文件系统。**
3. **所有工程难题最后都会落到三件事：上下文别爆、请求能停、出问题能查。**

理解这三点，后面的设计都能自己推出来。

## 1. 改造前 vs 改造后

### 1.1 改造前：固定流程

```
用户问题
  → LightRAG.aquery(mode="hybrid", top_k=20)
      （内部：检索 → 拼提示词 → 调模型生成）
  → 返回一段文本
```

整条链路**没有任何决策点**。不管用户问的是「报销流程」「现在几点」还是「把文件入库」，
都走同一条路。问题在于：

- 问具体术语和问全局主题，需要不同的检索模式，但 `mode` 写死了；
- 需要多跳的问题（先查 A，再根据 A 查 B），一次检索做不到；
- 有些问题根本不该查知识库（计算、时间、闲聊），但链路仍会去检索；
- 入库、删除这类操作完全在对话之外，模型无法参与；
- `aquery` 是黑盒：检索、拼提示词、生成绑在一起，中间插不进任何判断。

### 1.2 改造后：决策循环

```
用户问题
  → 模型规划（这一步要不要调工具？调哪个？参数是什么？）
  → 执行工具，拿到结果（observation）
  → 模型根据结果决定：继续调工具，还是给出最终回答
  → 循环，最多 6 步
  → 流式输出最终回答
```

看起来只是多了一个循环，但系统的性质变了：

| | 固定 RAG | Agentic RAG |
|---|---|---|
| 检索次数 | 固定 1 次 | 模型决定 0~N 次 |
| 检索模式 | 写死 | 模型按问题选择 |
| 能否不检索 | 不能 | 能（计算、时间、常识） |
| 能否写操作 | 不能 | 能，但要人工确认 |
| 失败处理 | 整条链路失败 | 工具失败变成「观察结果」，模型可以换策略 |
| 可解释性 | 只有最终答案 | 每一步思考、工具、参数、耗时都有记录 |

## 2. 三层架构与职责边界

```
浏览器（React）
  │  SSE：每帧一个事件 JSON
  ▼
Java BFF（Spring Boot）
  │  NDJSON：一行一个事件 JSON
  ▼
Python RAG 服务（FastAPI）
  ├─ 决策循环（agent/loop.py）
  ├─ 工具注册表（agent/tools/）
  ├─ 会话记忆 / trace
  ├─ 人工确认
  └─ LightRAG（检索器 + 写入器）
```

### 2.1 各层只做自己该做的事

| 层 | 职责 | 刻意不做的事 |
|---|---|---|
| Python | 决策、调工具、生成回答、记忆、trace、确认 | 不负责把事件翻译成 UI 文案 |
| Java BFF | 注入身份、UTF-8/NDJSON 解码、原样转发、落库 | **不重新实现事件协议**，不合并/过滤事件 |
| 前端 | 把事件渲染成消息、轨迹、确认弹窗 | 不猜事件含义，不依赖 `run_id` 去重 |

**最重要的一条：事件协议只有一份实现，在 Python 的 `agent/events.py`。**
Java 只做「字节流 → 行 → SSE 帧」的搬运；前端只做「事件 → 状态」的应用。
如果 Java 也解析并重新拼事件，就会出现第二份契约，早晚和 Python 不一致。

### 2.2 为什么新开一条链路，而不是改旧接口

新增 `/ai/agent/chat`，旧的 `/ai/chat` 完全不动。好处：

- 随时可以回滚：摘掉新页签或停用新路由即可；
- 可以用同一个问题做 A/B 对比；
- 旧链路的行为、格式、前端都不受影响，改造风险被隔离。

## 3. 核心循环：ReAct 是怎么跑起来的

循环的形状可以概括成下面几行伪代码：

```
messages = 系统提示 + 历史对话 + 本轮问题
循环 step = 1..6：
    结果 = 规划调用(messages, 可用工具)     ← 非流式，带 tools
    如果结果没有工具调用：
        流式生成最终回答，写入记忆，结束
    否则：
        把模型的工具调用意图加入 messages
        逐个执行工具，把结果作为 observation 加入 messages
超过 6 步：发 error(MAX_STEPS)，结束
```

### 3.1 为什么规划调用是非流式的

工具调用（function calling）需要拿到结构化的 `tool_calls`，包括工具名、
参数 JSON、调用 ID。流式增量拼装这些结构既麻烦又容易出错。
所以规划阶段用非流式调用，**只有最终回答才流式**。

### 3.2 为什么最终回答要再调一次模型

规划调用返回正文、且没有工具调用时，这已经是答案了。但非流式调用拿不到
「逐字出现」的体验，用户会感觉「等很久 → 一瞬间刷完」。

所以做法是：把这段正文放进消息历史，再发起一次**不带工具的流式调用**。
代价是多一次生成，换来真正的流式体验。这是一次明确的取舍，不是浪费。

### 3.3 六步上限

`AGENT_MAX_STEPS` 默认 6。它同时限制了三件事：延迟、token 成本、
以及模型「为了显得努力而反复检索」的倾向。超限会返回 `MAX_STEPS` 错误，
而不是无限循环。

### 3.4 工具失败不是请求失败

工具超时、抛异常、工具名不存在、参数非法——这些都不会让 HTTP 500。
它们会被包装成一个「失败的工具结果」塞回对话，模型看到后可以：

- 换个关键词再查；
- 换一个工具；
- 直接告诉用户做不到。

这是 agent 和传统接口最大的区别：**错误是上下文的一部分，不是终点。**

## 4. 事件协议：为什么是 NDJSON

Python → Java 之间用 **NDJSON**：一行一个 JSON 对象，用换行分隔，UTF-8。
而不是 SSE。

原因很实际：

- Java 现有的字节流解码器本来就是「按行处理」，NDJSON 与它同构，
  只需要在行尾多一步 JSON 解析；
- SSE 的 `data:` / `event:` 前缀在裸流转发时容易和正文冲突；
- 前端协议不用变：Java 仍然按 SSE 帧推给浏览器。

### 4.1 事件类型

所有事件共享 `v`、`type`、`run_id`、`ts` 四个字段。

| 事件 | 作用 | 关键字段 |
|---|---|---|
| `start` | 一次 run 开始，必须第一个 | `session_id`、`user_id` |
| `thought` | 模型在调工具前的说明文字 | `step`、`text` |
| `tool_call` | 即将调用工具 | `step`、`call_id`、`name`、`args` |
| `tool_result` | 工具结果 | `ok`、`summary`、`data`、`elapsed_ms`、`error` |
| `answer` | 最终回答的逐字增量 | `delta` |
| `confirm_required` | 写操作等待人工确认 | `call_id`、`name`、`args`、`token`、`expires_at` |
| `done` | 成功终态（唯一可信的成功信号） | `steps`、`usage` |
| `error` | 失败终态 | `code`、`message`、`retryable` |

### 4.2 三条硬规则

1. **每个 run 恰好一个终态**：一个 `done` 或一个 `error`，之后不再有事件。
2. **`summary` 给模型看，`data` 给前端看。**
   `summary` 控制在 2000 字符内，避免撑爆上下文；
   `data` 序列化后超过 2KB 就不下发细节，并标记 `truncated`。
3. **HTTP 200 不等于成功。**
   Python 的 `BUSY`、`MODEL_ERROR`、`MAX_STEPS` 都是「先发一个 `error` 事件，
   然后正常关闭流」。所以 Java 和前端必须**见到 `done` 才算成功**。
   这条规则在 Java 和前端各实现了一次，是有意重复：两边都要能独立判断终态。

## 5. 工具系统

### 5.1 一个工具由什么组成

- 名字；
- 给模型看的描述（说明什么时候用、什么时候不用）；
- JSON Schema 参数定义；
- 异步执行函数；
- 超时时间；
- 是否是写操作（`side_effect`）。

工具在导入时自动注册。新增工具只需要：写一个类、注册、把模块加入
`agent/tools/__init__.py`。

### 5.2 工具描述就是提示词

模型选不选一个工具、参数传得对不对，**80% 取决于描述**，而不是代码。
所以描述要写「使用条件」和「反例」，例如：

- `kb_search`：涉及公司制度、文档时用；计算、时间、常识不要用；
  同一份信息最多查两次。
- `kb_ingest`：用户明确说「把某文件入库」时才用；**你无法访问用户本机文件系统**；
  找不到文件时提示用户点页面上的上传按钮，不要索要路径或全文。
- `biz_query`：只能使用预定义查询，不支持自由 SQL。

### 5.3 工具清单

| 工具 | 读/写 | 说明 |
|---|---|---|
| `kb_search` | 读 | 知识库检索，可指定 mode / top_k |
| `kb_status` | 读 | 入库进度：最近任务 → doc_status → 暂存区 |
| `calculator` | 读 | 安全四则运算，不用 `eval` |
| `now` | 读 | 当前时间 |
| `web_search` | 读 | 配置后才会注册 |
| `biz_query` | 读 | 查业务库，预定义查询，无自由 SQL |
| `kb_ingest` | 写 | 对暂存文件触发入库 |
| `kb_delete` | 写 | 删除文档及派生数据，需人工确认 |

注意：**没有 `kb_stage` 工具**。上传暂存是 HTTP 接口，模型只拿得到 `staged_id`
或文件名。文件正文永远不进入模型上下文——既省钱，也减少提示注入面。

### 5.4 工具的三种防护

1. **超时**：每个工具自己声明超时，超过就返回失败结果，不拖死整个 run。
2. **异常回灌**：工具抛异常会变成 observation，不会让请求 500。
3. **写操作预检**（`precheck`）：弹确认框之前先做只读检查。
   文件不在暂存区、要删的文档不存在或同名多份时，直接返回失败，
   不让用户为一个注定失败的操作点一次「确认」。

## 6. 写操作与人工确认（HITL）

### 6.1 为什么必须有人工确认

模型可能被文档内容误导，也可能因为用户一句话就自主决定删除。
入库和删除都是不可逆或代价很高的操作，不能由模型单方面执行。

默认配置是：

- `AGENT_ALLOW_WRITE_TOOLS=0`：**写工具根本不出现在模型的工具列表里**，
  模型连「看得到再被拒绝」都做不到；
- `AGENT_REQUIRE_CONFIRM=1`：即使启用了写工具，执行前也必须经过用户确认。

### 6.2 确认流程

```
tool_call(kb_delete)
  → precheck（文档存在吗？同名多份吗？）
  → confirm_required(token, expires_at)
  → 前端弹窗
  → 用户点「批准」或「拒绝」
  → POST /ai/agent/confirm（独立请求，不经过问答流）
  → 批准：执行工具；拒绝：返回“未确认”
  → 无论批准还是拒绝，问答流都继续，最终仍会 done
```

几个容易忽略的细节：

- **流不中断**：确认期间 Python 在等，但问答连接一直开着；确认接口是另一条请求。
- **拒绝是正常路径**：拒绝后工具不执行，`tool_result.ok=false`，模型继续回答。
- **拒绝后不重试**：同一个 run 内，按「工具名 + 规范化参数」记住被拒绝的操作。
  模型换个说法再调一次相同操作时，直接返回「不要重试」，不再弹窗。
- **超时等同拒绝**：`AGENT_CONFIRM_TTL_S` 默认 120 秒。
- **取消要清理 token**：用户断连导致等待被取消时，token 必须在 `finally` 里删掉，
  否则确认接口还能“批准”一个已经没人等待的操作。

### 6.3 为什么用线程 Event + 轮询，而不是 asyncio.Event

确认请求和 agent 循环运行在不同线程：一个在 FastAPI 线程池，一个在常驻事件循环。
`asyncio.Event` 不是线程安全的。用 `threading.Event` + 每 200ms 轮询，
实现更笨，但不会出现跨 loop 调度的隐蔽错误。

## 7. 上传与入库：文件内容不经过模型

### 7.1 两段式流程

```
浏览器上传 ──POST /api/rag/agent/stage──► Java ──► Python 暂存区
                                                     │ 返回 staged_id
模型决定入库 ──kb_ingest(staged_id 或 file_name)──► 读暂存文件 → 提交入库任务
```

上传只暂存，不自动入库。前端上传后会填一句草稿：「请把『xxx.txt』入库」，
用户按发送，模型才会调用 `kb_ingest`，而且仍要经过确认。

### 7.2 为什么不让模型传文件内容

如果工具参数是 `content`，文档正文就会：

- 进入模型上下文，按 token 计费，大文件直接超限；
- 成为提示注入的入口（文档里可以写「忽略之前的指令」）；
- 被写进 trace 和日志，扩大泄露面。

所以模型只接触 `staged_id` 或文件名，正文始终在服务端。

### 7.3 入库涉及的可靠性细节

- **单任务互斥**：同一时间只允许一个入库任务，忙碌时明确返回「已有任务」；
- **任务保留**：已完成任务保留 1 小时 / 最多 20 个，方便下一轮继续查询；
- **MD5 去重**：重复上传直接跳过，返回「已存在」，这是成功而不是失败；
- **删除后清理去重索引**：否则文件删了，重传仍会被判「已存在」；
- **暂存 TTL**：24 小时，避免用户只上传不入库时把磁盘占满；
- **大小上限**：默认 100MB，超限返回 413；
- **同名文件**：删除时如果命中多份，返回「歧义」，不猜。

## 8. 会话记忆与 trace

### 8.1 什么回放，什么不回放

| 内容 | 下一轮是否回放 | 存在哪 |
|---|---|---|
| 用户问题 + 最终回答 | 是 | `chat_history/agent_<session_id>.json` |
| 模型的工具调用 | 否 | `agent_runs/<run_id>.jsonl` |
| 工具返回的观察结果 | 否 | 同上 |

为什么不回放工具消息：

1. 下一轮需要的是「上一轮聊了什么结论」，不是几千字原文；
2. 工具结果来自文档内容，属于不可信数据，反复回放会扩大提示注入面；
3. 工具调用的价值在**可排查**，不在**可续接**。

### 8.2 截断策略

- 最多回放 10 轮（`AGENT_HISTORY_MAX_TURNS`）；
- 单条问题/回答最多 2000 字符（`AGENT_HISTORY_MAX_CHARS`）；
- **写入和读取都截断**：新数据不再写长，旧文件读出来也会被截断。

旧链路曾经因为 `top_k` 撑爆过一次上下文，这个教训直接写进了默认值。

### 8.3 trace 是排查工具

每次 run 写一个 `agent_runs/<run_id>.jsonl`，**每一步立即追加**。
它只写不读，不参与推理。记录内容：

- `start` / `thought` / `tool_call` / `confirm_required` / `tool_result` / `error` / `done`；
- **不记录逐 token 的 `answer`**：一次回答上千条，每条都开关文件，会把事件循环拖慢，
  而且正文本身已经在最终回答里。

记忆回答「聊过什么」，trace 回答「这次为什么这么做」。

## 9. 取消、超时与并发

### 9.1 agent 必须跑在 LightRAG 的常驻事件循环上

LightRAG 的模块级共享锁绑定到「第一次获取它的那个事件循环」。
如果在 agent 里自己 `asyncio.run()`，就会触发
`bound to a different event loop`。

所以 Runtime 只做一件事：把 agent 协程**投递**到 `LightRAGService` 的常驻 loop，
再通过线程安全队列把事件搬回同步生成器。agent 内部禁止新建事件循环。

### 9.2 真正的取消

`Future.cancel()` 对**已经开始执行**的协程无效，它只能取消还没开始的任务。
用户断连后，协程可能还在调模型、等确认、或者跑工具。

正确做法：

1. 协程开始时把自己的 `asyncio.Task` 登记下来；
2. 消费者退出时，通过 `loop.call_soon_threadsafe(task.cancel)` 把取消注入进去；
3. 显式关闭异步生成器，避免留下 pending 的 `async_generator_athrow`。

### 9.3 删除为什么放在线程里

删除文档会重建受影响的实体和关系，可能调用模型，耗时很长。
如果直接 await，取消会把它从中间切断，留下孤立数据。

做法是把它放进 `asyncio.to_thread`：

- 用户断连时，**停止等待**；
- 删除本身继续跑完。

宁可让用户多等一会儿，也不留下「删了一半」的状态。

### 9.4 并发与忙碌

- agent run 有并发上限（默认 2），超过返回 `BUSY`；
- 入库是单任务互斥，第二个任务返回「已有任务」，而不是悄悄排队；
- 单 worker 是硬约束：多 worker 会多个进程同时写同一份向量库目录。

## 10. Java BFF 在做什么

Java 看起来只是「转发」，但有几件事必须在它这里做：

| 职责 | 原因 |
|---|---|
| 注入 `X-User-Id` | 浏览器不可信，身份只能由 BFF 注入 |
| UTF-8 字节流解码 | 汉字可能被切在两个网络包之间 |
| NDJSON 行缓冲 | 一行可能跨包，一个包可能有多行，最后一行可能没换行 |
| 原样转发为 SSE | 前端协议保持不变 |
| 攒最终正文 | 上游只流一次，不落库就没了 |
| 终态判定 | 见 `done` 才算成功 |
| 轨迹落库 | `chat_step`，旁路观测 |
| 取消传播 | 浏览器断开 → 关闭上游连接 → Python 收到取消 |

### 10.1 两个表的关系

- `chat_message`：一问一答各一行。提问和空的助手行在请求开始时落库，
  助手行状态是 `STREAMING`；流结束时更新一次终态。
- `chat_step`：agent 的思考与工具调用流水。`tool_call` 先插入一行 `RUNNING`，
  `tool_result` 到达后按 `run_id + call_id` 回填。
- `chat_step.assistant_id` 指向具体的助手消息。没有它，同一会话连续追问时，
  只能按时间和会话 ID 猜「这条轨迹属于哪次回答」，很容易挂错。

**所有 `chat_step` 写入排在同一个单线程上**：如果 `tool_result` 的更新先于
`tool_call` 的插入执行，就会命中 0 行，轨迹永远少一条。单线程既保证顺序，
又把阻塞的 JDBC 从网络事件循环上挪走。

### 10.2 为什么有 `biz_query` 的内部接口

Python 需要查业务库（会话、消息、入库任务），但：

- 不想把 MySQL 凭证发给 Python；
- 不想让 Python 知道业务库 schema；
- 更不能给模型自由 SQL。

所以 Java 暴露一个内部接口：查询名 + 白名单参数，SQL 和表名写死在 Java，
身份参数（`user_id` / `session_id`）由服务端注入，模型只能传 `limit`。
接口用独立的 `X-API-Key` 保护，未配置时整体 503，Python 也不注册这个工具。

## 11. 前端：事件驱动的状态机

前端不再「猜 delta 信封」，而是拿到什么事件就应用什么状态：

| 事件 | UI 行为 |
|---|---|
| `start` | 记录 `run_id` |
| `thought` | 追加到可折叠的「决策过程」 |
| `tool_call` | 新建工具卡片（运行中） |
| `tool_result` | 按 `call_id` 更新卡片：成功/失败、摘要、耗时 |
| `confirm_required` | 弹确认框，批准/拒绝发独立请求 |
| `answer` | 追加正文 |
| `error` | 记录原因；没有 `done` 就按失败/中断收尾 |
| `done` | 终态成功 |

设计取舍：

1. **轨迹跟消息走**，不做全局时间线。往回翻历史时，那次调用是检索还是删除，
   必须跟着对应的回答。
2. **确认期间不 abort 流**。弹窗只是覆盖层，问答流仍然开着。
3. **拒绝也是成功路径**。工具不执行，Agent 继续回答，终态仍是 `done`。
4. **store 是模块级单例**，切页签不会丢状态，也不会打断正在生成的回答。

## 12. 踩坑清单（最有学习价值的部分）

下面每一条都是复查时真实发现的问题，按「现象 → 根因 → 修法」整理。

| 现象 | 根因 | 修法 |
|---|---|---|
| 删除文档后重传，永远提示「已存在」 | MD5 索引只记 hash，不知道它属于哪个文件，删除时清不掉 | 索引改成「hash + 文件名」，删除后按文件名和 content_hash 清理 |
| 多轮对话后上下文爆炸 | 历史只限轮数，不限单条长度 | 单条问题/回答写读都截断到 2000 字符 |
| 用户断开后后台还在跑 | `Future.cancel()` 停不了运行中的协程 | 登记 Task，向常驻 loop 注入 `CancelledError` |
| 取消后确认 token 还活着 | 异常路径没清理 | `confirm.wait()` 在 `finally` 里删 token |
| 删除被取消后留下半截数据 | 取消直接打断了删除协程 | 删除放进线程，取消只停止等待 |
| 刚完成的入库任务立刻查不到 | 只保留「当前任务」 | 任务注册表保留 1 小时 / 最多 20 个 |
| trace 拖慢回答 | 逐 token 写 `answer` 事件，每条约一次文件开关 | trace 只记决策与工具事件 |
| 上传后无法入库 | 上传只落盘，没有接口返回 `staged_id`，工具也不认文件名 | 打通 `stage → kb_ingest(file_name)` |
| 工具耗时忽大忽小 | 用两端时间戳相减，受时钟和网络分帧影响 | Python 实测 `elapsed_ms` 下发，Java/前端优先使用 |
| token 用量只统计最后一步 | 每轮 planning 的 usage 被覆盖 | 累计每轮 planning + 最终流式 |
| 同名文档被误删 | 命中多份时取了第一份 | 命中多份返回「歧义」，不猜 |
| 用户拒绝后模型反复重试 | 模型换个说法再调一次相同操作 | 同一 run 内按「工具名 + 规范化参数」短路 |
| 查一个不存在的文件，却返回别的文件的状态 | 按文件名找不到时回退到「最新一条记录」 | 指定文件名必须精确匹配，查不到就是查不到 |
| 写工具明明关着，模型却说「未启用」 | 这是预期行为：写工具根本没进模型可见列表 | 要入库需显式设置 `AGENT_ALLOW_WRITE_TOOLS=1` |
| 文件不存在也弹确认框 | 确认发生在工具执行之前，没有预检 | 新增 `precheck`，注定失败的操作不打扰用户 |
| 历史轨迹挂到错误的回答上 | `chat_step` 只有 `session_id`，没有消息 ID | 新增 `assistant_id`，指向具体的助手消息 |

这些问题的共同点：**都不是模型效果问题，而是状态、边界和可观测性问题。**
做 agent 系统，大部分工作量在这里。

## 13. 配置与安全默认值

| 配置 | 默认值 | 含义 |
|---|---|---|
| `AGENT_ENABLED` | `1` | 关闭时接口仍存在，但返回结构化 `AGENT_DISABLED` 错误 |
| `AGENT_MAX_STEPS` | `6` | 决策循环上限 |
| `AGENT_STEP_TIMEOUT_S` | `90` | 单次规划调用超时 |
| `AGENT_TOOL_RESULT_MAX_CHARS` | `2000` | 给模型的 observation 上限 |
| `AGENT_HISTORY_MAX_TURNS` | `10` | 回放轮数 |
| `AGENT_HISTORY_MAX_CHARS` | `2000` | 单条历史截断 |
| `AGENT_MAX_CONCURRENT_RUNS` | `2` | 并发 agent run 上限 |
| `AGENT_ALLOW_WRITE_TOOLS` | `0` | 写工具总闸门，**默认关闭** |
| `AGENT_REQUIRE_CONFIRM` | `1` | 写操作人工确认 |
| `AGENT_CONFIRM_TTL_S` | `120` | 确认过期时间 |
| `AGENT_STAGE_MAX_BYTES` | 100MB | 暂存文件大小上限 |
| `AGENT_WEB_SEARCH_ENABLED` | `0` | 联网搜索开关 |
| `AGENT_BIZ_QUERY_KEY` | 空 | 未配置时 Java 内部查询接口 503，Python 不注册 `biz_query` |

安全上的三条底线：

1. **身份只来自 BFF 注入的请求头**，请求体里的 `user_id` 一律忽略；
2. **写工具默认不可见**，启用后仍要人工确认；
3. **不给模型自由 SQL**，只给预定义查询和服务端注入的身份范围。

## 14. 如果让你自己复刻一遍，建议这个顺序

### 第一步：先冻结协议

先定事件类型、字段、终态规则、`summary`/`data` 的大小限制。
协议不定，三端都会返工。

### 第二步：先证明底层能力可用

在 REPL 里直接调用 `aquery_data`，打印真实返回结构。
不要先写循环再发现字段名和假设不一致。

### 第三步：只挂一个只读工具，跑通最小循环

先只注册 `kb_search`。用 `curl -N` 直接看 NDJSON：
每行能不能独立解析？事件序列对不对？模型会不会在不该检索时也检索？

### 第四步：解决事件循环

把 agent 协程投递到 LightRAG 的常驻 loop。这一步不解决，后面所有工具都会报
`bound to a different event loop`。

### 第五步：做 Java 透传

先不做落库，只做字节流解码 + 行缓冲 + SSE 转发。
用「汉字被切成两个包」「一行跨多个包」的用例测解码器。

### 第六步：做前端轨迹

先渲染 `thought` / `tool_call` / `tool_result` / `answer` / `done`。
确认「没有 done 就不算成功」这条规则在 UI 上也成立。

### 第七步：加记忆和 trace

记忆只回放问答，trace 记录每一步。两者物理隔离，不要混在一起。

### 第八步：最后做写操作

顺序不能反：**只读工具 → 写工具闸门 → 预检 → 人工确认 → 取消清理 → 拒绝去重。**
每一步都要有对应的失败路径测试。

### 新增一个工具的检查清单

- 描述写清楚「什么时候用 / 什么时候不用」了吗？
- 参数有 JSON Schema 约束吗（枚举、范围、必填）？
- 超时设了吗？
- 是写操作吗？是的话 `side_effect=True`，并考虑 `precheck`。
- 返回值区分了「给模型的 summary」和「给前端的 data」吗？
- 异常会不会被回灌成 observation，而不是抛到请求层？
- 会不会把敏感信息（路径、凭证、SQL）写进 summary 或 trace？

### 测试策略

- **离线单测**：模型和 LightRAG 都用假实现，不访问网络、不启动向量库；
- **假上游**：不启动真实模型，也能验证前端完整交互；
- **字节级测试**：专门测半个汉字、半行、CRLF；
- **端到端脚本**：普通提问、批准写操作、拒绝写操作三条路径。

## 15. 出问题时先看哪里

| 症状 | 先看 | 常见原因 |
|---|---|---|
| 回答结束了但 UI 显示失败 | 事件流里有没有 `done` | Python 发了 `error` 后正常关流，被误判为成功/失败 |
| 工具卡片一直转圈 | `chat_step.status` 是否为 `RUNNING` | `tool_result` 没到，或按 `run_id + call_id` 没匹配上 |
| 工具显示成功但结果不对 | trace 里的 `tool_call.args` 和 `tool_result.summary` | 参数解析错误、工具查错了数据源 |
| 写工具完全看不到 | `AGENT_ALLOW_WRITE_TOOLS` | 默认关闭，模型可见列表里没有它 |
| 用户断连后后台继续跑 | 日志有没有 `CancelledError` | 取消没有注入到运行中的 Task |
| 中文乱码或事件丢失 | Java 的字节解码与行缓冲 | 半个汉字、半行、最后一行没换行 |
| 历史回答张冠李戴 | `chat_step.assistant_id` | 老库没做 `ALTER TABLE`，或 `beginExchange` 失败时为 NULL |
| 入库查不到但任务在跑 | `kb_status` 的查询顺序 | 正在入库的文件还没写进 `doc_status`，要先查任务注册表 |

排查顺序建议：**trace → 事件流 → `chat_step` → `chat_message`**。
先看 Python 当时到底做了什么，再看传输有没有丢，最后看落库是否正确。

## 16. 术语表

| 术语 | 含义 |
|---|---|
| RAG | 检索增强生成：先查资料，再让模型回答 |
| Agentic RAG | 让模型自己决定查不查、查什么、查几次，而不是走固定流程 |
| ReAct | Reason + Act：模型交替进行「思考」和「调用工具」 |
| Tool calling | 模型输出结构化的工具名和参数，由宿主执行 |
| Observation | 工具返回给模型的观察结果 |
| HITL | Human-in-the-loop：关键操作需要人确认 |
| NDJSON | 一行一个 JSON 的流式格式 |
| Trace | 一次 run 的完整决策轨迹，用于排查 |
| side effect | 会改变系统状态的操作（写入、删除） |
| precheck | 执行写操作前的只读校验 |

## 17. 最后总结

这次改造真正做的事情，不是「给 RAG 加了一个模型循环」，而是：

1. **把 LightRAG 从「回答者」降级成「检索器和写入器」**，
   把决策权交给外层循环；
2. **把能力封装成工具**，每个工具都有明确的输入、输出、超时和副作用标记；
3. **把一次回答变成可观察的事件流**，让三端都能独立判断状态；
4. **把写操作关进笼子**：默认不可见、执行前预检、人工确认、拒绝去重；
5. **把可靠性做成默认值**：上下文截断、任务保留、真实取消、单线程有序落库。

如果只记一个结论：

> Agentic 系统的难点不在「让模型会调工具」，
> 而在「模型调错、用户反悔、网络断开、进程重启时，系统仍然可解释、可恢复、可审计」。
