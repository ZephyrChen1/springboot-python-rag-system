# 知识库前端工程说明 —— 每个文件在做什么

> 目标：给不写前端的人看的分工说明。
>
> 本文**不解释代码语法**，只解释三件事：这个文件为什么存在、它和后端哪个概念对应、
> 你什么时候会需要动它。看完你应该能自己判断「我想改个东西，该找哪个文件」。

---

## 一、先建立一个心智模型

如果你只读一节，读这节。不理解这个差异，后面所有文件的分工都会觉得别扭。

### 1.1 后端是「请求 → 处理 → 返回」，前端不是

你的 `RagController` 收到一个请求，处理完返回，然后就**忘了这件事**。下一次请求来，
它不记得上一次发生过什么。这是后端的常态。

前端相反：**页面是一个一直活着的东西**。用户拖了 3 个文件，这 3 个文件正在入库、
各自走到哪一步了——这些信息必须**存在某个地方**，一直到用户关掉页面为止。

所以前端一定有一块地方专门存「当前的状态」。这个工程里有两个这样的地方，
一个功能一个：入库是 `src/ingest/ingestStore.js`，问答是
`src/chat/chatStore.js`。前者是整个前端最有分量的一个文件。

> 一句话：**界面只是状态的一个投影**。数据变了，界面自动跟着变；
> 你改界面代码时基本不用管数据，改数据时基本不用管界面。这是前端和写后端最不一样的地方。

### 1.2 前端的「等待」不能阻塞

你的 Java 代码里，调 FastAPI 是同步的——线程就停在那儿等结果。

前端不能这么干。浏览器只有一个线程跑界面代码，你要是停在那儿等，
**整个页面会卡死，用户点什么都没反应**。所以前端处理"等待"只有两种办法：

- **轮询**：每隔一段时间主动去问一次「好了吗」。本工程用的就是这个。
- 或者服务端主动推（SSE / WebSocket）。本工程没用。

这就是为什么你会看到代码里有个"每隔 1.5 秒问一次"的逻辑——
不是设计得笨，是浏览器环境下的标准做法。

### 1.3 为什么前端要"分层"

和后端一样，前端也要分层，否则会写成一坨。本工程的分层和你的后端几乎一一对应：

```
你的后端                              本前端
─────────────────────────────────────────────────────────
RagController     接收前端请求   ←→   pages/UploadPage.jsx   接收用户操作
RagService        业务编排       ←→   ingest/ingestStore.js  业务编排（核心）
RagClient         调上游         ←→   api/rag.js             调后端接口
RagClientConfig   统一错误处理   ←→   api/http.js            统一错误处理
application.yaml  配置           ←→   vite.config.js         配置
pom.xml           依赖清单       ←→   package.json           依赖清单
```

看这张表你就能猜到每个文件大概是干嘛的。下面逐个说。

> **问答（第二个功能）的对应关系是一模一样的**，只是右列换了人：
> 页面换成 `pages/ChatPage.jsx`，store 换成 `chat/chatStore.js`，
> 接口封装还是 `api/rag.js`（多了一个 `chatStream`），错误处理还是 `api/http.js`。
> 读完入库这一半，问答那一半只需要再看两件事：**SSE 分帧**和**流式状态机**。

## 二、一张图：文件之间怎么协作

从用户拖入文件，到看见「成功」，数据是这样流动的：

```
   用户拖入文件
        │
        ▼
┌──────────────────────┐
│ pages/UploadPage.jsx │  接住用户的文件，做初步检查（格式、大小）
└──────────┬───────────┘
           │ 把文件交给 store
           ▼
┌──────────────────────────────┐
│ ingest/ingestStore.js   ★核心 │  存着所有任务的状态；
│  · 串行闸门（一次只传一个）    │  决定什么时候上传、什么时候去问进度
└──────┬────────────────▲──────┘
       │ 调接口          │ 拿到最新进度
       ▼                 │
┌──────────────────────┐ │
│ api/rag.js           │─┘  只负责"发请求 / 收响应"，不管业务
└──────────┬───────────┘
           │ 用统一的 http 实例
           ▼
┌──────────────────────┐
│ api/http.js          │  统一给请求加前缀、统一把错误翻译成人话
└──────────┬───────────┘
           │
           ▼
      Java :8080  ──►  FastAPI :8102
           （这一段就是你的后端了）

  状态一变，下面这条线自动刷新界面：
┌──────────────────────────────┐
│ hooks/useIngestTasks.js      │  把 store 里的状态"接"给界面
└──────────┬───────────────────┘
           ▼
┌──────────────────────┐   ┌──────────────────────┐
│ components/TaskList  │──►│ components/TaskItem  │  画出每个任务的
│   （列表容器）        │   │  （一行：文件名+进度）│  进度条 / 转圈 / 结果标签
└──────────────────────┘   └──────────────────────┘
```

**记住一句话**：`UploadPage` 只管"收"，`ingestStore` 管"怎么办"，`api/*` 管"怎么发"，
`components/*` 管"怎么画"。改需求时先想清楚是哪一类，就知道该找谁。

## 三、逐个文件说明

按"你要不要懂它"分成四组。**第一组你基本可以完全无视。**

### 第一组：工程配置（知道有这回事就行，不用懂）

| 文件 | 作用 | 类比你的后端 |
| --- | --- | --- |
| `package.json` | 声明这个前端依赖哪些第三方库，以及 `npm run dev` 这类命令对应做什么 | `pom.xml` |
| `package-lock.json` | 把每个依赖的**精确版本**锁死，保证换台机器装出来一模一样 | 类似 Maven 的版本锁定 |
| `vite.config.js` | 开发服务器的配置。**本工程最关键的一条在它里面**（见下方） | `application.yaml` |
| `.gitignore` | 告诉 git 哪些东西不要提交（`node_modules`、构建产物） | 根目录那个同名文件 |
| `index.html` | 整个应用唯一的 HTML 文件，里面其实只有一个空壳 `<div id="root">` | 没有直接对应物 |

**`vite.config.js` 里最重要的那条**：

它配了「浏览器访问 `/api/...` 时，帮我转发到 `localhost:8080` 去」。
这条配置就是**「后端一行都不用改」的全部原因**——浏览器以为 `/api` 是自己人，
所以不会触发跨域检查，后端也就不需要配 CORS。

哪天你要把前端部署到正式环境，这条代理**会失效**（正式环境没有 Vite 了），
那时要换成 nginx 做同样的事。这是部署时最容易踩的坑。

---

### 第二组：入口与外壳（各看一次就够）

| 文件 | 作用 | 类比 |
| --- | --- | --- |
| `src/main.jsx` | 整个前端的启动点。它做三件事：把 React 挂到页面上、装载中文语言包、装载全局主题色 | 你的 `ComputerBizServiceApplication`（启动类） |
| `src/App.jsx` | 页面最外层的样子：一条标题栏 + 一块内容区。内容区里放的是 `UploadPage` | 没有直接对应物，是个"页面框架" |
| `src/styles.css` | 纯样式（间距、边框、字体大小）。不含任何逻辑 | CSS 文件 |

这三个文件你可以理解成"这个网页长什么样"的骨架，**改布局才需要动它们**。

---

### 第三组：和后端通信（对应你的 client + config 层）

| 文件 | 作用 | 类比 |
| --- | --- | --- |
| `src/api/http.js` | **统一的请求出口**。所有请求都经过它，所以错误处理只写一次 | `RagClientConfig`（就是配 `defaultStatusHandler` 那个） |
| `src/api/rag.js` | 三个接口的具体封装：`uploadDocument`、`queryTask`、`chatStream`，一个方法对一个接口 | `RagClient` |

**`http.js` 干了什么，为什么值得单独一个文件：**

你的后端所有错误出口都是 `{"detail": "..."}`。前端如果每个地方都自己解析一遍，
很快就会写乱。所以 `http.js` 把这件事**集中做一次**：

- 后端说 `{"detail":"不支持的文件格式: .md"}` → 前端就拿到一句可以直接显示的话
- 后端根本没启动 → 翻译成「无法连接后端服务，请确认后端已启动」
- 用户自己取消了上传 → 标记成"取消"，**不弹错误提示**

它还负责把 HTTP 状态码（404 / 502 这些）一起保留下来。这个很重要：
轮询时遇到 404 说明"任务已经不存在了，别白费劲"，遇到 502 说明"可能只是暂时故障，
等一下再问"。**没有这个状态码，前端就没法区分这两种情况。**

**`rag.js` 干了什么：**

只做两件事：把请求发出去、把回来的 JSON 整理成前端好用的形状。

顺带一提，它还做了一层**字段名保险**：后端返回的是 `job_id` 这种下划线命名，
前端代码里习惯用 `jobId`。它在中间做一次转换。这样万一以后后端改了命名风格，
只需要改这一个文件，界面代码一行都不用动。

**`chatStream` 为什么长得和另外两个不一样（它用 fetch，不用 axios）：**

上传和轮询是「发一个请求，等一个结果」，axios 正好。但问答是**流式**的 ——
服务端生成一个字就推一个字。浏览器的 XHR（axios 的地基）没有流式读的口子，
所以这一段只能用 `fetch` + `ReadableStream` 手动读、手动把字节流切成一条条 SSE 事件。

这件事的代价是：错误处理得自己做一遍。于是 `http.js` 把「抽出 `{"detail":...}`
+ 带上状态码」抽成了一个**导出的函数** `toHttpError()`，两条路共用 ——
否则错误文案会有两份实现，早晚有一份先腐烂。

这段代码里还埋着四个上游/中间层的坑（注释里都写了原因）：

1. **Java 侧 Spring 写 SSE 时不转义内容里的换行** —— 一段多行文本会被拆成裸行。
   不处理的话，markdown 回答在界面上只剩第一行。
2. **上游出错时状态码已经改不了了**（响应已按 200 提交），Spring 只能把错误 JSON
   直接写进流里。前端要从这些「没有 `data:` 前缀的悬空行」里把 `detail` 捞出来。
3. **一个汉字占 3 字节**，很容易被切在两个数据块之间。解码器必须带 `{ stream: true }`，
   否则界面上会出现一堆 ``。
4. **SSE 路径上的错误体被 Accept 协商吃掉了**（实测出来的，最容易把人带偏）：
   浏览器发 `Accept: text/event-stream`，接口 `produces` 也是 `text/event-stream`，
   于是 `GlobalExceptionHandler` 返回的 `ApiErrorResp` 找不到能写它的转换器 ——
   5xx 成了「无 Content-Type、body 为空」的裸响应：

   ```
   Accept: application/json   -> 406  {"detail":"Acceptable representations: [text/event-stream]."}
   Accept: text/event-stream  -> 500  ct=null  body=""
   Accept: */*                -> 500  {"detail":"服务内部错误"}
   ```

   而「空 body 的 5xx」在 axios 那条路上等价于「Java 没启动」，`toHttpError`
   于是输出「请确认后端已在 8080 启动」。**那句话在这个接口上是误导** ——
   Java 活着，真实原因是它调用上游失败。`chatStream` 为这条分支单独换了文案兜底。

   **已治本**：`GlobalExceptionHandler` 现在统一走一个私有 `error(...)` 出口，
   在里面 `.contentType(MediaType.APPLICATION_JSON)` —— 显式指定后不再走 Accept 协商，
   错误体一定写得出去，前端拿到的就是上游的真实 detail。

> 这四条都不是猜测，`tools/verify-chat.mjs` 会把它们逐条回放一遍。

### 第四组：业务核心与界面（★ 这才是主体）

#### `src/ingest/ingestStore.js` ★ 最重要

**它是整个前端的大脑。** 前面说过前端必须有地方存状态，就是这里。

它负责四件事：

1. **存所有任务的状态**——每个文件当前是排队中/上传中/入库中/成功/跳过/失败/状态未知
2. **串行闸门**——决定"现在能不能开始传下一个文件"（见下方说明）
3. **轮询调度**——定期去问后端"那个任务好了吗"，问到结果就更新状态
4. **重试与兜底**——网络抖动了重试几次；某个任务卡太久就放弃并提示

**为什么要有"串行闸门"这件事：**

这是本项目最反直觉、也最容易改错的地方。上游 FastAPI 有两条硬限制（已实测确认）：

- 同一时刻**只允许一个**入库任务在跑，第二个会被直接拒绝
- 只保留**最近一个**任务的记录，新任务一提交，旧任务的编号立刻失效

所以多个文件**必须一个接一个来**。而且"一个接一个"的粒度是
**上一个任务彻底结束**，而不是"上一个文件传完了"——
文件传完只是开始，后面还有漫长的入库过程。

如果你看到用户拖了 3 个文件，界面显示"2 个排队中"，那不是卡住了，是**正在按顺序处理**。

> ⚠️ 改这个文件前请一定先读 `frontend/README.md` 里的「上游的硬限制」一节。

#### `src/hooks/useIngestTasks.js`

**它本身几乎没逻辑，只是根"电线"。**

作用是把 `ingestStore` 里存的状态接到界面上，让界面能读到、并且状态一变就自动刷新。

为什么要单独一个文件、不直接在界面里读 store——这属于 React 的写法习惯，
你不需要理解细节。**你可以把它当成 `ingestStore` 的对外接口**：
界面只通过它拿数据和操作，不直接碰 store。

#### `src/components/TaskList.jsx` 和 `src/components/TaskItem.jsx`

- `TaskList.jsx`：任务列表的**外框**。管"有几个任务""全部完成时显示一个清理按钮"。
- `TaskItem.jsx`：**一行任务**长什么样。文件名、大小、进度条或转圈、结果标签、重试/移除按钮。

`TaskItem.jsx` 里最值得知道的是**进度分三段**，因为上传这件事本身就是两段式的：

| 界面显示 | 含义 | 有没有真实百分比 |
| --- | --- | --- |
| 进度条 + "上传中 37%" | 文件字节正在通过网络传 | ✅ 有，是真实的 |
| 进度条满 + "等待服务端受理…" | 字节发完了，后端还没回话 | 通常不到 1 秒，一闪而过 |
| 转圈 + "实体/关系抽取中…（12s）" | 后端在真正干活（入库） | ❌ **没有**，只能显示转圈 |

第三段为什么没有进度条：后端只给了一句人话（`stage` 字段），
没有"完成了 80%"这种数字。硬要画进度条就只能瞎编，
而"进度条卡在 100% 不动"比转圈更让人以为坏了。所以这里刻意用转圈。

#### `src/pages/UploadPage.jsx`

**用户能看到的那个页面，也是用户操作的入口。** 类比你的 `RagController`。

它做三件事：

1. 画出那个大虚线框（拖拽上传区）
2. 用户拖入文件后，**先自己检查一遍**：格式对不对、有没有超过 95MB。
   不合格的直接拦下来提示，不浪费一次网络请求
3. 合格的交给 `ingestStore`，自己的活就干完了

注意第 2 点是有意为之：后端限制单个文件 100MB，但网络传输本身还有额外开销，
所以前端卡在 95MB 更稳妥。**前端拦一道，用户体验比让后端报错好得多。**

#### `src/chat/chatStore.js`

**问答这一半的「大脑」**，和 `ingestStore` 同一个位置、同一个套路（状态活在模块里，
组件只订阅）。但它**明显更薄**，因为问题本身更简单：

| | `ingestStore` | `chatStore` |
| --- | --- | --- |
| 要排队吗 | 要（上游只允许一个任务） | 不要 |
| 要轮询吗 | 要（入库是异步的） | 不要 |
| 生命周期 | 一个任务从上传到入库结束 | 一条流从发出到生成完 |
| 状态机 | 7 个状态 + 串行闸门 + 退避重试 | 5 个状态，没有调度 |

它只管四件事：把用户那句话和一条空的 AI 消息放进列表 → 把流里来的每个增量
追加到 AI 消息上 → 按情况收尾 → 让界面能订阅。

**收尾那三种情况是这里最值得看的部分**（对应界面上三种不同的标签）：

| 情况 | 界面显示 | 为什么要分开 |
| --- | --- | --- |
| 正常生成完 | 不打标签 | —— |
| 用户点了「停止生成」 | 已停止 | 是用户自己的操作，**不能显示成失败** |
| 流断了但已经收到一部分 | 回答中断 | 那半截答案往往仍然有用，丢掉它等于逼用户重问一遍 |
| 一个字都没收到 | 未收到回答 | 这才是真的失败 |

> 这和 `ingestStore` 里那条「轮询失败 ≠ 入库失败」是同一条原则：
> **不确定的时候，不要替上游下判断，更不要把已经拿到的信息扔掉。**

#### `src/hooks/useChat.js`

和 `useIngestTasks.js` 一样，只是根电线，没逻辑。**永远不用改。**

#### `src/components/ChatMessage.jsx`

一条消息气泡。刻意只渲染**纯文本**（保留换行），不引 markdown 渲染库：
多一个依赖就多一套 XSS 面，而这里真正要保证的是「一个字都不能少、换行不能丢」。

生成中的那个闪烁光标是一个 CSS 动画（`.chat-caret`），没有任何 JS 定时器。

#### `src/pages/ChatPage.jsx`

输入框 + 消息列表 + 「停止生成」/「发送」两个按钮。三件事值得知道：

1. **回答是流式的，所以列表是固定高度的滚动区**（`max-height: 52vh`）。
   让它自己长会把输入框顶出屏幕，用户得一边打字一边追着它滚。
2. **自动贴底是有条件的**：只在用户本来就贴着底部时才滚。不然用户往上翻看
   刚才那句话，新到的增量会一直把他拽回底部 —— 生成中这个问题特别烦人。
3. **生成中不禁用输入框**，用户可以先把下一个问题打好。闸门在 store 里
   （`streaming` 时 `sendMessage` 直接返回），界面上则是把「发送」换成「停止生成」。

### 额外：四个开发用的验证脚本

| 文件 | 作用 | 要不要后端 |
| --- | --- | --- |
| `tools/verify-serial.cjs` | 自动开一个浏览器，拖入 3 个文件，验证**真的在串行**处理，并截图 | 要（三个进程都在跑） |
| `tools/verify-error.cjs` | 在后端故意停掉的情况下上传，验证界面**不会白屏、不会显示错误的"入库失败"** | 要（且要停掉后端） |
| `tools/verify-chat.mjs` | 回放问答链路的脏情况：半个汉字跨块、帧被切断、不转义的换行、错误 JSON 混进流里、中途停止 | **不要** |
| `tools/verify-http-errors.mjs` | 逐条验证失败时吐给用户的那句文案 | **不要** |

它们不参与打包，只在开发时手动跑：

```bash
node tools/verify-serial.cjs 文件1 文件2 文件3
node tools/verify-chat.mjs
```

留着它们的价值在于：这几块逻辑一旦被改坏，界面表现都是"看起来像玄学 bug"——
串行坏了会说"传 3 个文件 2 个失败"；分帧坏了会说"回答少了半段"或"明明出错了
却显示成功"。有脚本在，一跑就知道是不是这里坏的。

> 后两个（`.mjs`）不需要后端：它们自己起临时服务器 / 自己造字节流回放。

## 四、一次「拖入 3 个文件」的完整旅程

把所有文件串起来看一遍，你就彻底懂了：

| 步骤 | 发生了什么 | 涉及文件 |
| --- | --- | --- |
| 1 | 用户把 3 个文件拖进虚线框 | `UploadPage.jsx` |
| 2 | 检查格式和大小，3 个都合格 | `UploadPage.jsx` |
| 3 | 把 3 个文件登记成 3 个任务，状态都是「排队中」 | `ingestStore.js` |
| 4 | 闸门放行第一个文件，开始上传字节 | `ingestStore.js` → `api/rag.js` → `api/http.js` |
| 5 | 界面显示：a 上传中 45%，b/c 排队中 | `components/*` |
| 6 | 第一个文件传完，后端返回一个任务编号 | `api/rag.js` |
| 7 | 拿到编号，开始每隔 1.5 秒去问一次"好了吗" | `ingestStore.js` |
| 8 | 每次问回来的进度文案刷新到界面上 | `hooks/` → `components/*` |
| 9 | 后端说完成了，结果是"成功" | `ingestStore.js` |
| 10 | 闸门放行第二个文件，重复 4~9 | `ingestStore.js` |
| 11 | 三个都完成，界面显示三个绿色"成功"标签 | `components/*` |

**注意第 10 步**：第一个文件彻底结束之前，第二个文件**不会**开始。
这就是上面说的串行闸门。

## 六、你基本永远不用碰的文件

- `package-lock.json` —— 让工具自己维护，手动改会出乱子
- `src/main.jsx` —— 启动配置，除非要换主题色或加全局设置
- `src/hooks/useIngestTasks.js`、`src/hooks/useChat.js` —— 只是两根电线，没逻辑可改
- `src/utils/format.js` —— 就一个把字节数变成"2.88 KB"的小函数
- `node_modules/`、`dist/` —— 都是自动生成的，**不要提交到 git**（已在 `.gitignore` 里）
