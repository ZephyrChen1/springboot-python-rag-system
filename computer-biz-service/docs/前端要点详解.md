## 0. 先建立直觉:八个概念,用 Java 的话说

你写过 Spring Boot、DAO、单例、观察者,这些经验全部可以平移。

| 前端概念 | 用 Java 类比 | 在你项目里的对应物 |
| --- | --- | --- |
| **组件(component)** | 一个「返回界面的方法」。输入 props,输出一段界面 | `ChatPage`、`TaskItem` 这些 `.jsx` 文件 |
| **props** | 方法参数,而且**只读**。子组件不能改传进来的 props | `<TaskItem task={task} onRetry={...} />` |
| **state** | 带记忆的局部变量。改了它,方法会被**重新执行一遍** | `const [draft, setDraft] = useState('')` |
| **渲染(render)** | 重新执行组件这个「方法」的函数体,产出新的界面描述 | 每次 `emit()` 之后 React 重跑组件 |
| **Hook** | 框架提供的接口,**有调用规则**(只能在组件函数顶层调,不能放进 if/循环里)。类似 Spring 里必须在容器回调点调用的东西 | `useState` / `useEffect` / `useRef` / `useSyncExternalStore` |
| **store(模块级单例)** | **就是你在 LearnDao 里写过的单例**,只不过里面装的是界面状态 | `chatStore.js`、`ingestStore.js` |
| **订阅 / 发布** | 观察者模式。`subscribe(监听器)` 返回「取消订阅」的函数 | `chatStore.subscribe` + `listeners.forEach(l => l())` |
| **axios 拦截器** | Spring 的 `HandlerInterceptor` / `Filter`。请求出去和回来都过一遍 | `http.interceptors.response.use(...)` |
| **AbortController** | `Future.cancel(true)`。把一个在途请求掐掉 | `controller.abort()` |
| **Vite 代理** | nginx 反向代理 / 网关路由。把 `/api` 转发到另一个端口 | `vite.config.js` 的 `server.proxy` |
| **Vite** | Maven,但开发模式下**不打包**,浏览器按需即时编译 | `npm run dev` / `npm run build` |

**一个必须先破的误区**:前端不是「请求 → 等 → 返回」。
后端一个线程等 3 秒无所谓,前端**主线程一等,整个页面就冻住**(按钮点不动、字打不出来)。
所以前端一切「等待」都必须做成「先返回一个空壳,数据到了再补上去」——
这就是为什么你项目里到处是 `status: 'uploading'` 这种中间态。
详见 `docs/前端工程说明.md` §1.1、§1.2。

**第二个误区**:React 组件**整个函数体会反复执行**。
所以你写在函数体里的 `const x = 1 + 1` 每次渲染都会重算,而写在 `useState`/`useRef` 里的东西才有记忆。
想通这一点,后面所有 Hook 都讲得通。

## 1. 「熟悉前后端接口联调」

### 1.1 这句话什么意思

让前端和后端「说得上话」:字段名对得上、格式对得上、错误能互相看懂、端口不同怎么连。
听起来简单,实际上前后端联调 80% 的时间花在**对不上的细节**上。

### 1.2 你项目里的三段式分工

| 文件 | 职责 | 行 |
| --- | --- | --- |
| `frontend/src/api/http.js` | 唯一的 axios 实例 + 错误拦截器 | 全文 145 行 |
| `frontend/src/api/rag.js` | 三个接口的薄封装 + 字段归一化 | 全文 379 行 |
| `frontend/vite.config.js` | 开发期把 `/api` 代理到后端 | 8~19 行 |
| `src/main/java/.../controller/RagController.java` | 后端的另一头 | 整个类 |

三个接口的对应关系:

| 前端调用 | 后端 Java | 上游 FastAPI |
| --- | --- | --- |
| `uploadDocument()` (`rag.js:46`) | `POST /api/rag/documents` | `POST /v1/kb/upload` |
| `queryTask()` (`rag.js:71`) | `GET /api/rag/tasks/{jobId}` | `GET /v1/kb/ingest/{jobId}` |
| `chatStream()` (`rag.js:282`) | `POST /api/rag/chat` | `POST /ai/chat` |

注意这张表:**前端的两段都跟上游不一样**。这是有意的 —— Java 那层存在的理由之一
就是「对前端隐藏上游」,所以路径可以自由重组。

### 1.3 联调时真正对上的六个细节(这些才是能讲的)

**① 字段名:snake_case vs camelCase**

后端 DTO 上写了 `@JsonProperty("job_id")`,所以返回的 JSON 是 `job_id` 而不是 `jobId`。
前端 `rag.js:13` 用一个 `pick` 函数两个都认:

```js
const pick = (obj, snake, camel) => obj?.[snake] ?? obj?.[camel]
```

`rag.js:15` 的 `normalizeUploadResp` 和 `rag.js:29` 的 `normalizeTaskResp`
把后端的原始响应**转成前端内部统一用的形状**。这一步是整个联调能稳的关键:
后面所有组件都只用 `task.jobId`,不再关心后端到底给的是哪个名字。

> 面试点:这就是「防腐层」。后端改字段名,只改这两个函数,组件一行不动。

**② 上传表单的字段名必须和 `@RequestPart` 严格一致**

`rag.js:49`:

```js
form.append('file', file, file.name)   // 字段名必须是 file
```

对应后端 `RagController.java` 的 `@RequestPart("file") MultipartFile file`。
写成 `file2` 后端直接 400。

**③ FormData 千万不要手写 Content-Type**

`rag.js:56` 的注释记了这条:

> 不要手动设 `Content-Type` —— axios 检测到 FormData 会让浏览器自己设置带 boundary 的头。
> 手写会导致 boundary 丢失,后端直接 400。

**④ 可空字段「干脆不发」而不是「发 null」**

`rag.js:211` 的 `buildChatBody`:

```js
const body = { message, session_id: sessionId }
if (userId != null) body.user_id = userId    // null 时这个字段整个不出现
if (topK != null) body.top_k = topK
```

原因(FastAPI 侧 `user_id: int = 0` 是**非 Optional 的 int**):
- 「字段缺失」→ 用默认值 0 ✓
- 「字段是 null」→ 类型错,直接 422 ✗

**同一个坑在 Java 侧也踩了一次**:`AiChatReq` 字段上必须加 `@JsonInclude(NON_NULL)`,
否则 Jackson 会老实地把 `"user_id": null` 发出去。

> 面试点:这是一个**跨三个进程**的契约问题。前端、Java、Python 任一侧理解错,
> 表现都是一个莫名其妙的 422。能讲清楚这条,面试官会觉得你真联调过。

**⑤ 开发期的端口问题用代理解决,而不是 CORS**

前端 5173、后端 8080,浏览器同源策略会拦。你项目选的是**不碰 CORS**,
让 Vite 把 `/api` 代理到 8080,浏览器视角全程只有 5173 一个源。
详见 §6。

**⑥ 上游的硬限制直接决定了前端架构**

联调不只是「通」,还要知道对方**做不到什么**。`frontend/README.md` 里记了实测出来的三条:

| 上游限制 | 前端怎么应对 |
| --- | --- |
| 同时只允许一个入库任务 | `ingestStore` 做串行闸门 |
| 只保留最近一个 job,旧的立刻 404 | 不能「先全传完再慢慢轮询」 |
| 只接受 `.txt` | `UploadPage.jsx:19` 的 `ACCEPT` 跟它对齐 |

### 1.4 一个已经找到根因的真实联调事故

项目里最值钱的一条联调记录(`frontend/README.md` 里有完整版):

浏览器发 `Accept: text/event-stream`,而问答接口的 `produces` 也是 `text/event-stream`,
于是 Java 的 `GlobalExceptionHandler` 想返回 `ApiErrorResp` 时**找不到能写这个对象的转换器**,
5xx 就变成了「没有 Content-Type、body 为空」的裸响应。实测三种 Accept:

```
Accept: application/json   -> 406  {"detail":"Acceptable representations: [text/event-stream]."}
Accept: text/event-stream  -> 500  ct=null  body=""     ← 前端只能瞎猜
Accept: */*                -> 500  {"detail":"服务内部错误"}
```

前端在 `rag.js:314` 针对这条单独改写文案,后端一行 `contentType(APPLICATION_JSON)` 就能治本。

> 面试点:这条能同时证明三件事 —— 你会看响应头、你定位到后端、你给了修复方案。

### 1.5 面试问「怎么联调」怎么答

> 我把前端分了三层:最底下一层是唯一的 axios 实例和错误拦截器,中间一层是每个接口一个薄封装
> 顺手做字段归一化,最上面组件只用归一化之后的形状。
> 联调主要卡在三个地方:字段命名(snake_case)、可空字段的语义(不能发 null)、
> 以及 SSE 那条路的错误体被内容协商吃掉了。前者用归一化解决,后两者我在代码里都留了注释和证据。

## 2. 「了解 React 18 函数组件与 Hooks」

### 2.1 这句话什么意思

React 写界面有两种写法:老的「类组件」和新的「函数组件」。
React 18 时代**函数组件 + Hooks 是唯一推荐写法**。Hooks 是往函数组件里「挂钩子」,
让它能有状态、能处理副作用。

**你项目里全部是函数组件,没有一个是类组件**,而且用了 React 18 新引入的
`useSyncExternalStore` —— 这条本身就值钱,因为它不常用。

### 2.2 项目里用到的东西,逐个对

#### ① 函数组件 + props(只读)

`components/ChatMessage.jsx:21`:

```jsx
export default function ChatMessage({ message }) {
  const mine = message.role === 'user'
  ...
}
```

调用方 `pages/ChatPage.jsx:75`:

```jsx
messages.map((m) => <ChatMessage key={m.id} message={m} />)
```

两个点:
- `{ message }` 是**解构 props**,等价于 Java 里取方法参数的字段;
- `key={m.id}` **必须有**。React 靠它认「这一项还是刚才那一项」。
  用数组下标当 key 是经典 bug —— 列表中间删一条,后面所有项的状态会错位。

#### ② `useState` —— 有记忆的局部变量

`ChatPage.jsx:14`:

```jsx
const [draft, setDraft] = useState('')
```

- `draft` 是当前值,`setDraft` 是唯一能改它的方式;
- **直接 `draft = 'x'` 没用** —— 必须 `setDraft('x')`,React 才知道要重新渲染。
  (这点最反 Java 直觉:它不像给字段赋值,更像是「提交一次变更」。)

`UploadPage.jsx:23` 的 `notice`(跳过文件时的提示)也是同一个用法。

#### ③ `useEffect` —— 副作用,以及必须写对的清理函数

`ChatPage.jsx:23`:

```jsx
useEffect(() => {
  const el = listRef.current
  if (el && stickRef.current) el.scrollTop = el.scrollHeight
}, [messages.length, lastLen])       // ← 依赖数组
```

读法:**依赖数组里任何一个值变了,就重新执行这个函数**。

注意依赖写的是 `lastLen`(`ChatPage.jsx:21` 在渲染时算出来的最后一条消息长度),
而不是 `messages`。因为流式回答时 `messages` 数组每次增量都会换新引用,
写 `messages` 的话每来一个字都要滚一次 —— 写 `lastLen` 才是对的。

**带清理的 effect**(`components/TaskItem.jsx:32`):

```jsx
useEffect(() => {
  if (!live) return undefined
  const timer = setInterval(() => forceTick((n) => n + 1), 1000)
  return () => clearInterval(timer)          // ← 清理函数
}, [live])
```

这是「入库耗时每秒走动」的那个心跳。**返回的函数是清理函数**,
组件卸载或 `live` 变化时 React 会调用它,把定时器清掉 —— 不清就是内存泄漏。
这个模式和你写 `try/finally` 里关资源是一个意思。

#### ④ `useRef` —— 不触发渲染的「盒子」

`ChatPage.jsx:15` 和 `:18`:

```jsx
const listRef = useRef(null)      // 指向 DOM 元素
const stickRef = useRef(true)     // 用户是否「还贴着底部」
```

和 `useState` 的区别:**改 `ref.current` 不会触发重新渲染**。
所以它适合装两类东西:
1. DOM 引用(`listRef.current` 就是那个滚动容器);
2. 「不需要显示、但渲染之间要记住」的值(`stickRef`)。

`stickRef` 解决的体验问题(`ChatPage.jsx:28~31`):用户往上翻历史时,
新到的增量不能把他硬拽回底部。这个判断要读 DOM 尺寸,而且**不该引起重渲染**,
所以放 ref 不放 state。

#### ⑤ `useSyncExternalStore` —— 你项目里最"高级"的一个 Hook

`hooks/useChat.js:11`:

```jsx
const snap = useSyncExternalStore(subscribe, getSnapshot, getSnapshot)
```

这是 React 18 官方专门为「状态活在 React 之外」这种情况提供的 Hook。
它的语义是:**订阅一个外部数据源,它变了就让我重新渲染。**

你项目里两个 store 都是模块级单例(`chatStore.js`、`ingestStore.js`),
内部维护 `listeners` 集合和 `snapshot`:

```js
// chatStore.js:75
export function subscribe(listener) {
  listeners.add(listener)
  return () => listeners.delete(listener)     // ← 返回取消订阅
}

// chatStore.js:64
function emit() {
  snapshot = { ...snapshot }                  // ← 必须是新引用!
  listeners.forEach((l) => l())
}
```

> ⚠️ **`snapshot = { ...snapshot }` 这一行是必需的**,代码注释里写了原因:
> `useSyncExternalStore` 靠**引用是否变化**来判断状态变没变。
> 原地改字段(`snapshot.streaming = true`)引用不变,React 会认为「没变化」,界面就不更新。
> 这和 Java 里 `List.equals()` 的坑是同一类问题。

**为什么要把状态放到 React 外面?** 这是你项目里最值得讲的一个设计决定。
`ingestStore.js:5~15` 的注释列了三条,核心是第 2 条:

> React 18 的 `<StrictMode>` 在开发模式下会刻意执行「挂载 → 卸载 → 再挂载」来暴露副作用 bug。
> 如果轮询由一个 `useEffect` 启动,你会经历「effect 启动 → cleanup 停掉 → effect 再启动」,
> 写错一点就会漏掉轮询。放在模块里则完全不受影响。

`main.jsx:10` 确实开着 `<React.StrictMode>`。这是**认真读过 React 18 文档才知道的坑**。

#### ⑥ 自定义 Hook —— 把「订阅」这件事抽出来

`hooks/useChat.js` 全文只有 13 行,`hooks/useIngestTasks.js` 20 行,都是同一个套路:

```jsx
export function useIngestTasks() {
  const { tasks } = useSyncExternalStore(subscribe, getSnapshot, getSnapshot)
  return { tasks, enqueueFiles, retryTask, removeTask, clearFinished }
}
```

自定义 Hook 就是「以 `use` 开头的普通函数」,作用是让组件里那一行
`useIngestTasks()` 就拿到全部数据和操作,而不用关心 store 怎么实现的。

### 2.3 面试问「React Hooks」怎么答

> 项目里唯一的状态容器是 `useState`(输入框草稿、提示语)和 `useRef`(DOM 引用、
> 贴底判断);真正复杂的两个状态——入库任务列表和问答会话——我没有放在组件里,
> 而是做成模块级单例,组件用 `useSyncExternalStore` 订阅。
> 这么做主要是为了躲开 StrictMode 的双调用,以及让「切页签/组件卸载」不打断在途的轮询和流。
> 另外我刻意没引入 Redux/Zustand 这类库,因为这套 store 一共就两个,自己写反而更清楚。

## 3. 「了解 Ant Design 组件库」

### 3.1 这句话什么意思

Ant Design(简称 antd)是蚂蚁的 React 组件库,提供按钮、表格、上传、弹窗这些现成组件。
好处是不用自己写 CSS 和交互;代价是要理解它的**受控/非受控**约定和一些特殊 API。

### 3.2 项目里用到的组件

| 组件 | 用在哪 | 行 |
| --- | --- | --- |
| `ConfigProvider` | 全局主题 + 中文 | `main.jsx:11` |
| `App`(antd 的) | 提供 message/notification 的 context | `main.jsx:15` |
| `Layout` / `Header` / `Content` | 页面骨架 | `App.jsx:17` |
| `Tabs` | 两个页签 | `App.jsx:32` |
| `Upload.Dragger` | 拖拽上传区 | `UploadPage.jsx:59` |
| `Alert` | 跳过文件的警告条 | `UploadPage.jsx:75` |
| `Card` / `Empty` | 卡片容器、空状态 | `TaskList.jsx`、`ChatPage.jsx:70` |
| `Progress` / `Spin` / `Tag` | 进度条、转圈、标签 | `TaskItem.jsx:69,96,60` |
| `Button` / `Input.TextArea` / `Space` | 交互控件 | `ChatPage.jsx` |
| `Typography` | 统一字体规范 | 各处 |
| `@ant-design/icons` | 图标 | `TaskItem.jsx:3` 等 |

### 3.3 三个「不只是会用」的点

**① 全局配置:`main.jsx:11`**

```jsx
<ConfigProvider locale={zhCN} theme={{ token: { colorPrimary: '#1677ff' } }}>
  <AntdApp>
    <App />
  </AntdApp>
</ConfigProvider>
```

- `locale={zhCN}`:分页器、日期选择器这些内置文案变中文;
- `theme.token`:主色统一改一处;
- **`<AntdApp>` 这层是有讲究的**(`main.jsx:15` 注释):
  antd 的 `message.success()` 这类**静态方法**会脱离主题和 locale 上下文,
  必须用 `<App>` 包一层,改用 context 里的版本才能拿到上面的配置。
  这是看过文档才知道的细节。

**② `Upload.Dragger` 被当成「纯粹的文件选择器」用**(`UploadPage.jsx:25~55`)

这是全项目最绕的一段 antd 用法,值得单独讲。正常情况下 antd 的 Upload 会**自己**发上传请求。
但你的上传流程要排队、要轮询、要重试,antd 管不了,所以把它整个接管了:

```jsx
const handleBeforeUpload = (file, batch) => {
  // ① antd 对同一批里每个文件各调一次 beforeUpload,但每次传进来的 batch 都是整批
  //    只让第一个负责把整批交出去 → 否则拖 10 个文件会入队 100 个任务
  const firstUid = batch?.[0]?.uid ?? file.uid
  if (file.uid !== firstUid) return Upload.LIST_IGNORE
  ...
  // ② 所有分支都必须返回 LIST_IGNORE
  return Upload.LIST_IGNORE
}
```

- `return Upload.LIST_IGNORE` 的意思是「你别管了,我自己处理」。
  注释里写了不返回的后果:`rc-upload` 会以为「可以上传」,然后拿空的 `action` 去发请求;
- `showUploadList={false}`(`UploadPage.jsx:62`):不用 antd 自带的文件列表,
  因为你的列表语义不一样(有排队、轮询、重试),由 `TaskList` 自己渲染。

**③ 用组件属性表达业务语义,而不是硬编码样式**

`TaskItem.jsx:16~21` 用一张表把状态映射成 antd 的 `color`:

```jsx
const OUTCOME = {
  [STATUS.SUCCESS]: { color: 'success',  icon: <CheckCircleFilled />, text: '成功' },
```

## 4. 「了解 axios 封装与错误统一处理」

### 4.1 这句话什么意思

axios 是浏览器里发 HTTP 请求的库。「封装」= 不要在每个组件里各写各的请求;
「错误统一处理」= 各种形态的失败(断网、超时、400、502、HTML 错误页)
最终都变成**同一个形状**的对象,调用方只需判断一次。

### 4.2 骨架:`http.js:15`

```js
export const http = axios.create({
  baseURL: API_PREFIX,      // '/api'
  timeout: 15000,
})
```

全项目**只有这一个 axios 实例**,所有请求都从它出去。
`baseURL` 用相对路径 `/api`,配合 §6 的 Vite 代理,浏览器视角是同源。

### 4.3 核心:响应拦截器(`http.js:124`)

```js
http.interceptors.response.use(
  (res) => res,
  (error) => {
    // ① 主动取消不是错误,只打标记
    if (axios.isCancel?.(error) || error.code === 'ERR_CANCELED') {
      error.isCanceled = true
      return Promise.reject(error)
    }
    // ② 其余全部翻译成统一形状
    return Promise.reject(toHttpError({
      status: error.response?.status,
      rawBody: error.response?.data,
      code: error.code,
      cause: error,
    }))
  },
)
```

拦截器的位置相当于 Spring 的 `HandlerInterceptor`:所有响应先过这里,再交给业务代码。

**`error.response?.status` 那个 `?.` 不能省**(`http.js:134` 注释):

> `error.response` 在断网 / 超时 / 被 abort 时是 `undefined`,必须用可选链,
> 否则这里会抛 `TypeError` —— 你看到的就变成「拦截器自己崩了」而不是真实错误。

### 4.4 统一形状:`toHttpError`(`http.js:73`)

翻译的结果是一个普通的 `Error`,但挂了几个自定义字段:

| 字段 | 含义 |
| --- | --- |
| `message` / `detail` | **可以直接显示给用户的人话** |
| `status` | 真实 HTTP 状态码(没有就是 `undefined`) |
| `isCanceled` | 是不是我们自己主动取消的 |
| `raw` | 原始错误,留给排查 |

`http.js:83~101` 那段是「没有 detail 时怎么编人话」的兜底,每种情况都有理由,挑两条:

```js
} else if (status == null) {
  detail = '无法连接服务,请确认后端已启动(或检查安全软件是否拦截了本地端口)'
} else if (status >= 500 && !hasBody) {
  // 最容易被误读的一种情况:后端没启动时,Vite 代理会返回一个空 body 的 500。
  // 如果只说「服务端错误」,排查时会以为是后端崩了
  detail = `无法连接后端服务(HTTP ${status}),请确认后端已在 8080 启动`
}
```

> 这一类「把技术错误翻译成排查指引」的写法,是「错误统一处理」真正的价值。
> 用户看不懂 502,但看得懂「请确认后端已在 8080 启动」。

### 4.5 `extractDetail`(`http.js:23`)—— 吃下四种错误形态

后端/上游/代理可能返回:

| 形态 | 例子 | 怎么处理 |
| --- | --- | --- |
| 字符串 | 纯文本 | 直接返回,超 300 字截断 |
| `{"detail":"..."}` | FastAPI/Java 业务错误 | 取 `detail` |
| `{"detail":[...]}` | FastAPI 422 校验失败,**是数组** | 摊平成 `user_id: Input should be a valid integer` |
| HTML 错误页 | 502 时代理返回的 | `startsWith('<')` → 返回 `''`,交给兜底 |

第二种如果不特殊处理,`ApiErrorResp(String detail)` 反序列化会直接抛异常,
结果是「整段原始 JSON 被当成错误文案丢给用户」。

### 4.6 整套设计里最值钱的一条:**错误翻译只能有一份实现**

SSE 问答走的是 `fetch` 而不是 axios(原因见 §5),那它怎么保证错误形状一致?
答案是 `rag.js:227` 的 `readErrorBody` + `rag.js:320` 的调用 —— **复用同一个 `toHttpError`**。

`http.js:68` 的注释写得很清楚:

> 为什么抽成导出的函数、而不是只写在拦截器里:SSE 问答走的是 fetch,
> 那条路也必须产出**一模一样**的 Error 形状 —— 否则「错误只翻译一次」就不成立了,
> 早晚会出现两份文案,其中一份先腐烂。

**这句话是整个项目里最像「架构判断」的一句**,而且它和你 Java 侧的
`RagApiException.fromUpstream` 是同一条原则(那里的注释也写着「错误翻译只有一份实现」)。
前后端同一条原则,面试时是很好的素材。

### 4.7 带 `status` 出去是为了业务判断

`ingestStore.js:208`:

```js
const definitive = [400, 413, 415, 422].includes(err?.status)
```

`ingestStore.js:266`:

```js
// 404 = job_id 在服务端已经不存在了。这是终态,重试没有意义
if (err?.status === 404) { ... }
```

> 这就是为什么 `toHttpError` 必须把 `status` 带上而不是只给一句人话:
> **上层要拿状态码做业务决策**。404 不重试,502 重试。

### 4.8 面试问 axios 封装怎么答

> 全项目只有一个 axios 实例,baseURL 走相对路径配合开发代理。
> 错误统一在响应拦截器里翻译成一个固定形状的 Error,带 message、status、isCanceled。
> 关键点有两个:一是取消不是错误,要单独标记,否则会被当成业务失败弹给用户;
> 二是这个翻译函数我导出给了走 fetch 的 SSE 那条路复用 —— 错误文案只能有一份实现,
> 不然两条路各写一份,早晚有一条先腐烂。

## 5. 「了解 AbortController 请求取消」

### 5.1 这句话什么意思

浏览器里的请求默认没法取消。用户点了「停止生成」或者关了页面,
请求还在后台跑,回来还想改界面 —— 这就是 bug。
`AbortController` 是标准的取消机制:创建一个 controller,把它的 `signal` 传给请求,
想取消时调 `controller.abort()`,请求会以一个特殊的「取消错误」失败。

类比:`Future.cancel(true)`,或者给一个长任务设中断标志。

### 5.2 项目里它在四个地方出现

| 场景 | 文件 | 行 |
| --- | --- | --- |
| 「停止生成」按钮 | `chatStore.js` | 184、197~203 |
| 「重新开始」(清空会话) | `chatStore.js` | 205~209 |
| 上传/轮询(每个任务一个) | `ingestStore.js` | 163、235、129~135 |
| 关标签页 / 离开页面 | `ingestStore.js` | 378~385 |

传递路径:store 创建 controller → 把 `signal` 塞进请求参数
(`rag.js:53`、`rag.js:74`、`rag.js:295`)→ 想停就 `abort()`。

### 5.3 五个「不这么做就出 bug」的细节

**① 取消不是错误,必须单独标记**(`http.js:117`)

```js
export function canceledError() {
  const err = new Error('已取消')
  err.isCanceled = true
  return err
}
```

调用方 `chatStore.js:147` 靠它区分:

```js
if (err?.isCanceled) {
  finalize(messageId, { status: MSG.CANCELED }, controller)   // 已停止
  return
}
```

不区分的话,用户点「停止生成」会看到「回答失败」—— 明明是用户自己按的。

**② 点了停止后,abort 只在**一个**地方处理状态**(`chatStore.js:197~203`)

```js
export function stopStreaming() {
  const controller = stream?.controller
  if (!controller) return
  // 这里**不**改状态:abort 会让 chatStream 抛出 isCanceled,
  // 由 runStream 的 catch 统一收尾。两处都写状态迟早会打架,而且 abort 是异步生效的
  controller.abort()
}
```

> 「abort 是异步生效的」这句是关键。如果你在 `stopStreaming` 里立刻把状态改成「已停止」,
> 而流那边稍后又回写一次,两处状态就会打架。

**③ 旧流的回落不能覆盖新状态**(`chatStore.js:99`)

```js
function finalize(messageId, patchObj, controller) {
  if (stream?.controller !== controller) return     // ← 这一行
  ...
}
```

场景:用户点了「重新开始」,新的流已经起来了,旧流的回调这才姗姗来迟。
不做这个身份校验,旧流会把新会话的状态改坏。

**④ 取消时缓冲区里的半个帧要**故意丢弃**(`rag.js:364`)

```js
if (signal?.aborted) {
  // 中止时缓冲区里那半个没凑齐的帧**故意丢弃**,不 flush:
  // 它最多是最后一个增量(用户已经按了停止,本来就不想要了),
  // 但它也可能是半截 JSON 信封 —— 补进答案里会变成一串花括号,比少一个字难看得多
  throw canceledError()
}
```

**⑤ 关页面时主动掐掉在途请求**(`ingestStore.js:378`)

```js
window.addEventListener('pagehide', () => {
  runners.forEach((runner) => {
    clearTimeout(runner.timerId)
    runner.controller?.abort()
  })
})
```

放在模块里而不是组件里,因为这是「页面」级别的事件,不是「组件」级别的。
大文件上传在页面卸载时如果不掐,会白占带宽。

> 反过来 `chatStore.js:211` 的注释解释了**为什么问答流不做同样的事**:
> 问答流在页面卸载时浏览器自己会断,多一个监听只会在 bfcache(前进/后退)时制造意外。
> **知道什么时候不该用**,比会用更能说明你懂了。

### 5.4 面试问 AbortController 怎么答

> 用在两类地方:问答的「停止生成」和上传/轮询。每一条在途请求都有自己的 controller,
> 信号一路传到 axios 的 config 和 fetch 的 options 里。
> 有三个细节我特意处理了:取消要单独标记成 isCanceled 而不是当错误,
> 否则用户点停止会看到「失败」;收尾函数要校验「这条流还是不是当前那条」,
> 防止点了重新开始之后旧流把新状态覆盖掉;
> 另外页面卸载时主动 abort 在途上传,但问答流不做这件事,因为浏览器会自己断,多一个监听反而在 bfcache 里出问题。

## 6. 「了解 Vite 构建与开发代理」

### 6.1 这句话什么意思

Vite 是新一代前端构建工具,相当于前端界的 Maven。它干两件事:

1. **开发模式**(`npm run dev`):起一个开发服务器,浏览器直接请求源码,
   改了文件立刻生效(热更新),**不打包**;
2. **生产构建**(`npm run build`):把源码打包压缩成 `dist/` 里的静态文件。

「开发代理」解决的是:前端跑在 5173、后端跑在 8080,浏览器跨端口请求会被同源策略拦。

### 6.2 你的配置(`vite.config.js` 全文 25 行)

```js
export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    strictPort: true,                 // 端口被占就直接报错,不要偷偷换端口
    proxy: {
      '/api': {
        target: 'http://127.0.0.1:8080',
        changeOrigin: true,
        timeout: 600000,
        proxyTimeout: 600000,
      },
    },
  },
  build: { outDir: 'dist', sourcemap: true },
})
```

### 6.3 四个值得讲的选择

**① 代理而不是 CORS**

浏览器只看到 `5173` 这一个源,同源策略根本不触发,**后端一行 CORS 配置都不用写**。
这是开发期最省事也最常见的做法。

**② 用 `127.0.0.1` 而不是 `localhost`** —— 这是真踩过坑才写得出来的:

> Windows 上 `localhost` 可能先解析到 `::1`(IPv6),而 Tomcat 只监听 IPv4 时
> 会得到一个非常难查的 `ECONNREFUSED`。

**③ 不 rewrite**

```js
// 不 rewrite:Java 侧暴露的就是 /api/rag/*,原样转发即可
```

后端路径和前端请求路径是一致的,所以不需要 `rewrite` 去掉前缀。
(如果后端 API 没有 `/api` 前缀,这里就要写 `rewrite: p => p.replace(/^\/api/, '')`。)

**④ `strictPort: true`**

端口被占用时**直接失败**,而不是悄悄换成 5174。
理由写在注释里:「否则你记的地址会失效」。对开发期来说,
「启动就报错」比「启动成功但地址变了」好排查得多。

### 6.4 两个必须知道的边界

**① 生产环境没有代理了**(`frontend/README.md` 里写了)

`npm run build` 出来的 `dist/` 是纯静态文件。部署时:
- 要么 nginx 把 `/api` 反代到 8080;
- 要么前后端同域;
- **分域部署就必须在 Java 侧加 CORS 配置**。

> 这一条面试官很爱问「你开发环境怎么解决跨域,生产呢?」——
> 能答出「开发用 Vite 代理,生产靠 nginx 反代或同域,分域才需要 CORS」就完整了。

**② `index.html` 是 Vite 的入口**(`index.html:9`)

```html
<div id="root"></div>
<script type="module" src="/src/main.jsx"></script>
```

Vite 认 `index.html` 作为入口(不像传统打包工具从 JS 入口开始),
`id="root"` 那个 div 就是 `main.jsx:9` 里 `createRoot(document.getElementById('root'))` 挂载的地方。

### 6.5 面试问 Vite 怎么答

> 开发期用 dev server 的 proxy 把 `/api` 转发到 8080,这样浏览器视角是同源的,
> 后端不需要配 CORS。有两个细节:target 我写的是 127.0.0.1 而不是 localhost,
> 因为 Windows 上 localhost 可能先解析到 IPv6 的 ::1,而 Tomcat 只监听 IPv4,
> 会得到一个很难查的 ECONNREFUSED;另外我开了 strictPort,端口被占直接失败,
> 不偷偷换端口。生产构建输出 dist 静态文件,那时代理没有了,要么 nginx 反代要么同域部署。
