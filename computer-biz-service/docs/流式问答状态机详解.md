# 流式问答状态机详解

> 对应简历亮点②：**实现流式问答的完整生命周期管理（生成中/完成/取消/中断/失败）：用户可实时看到每条回答的状态并随时停止，服务端能区分「用户主动取消」「生成到一半中断」「一开始就失败」三种情况；对每条回答的最终状态做了防重与防丢处理，后台写库不影响问答响应速度。**
>
> 本文是**学习文档**：把这条亮点拆到每一行代码，让你能答住追问。
> 姊妹篇：`docs/流式问答链路详解.md`（讲「字节怎么变成文字」），本文讲「一次生成怎么被判定成败」。
>
> ⚠️ **命名说明**：代码里、库里、本文里都叫「五态状态机」，但严格说它是**五态状态模型**——
> 迁移只有一层（`STREAMING → 五选一`），真正的难点在**判定**，不在迁移。面试被问「状态图长什么样」时，
> 照实说，然后把话题引到判定上（见 §8 Q2）。

## 0. 先记住这一条链

```
用户点「发送」
    │
    ├─ 前端：立刻建一条 status=streaming 的助手气泡（文字为空）
    │        └─ 用户即时看到「正在生成」    chatStore.js:174-182
    │
    ├─ Java：beginExchange 落一行 assistant(STREAMING)，拿到 id
    │        └─ 失败 → 整条落库旁路跳过，问答照常   RagService.java:98-107
    │
    └─ 流开始：每段增量  →  前端 appendDelta / Java doOnNext 攒正文
              │
              └─ 流结束（四种方式之一）
                       │
                 doFinally(signal) + 收到过内容没有 + 是不是客户端断开
                       │
                    五选一  ──┬─→ 落库（甩到弹性线程池）
                              └─→ 前端渲染状态
```

**30 秒面试版**：

> 流式问答有个绕不开的约束：响应头必须在**第一个 token 之前**就发出去（否则浏览器不会开始渲染），所以等失败真的发生时，状态码早就锁死成 200 了——**「失败」这件事没法用 HTTP 状态码表达**。我把终态放进数据库那一行：用 Reactor 的 `doFinally` 统一收口，结合「是正常完成 / 取消 / 异常」和「有没有收到过内容」两个维度，把一次生成归纳成五种状态。三个难点：① 用户点停止和上游断连，在 Java 侧**都表现为「流没正常结束」**，要能把它们分开；② `doFinally` 在边缘情况下可能触发多次，终态只能写一次；③ 终态落库是**阻塞的 JDBC**，而 `doFinally` 跑在 reactor-netty 的**事件循环**上，必须甩到弹性线程池去，否则会卡住所有并发请求共用的 IO 线程。

## 2. 问题的根源：为什么状态不能靠 HTTP 状态码

### 2.1 响应头一旦发出去，状态码就锁死了

普通请求是「算完再回」——服务端先把结果准备好，再决定状态码。**流式请求反过来**：

```
普通请求：  收到请求 → 处理 20 秒 → 写响应头(200/500) + 写 body → 结束
流式请求：  收到请求 → 写响应头(200) ──────────────→ 边生成边写 body → 结束
                        ↑
                   必须立刻写，否则浏览器不会开始渲染
```

**状态码是在第一个 token 之前就发出去的**。那一刻一切都还正常（谁能预料 20 秒后上游会挂？）。

失败发生在第 20 秒——**但那个 200 是改不了的**。HTTP 不允许"先回 200，再改口说 500"。

### 2.2 所以「失败」只能由流自己表达

这就是 `docs/流式问答链路详解.md` §4.5 讲的 `stray` 的来源：

> 上游失败时 Java 侧的响应已经提交成 200，状态码改不了了，Spring 只能把错误 JSON **直接写进流里**。前端从"悬空行"里把它捞出来，翻译成人话。

**但这只解决了一半。** "把错误写进流里"能表达的是：

```
✅ 失败（有错误信息）
✅ 成功（有正文）
❓ 用户点了停止 —— 流直接断了，谁来写？
❓ 生成到一半上游挂了 —— 跟"失败"有什么区别？
```

**流本身承载不了这五种状态。** 所以必须有第二个载体。

### 2.3 第二个载体：数据库那一行

```
chat_message 表，一次问答两行
   ├─ user 行      status=DONE          ← 提问本身没有流，写进去就是终态
   └─ assistant 行 status=STREAMING     ← 建行时的初值，此时 content 还是 null
                    ↓ 流结束时 UPDATE 一次
                    status=DONE / CANCELED / INTERRUPTED / ERROR
```

**`chat_message.status` 是五态唯一能被完整记录的地方**——HTTP 状态码只有"成功/失败"两态，而且流一开始就锁死了。

### 2.4 ⚠️ 最容易答错的一句：「那你就早点返回 500 不就行了」

**不行。因为在你"决定返回状态码"的那个时刻，你根本还不知道会不会失败。**

上游是**流式**的，答案分几十秒才吐完；第一秒返回 200 的时候，一切正常。失败发生在第 20 秒。

> **这不是设计缺陷，是流式的本质代价**：你为了"边生成边给用户看"，就必须在"知道结果"之前先承诺一个状态码。

同理，也不能"等流结束了再返回"——那就退化成非流式了，用户要盯着空白等 20 秒。

## 3. 五态是怎么定义的

### 3.1 五个值

`ChatMsgStatus.java:15-45`：

| 值 | 含义 | 什么时候是它 |
|---|---|---|
| `STREAMING` | 正在逐段生成 | assistant 行**建出来时的初值**，此时 content 还是空 |
| `DONE` | 正常结束 | 流走完 `onComplete` |
| `CANCELED` | 用户点了「停止生成」 | ★ **不是故障**——浏览器 abort 掉 fetch，连接断开，流被取消 |
| `INTERRUPTED` | 收到一部分，但流没正常结束 | 上游报错 / 连接被掐 |
| `ERROR` | 一个字都没收到就失败了 | 上游压根没起来 |

`INTERRUPTED` 和 `ERROR` 的唯一区别就是**有没有收到过东西**。这个区分很实用：**半截答案往往仍然有用**，把已经拿到的内容扔掉，用户只会重新问一遍。

### 3.2 三处逐条对应，不要造第六个

| Java（`ChatMsgStatus`） | 数据库（`chat_message.status`） | 前端（`chatStore.MSG`） |
|---|---|---|
| `STREAMING` | 大写字符串 | `'streaming'` |
| `DONE` | 同上 | `'done'` |
| `CANCELED` | 同上 | `'canceled'` |
| `INTERRUPTED` | 同上 | `'interrupted'` |
| `ERROR` | 同上 | `'error'` |

- **大小写不同是刻意的**：库里大写（SQL 习惯），前端小写（JS 习惯）。
- **`ChatMsgStatus` 的类注释写了一句话**：「**不要自己造第六个**——前端的状态机是这套语义的另一半，多加一个值它就渲染不出来。」
- 落库时靠 `@EnumValue` 把 `code` 写进去（这个注解**确实生效**过：前端小写、库里大写，若失效会写成枚举名，是最灵敏的探针）。

### 3.3 诚实一点：这是「状态模型」不是「状态机」

严格意义上的状态机要有**状态迁移图**。这里的迁移图是：

```
STREAMING ──→ DONE
          ──→ CANCELED
          ──→ INTERRUPTED
          ──→ ERROR
```

**就一层，而且终态不可逆。** 所以：

- 面试被问「你的状态图长什么样」→ 照实说"迁移很简单，就一层"，
- **然后把话题引到真正难的地方**：「难点不在迁移，在**判定**——怎么从一个统一的'流没正常结束'里，反推出到底是取消、中断还是失败。」

## 4. Java 侧：终态是怎么判出来的

### 4.1 三个副作用算子

`RagService.java:112-132`：

```java
return Flux.defer(() -> {
    StringBuilder answer = new StringBuilder(2048);
    AtomicReference<Throwable> failure = new AtomicReference<>();
    AtomicBoolean settled = new AtomicBoolean(false);
    return ragClient.aiChat(req)
            .doOnNext(piece -> answer.append(piece))   // ③ 攒正文
            .doOnError(failure::set)                   // ④ 只记录不消费
            .doFinally(signal -> {                     // ⑤ 统一收口
                if (settled.compareAndSet(false, true)) {
                    settleAsync(id, answer, signal, failure.get());
                }
            });
});
```

| 算子 | 干什么 | 为什么是它 |
|---|---|---|
| `doOnNext` | 把每段增量追加到 `StringBuilder` | 纯内存拼接，O(1) 摊还，**不做任何 IO**，所以留在事件循环上没关系 |
| `doOnError` | 把异常**存起来** | **只记录，不消费**——见下 |
| `doFinally` | 所有结束路径的统一出口 | 见 4.2 |

**为什么 `doOnError` 只是 `failure::set`，而不是 `onErrorResume`？**

`RagService.java:91-92` 写了理由：

> **不消费错误**：`onErrorResume`/`onErrorReturn` 会**改掉前端看到的东西**，前端那套「从悬空行里捞 detail」的逻辑就失效了。

也就是说：错误必须**原样流到前端**（前端靠它渲染"生成中断"），Java 只是**顺手抄一份存进数据库**——`doOnError` 是透明的，`onErrorResume` 不是。**这和 `doOnNext` 攒正文是同一个"分光镜（tee）"手法。**

### 4.2 ★ `doFinally` 而不是 `doOnTerminate`——这是最容易答错的一处

`doFinally` 和 `doOnTerminate` 长得很像，**但行为完全不同**：

| | `onComplete` | `onError` | **`cancel`** |
|---|---|---|---|
| `doOnTerminate` | ✅ 触发 | ✅ 触发 | ❌ **不触发** |
| `doFinally` | ✅ | ✅ | ✅ **触发** |

**如果用 `doOnTerminate`，用户点「停止生成」时终态永远不会落库**——那条 assistant 行会永远是 `STREAMING`，在库里看起来像"卡住了"。

> **面试答题点**：`doOnTerminate` 只认「正常终止」两个信号，`doFinally` 认**所有**终止信号，包括**取消**。这里必须用后者，因为「取消」恰好是我们最关心的一态之一。

### 4.3 `classify()`：两个维度推出五种

`RagService.java:187-195`：

```java
private static ChatMsgStatus classify(SignalType signal, int textLength, Throwable failure) {
    if (signal == SignalType.ON_COMPLETE) {
        return ChatMsgStatus.DONE;                       // 正常走完
    }
    if (signal == SignalType.CANCEL || isClientAbort(failure)) {
        return ChatMsgStatus.CANCELED;                   // 取消（两种形态）
    }
    return textLength == 0 ? ChatMsgStatus.ERROR         // 一个字没收到
                           : ChatMsgStatus.INTERRUPTED;  // 收到一半被打断
}
```

两个输入维度：

```
① 流的结束方式  signal        →  ON_COMPLETE / ON_ERROR / CANCEL
② 收到过内容没有 textLength   →  0 / >0
```

组合起来：

```
ON_COMPLETE                          → DONE
CANCEL                               → CANCELED
ON_ERROR 且 异常是"客户端断开"         → CANCELED
ON_ERROR 且 textLength == 0          → ERROR
ON_ERROR 且 textLength > 0           → INTERRUPTED
```

**这个判断只能放在这里**——因为只有它同时知道「收到过内容没有」和「是怎么结束的」（类注释原话）。别的层拿不到这两个信息。

> ★ 常量名是 `CANCEL` **不是** `ON_CANCEL`：Reactor 3.8 把后者去掉了（老版本的 `SignalType` 里叫 `ON_CANCEL`，**抄老例子会编译不过**）。

### 4.4 ★ 最难的一档：怎么区分「用户取消」和「上游断连」

这是整条链路上最微妙的地方。

**问题**：两种完全不同的情况，在 Java 侧**长得几乎一样**：

| 情况 | 发生了什么 | Java 侧看到的 |
|---|---|---|
| 用户点「停止生成」 | 浏览器 abort fetch → 连接断开 | 往这个已断的连接写 SSE 会失败 |
| 上游 FastAPI 挂了 | WebClient 读流失败 | 读流失败 |

**两者都表现为「流没正常结束」，而且都常常以 `IOException` 的形态冒出来。** 如果一律当成"取消"，就会把"上游挂了"记成"用户主动停"——**用户明明没停，状态却显示已取消**，这是错误的状态，而且会误导排查方向。

**解法**（`RagService.java:204-214`）：**只认类名里含 `ClientAbort` 的异常**。

```java
private static boolean isClientAbort(Throwable failure) {
    for (Throwable t = failure; t != null; t = t.getCause()) {
        if (t.getClass().getName().contains("ClientAbort")) {
            return true;   // Tomcat 的 ClientAbortException
        }
        if (t == t.getCause()) break;  // 自环，防呆
    }
    return false;
}
```

注释里特意强调：

> **不能**把 `IOException` 一律当成断开——上游挂掉时读失败同样是 `IOException`，那种情况应该是 `INTERRUPTED`（收到一半被打断），不是 `CANCELED`（用户主动停）。

几个细节：
- **沿 `getCause()` 链遍历**：Tomcat 往往把 `ClientAbortException` 包在别的异常里。
- **用类名而不是 `instanceof`**：`ClientAbortException` 在 `tomcat-embed-core` 里，`RagService` 引它会把 Tomcat 变成编译期硬依赖。**用类名字符串匹配是一种刻意的解耦**（代价是拼错不会编译报错）。
- **自环防呆**：`t == t.getCause()` 时跳出，防止异常链成环导致死循环。

> ⚠️ **一条待验证的事**（代码注释里也标了）：客户端断开到底以哪种形态到达——是干净的 `CANCEL`，还是带着 `ClientAbortException` 的 `ON_ERROR`？**本地没有实测过**，两种都处理了。
> **验证方法**：前端点一次「停止生成」，然后看 `settleAsync` 打的那行日志里的 `signal` 和异常类名。如果落成了 `INTERRUPTED`，就照着日志里那个类名把判断补准。

### 4.5 闸门：为什么终态只落一次需要 `AtomicBoolean`

`RagService.java:125-131`：

```java
.doFinally(signal -> {
    // doFinally 在边缘情况下可能不止触发一次（完成与取消都到），
    // 所以宁可加一个闸门，也不要写两次终态
    if (settled.compareAndSet(false, true)) {
        settleAsync(id, answer, signal, failure.get());
    }
})
```

- **为什么可能触发多次**：Reactor 文档对 `doFinally` 的语义是「在信号之后**或**取消之后」。某些信号组合下（比如 `onComplete` 和下游 `cancel` 都到）它会被调用不止一次。
- **为什么用 CAS（`compareAndSet`）而不是 `if (!settled) settled = true`**：后者在两次调用**并发**时两个线程都会通过检查。CAS 是原子的，只有一个能把它从 `false` 翻到 `true`。
- **实际会并发吗？** 大概率不会（`doFinally` 通常只在一条线程上回调）。但注释说得对——**这是一个代价极低、却能彻底消灭一类 bug 的防御**。用一行 CAS 换掉「终态可能写两次」这种极难复现的问题，划算。

> **注意和 `ingest_task` 的对照**：那边是**两个页签会并发轮询同一个 job**，所以必须靠 SQL 的 `WHERE status='INGESTING'` 兜住；这边是**一次问答只有一条流**，竞态在内存里就挡住了，**所以 `settle` 不做条件更新**（见 §6.3）。两处的差异是刻意的。

### 4.6 落库为什么必须换线程

`settleAsync()` `RagService.java:147-162`：

```java
Schedulers.boundedElastic().schedule(() -> {
    try {
        chatRecordService.settle(assistantId, answer.toString(), status, detailOf(failure, status));
    } catch (Exception e) {
        log.error("落库失败（回答已正常返回用户，数据不会进库）: assistantId={} status={}", assistantId, status, e);
    }
});
```

**理由一：`doFinally` 跑在 reactor-netty 的事件循环上。**

那是**所有请求共用**的 IO 线程：

```
reactor-netty 事件循环（少数几条线程，服务所有连接）
    ├─ 投递上游 chunk
    ├─ Spring 写 SSE
    └─ doFinally 回调  ← 你在这里做阻塞的 JDBC
                            ↓
                    这几条线程被卡住 = 所有并发请求一起变慢
```

> **症状：平时都好好的，一并发就整体变慢**——最难查的那类问题。单请求压测永远复现不出来。

**理由二：`answer.toString()` 在事件循环上拷 10 万字是没理由的开销。**

所以注意一个细节：`answer.toString()` 是写在 **lambda 里面**的（在弹性线程上执行），不是写在外层——**拷贝也一起甩出去了**。

**理由三：落库失败不能影响用户。** 整个过程 try/catch 包住，失败只记一行日志（注释原话："一个抛异常的终态回调会把**已经成功返回给用户的回答**变成报错"）。

### 4.7 ★ 为什么不干脆 `publishOn(boundedElastic)` 把整条流切走？

这是另一个常见误区。看起来"落库是阻塞 IO，那我把整条流切到弹性线程池不就行了"——**不行**。`RagService.java:87-90` 写了两个理由：

1. **`publishOn` 会在上游和 Spring 的写入器之间插一次调度跳转**——纯粹的额外开销。
2. **更要命**：`publishOn(boundedElastic)` 会为**整个回答**（可能几分钟）**长期占住一个弹性线程**。弹性线程池的线程是有限的——**那是线程池饥饿，不是修法。**

> **要换线程的是「落库那一件事」，不是流本身。**

**流本身根本不需要换线程**：它做的只是「收字节 → 解码 → 转发」，全是非阻塞的。真正阻塞的只有那一句 JDBC。

**面试答题点**：能说出"`publishOn` 会长期占住弹性线程"这层，说明你不是照搬教程，而是真的想过线程模型。

### 4.8 为什么提问要在订阅之前、请求线程上同步写

`RagService.java:96-107`：`beginExchange` 是在 `aiChat()` 的**方法体里**同步调的（**不在** `Flux.defer()` 里面）：

```java
Long assistantId = null;
try {
    assistantId = chatRecordService.beginExchange(req, AppConstants.DEFAULT_USER_ID);
} catch (Exception e) {
    log.error("落库失败（问答照常进行，数据不会进库）: ...", e);
}
if (assistantId == null) {
    return ragClient.aiChat(req);   // 落库失败 → 整条旁路跳过，问答照常
}
```

两个理由：

1. **那时响应还没开始，写库失败还能被抓住记日志**；而且**上游挂掉的那次提问也留下了痕迹**（后面虽然返回 ERROR，但"用户问了什么"这行已经在库里了）。
2. **放进 `Flux.defer()` 里写的话，落库就成了流的一部分——DB 一抖会把用户的回答带崩。**

> 注意 `Flux.defer()` 里放的是**累加器和闸门**（按每次订阅新建），不是落库。这个分工是刻意的。

## 5. 前端侧：同一套语义的另一半

前端状态由**四个出口**推出来（`chatStore.js:124-153`）：

```js
async function runStream(messageId, message, controller) {
  try {
    const { errorDetail } = await chatStream(...)

    if (errorDetail) {                                    // 出口 ①
      fail(messageId, controller, errorDetail)            //   → INTERRUPTED / ERROR
      return
    }
    finalize(messageId, { status: MSG.DONE, error: '' }, controller)   // 出口 ② → DONE
  } catch (err) {
    if (err?.isCanceled) {                                // 出口 ③
      finalize(messageId, { status: MSG.CANCELED }, controller)        //   → CANCELED
      return
    }
    fail(messageId, controller, err?.message || 'AI 问答失败')          // 出口 ④ → INTERRUPTED / ERROR
  }
}
```

### 5.1 为什么助手气泡要先建出来

`chatStore.js:174-182`：

```js
const aiMsg = {
  id: nextId(), role: 'assistant', text: '',
  status: MSG.STREAMING,          // ← 初值就是 STREAMING
  error: '', createdAt: now,
}
```

注释：「**助手消息先建出来再开流**——增量是往这条消息上追加的，不能等流结束才建（**否则用户会盯着一个没反应的界面**）。」

**这和 Java 侧 `beginExchange` 里"assistant 行以 STREAMING 落库"是同一个决定**：

```
前端：先建一条空消息  →  用户立刻看到「正在生成」
Java：先落一行空记录  →  库里立刻有一条可追踪的痕迹
```

**两侧都选择"先占位，后填充"**，因为流的本质就是"结果还没出来"。

### 5.2 ★ `stopStreaming` 为什么故意不改状态

`chatStore.js:197-203`：

```js
export function stopStreaming() {
  const controller = stream?.controller
  if (!controller) return
  // 这里**不**改状态：abort 会让 chatStream 抛出 isCanceled，由 runStream 的
  // catch 统一收尾。两处都写状态迟早会打架，而且 abort 是异步生效的
  controller.abort()
}
```

两个理由写得很清楚：

1. **两处都写状态迟早会打架**——`abort()` 是**异步**的，你在 `stopStreaming` 里立刻标 `CANCELED`，而流可能还会推来一两个增量（已经在路上的），它会把状态又改回 `STREAMING`。
2. **收尾只能有一个出口**——所有终态都由 `runStream` 的 `catch`/正常返回统一决定。

> **面试答题点**：这是"**状态只能由一个地方写**"的经典应用。用户点停止时 **只发信号（`abort`），不直接改状态**——信号会被翻译成异常，再由唯一的收尾处决定状态。**这跟 Java 侧"终态只由 `settleAsync` 写"是同一条原则。**

### 5.3 `finalize` 的 controller 校验：防旧流覆盖新状态

`chatStore.js:99-108`：

```js
function finalize(messageId, patchObj, controller) {
  if (stream?.controller !== controller) return   // ← 关键的一行
  stream = null
  ...
}
```

场景：用户点了「重新开始」（`resetConversation`），它内部先 `stopStreaming()` 掐掉旧流，再清空消息列表。

**旧流的 `abort` 是异步生效的**——它的 `catch` 可能在**清空之后**才跑。如果没有这一行校验，旧流的回落会把 `CANCELED` 写回到**已经不存在（或已属于新会话）的**消息上。

> **一句话**：**旧流可以死，但不能反过来影响新状态。** 靠"当前在途的 controller 是不是我"来判断。

### 5.4 `fail()`：有内容就是「中断」，没内容才是「失败」

`chatStore.js:115-122`：

```js
function fail(messageId, controller, detail) {
  const msg = snapshot.messages.find((m) => m.id === messageId)
  finalize(messageId, {
    status: msg?.text ? MSG.INTERRUPTED : MSG.ERROR,   // ← 只看有没有正文
    error: detail,
  }, controller)
}
```

**和 Java 侧 `classify` 里 `textLength == 0 ? ERROR : INTERRUPTED` 是完全同一个判断**——两侧独立实现，但语义逐字对齐。

理由（注释原话）：

> **失败，但不丢已经收到的内容**：有正文就是「回答中断」（那半截答案往往仍然有用），一个字都没有才算「失败」。和 `ingestStore` 里「轮询失败 ≠ 入库失败」是**同一条原则**——把已经拿到的信息扔掉，用户只会重新问一遍。

## 6. 落库：终态在库里长什么样

### 6.1 一轮问答两行，在同一时刻建出来

`ChatRecordService.beginExchange()` `:110-145`，一个事务里做三件事：

```
① 按 session_id 查 chat_session，没有就插一行（title = 提问的前 N 个字）
② 插 user 行：      role=USER,      content=提问原文, status=DONE      ← 提问没有流，写进去就是终态
③ 插 assistant 行： role=ASSISTANT, content=null,   status=STREAMING  ← 占位，content 还没生成
   并返回它的 id（终态时 settle 靠它定位）
```

两个细节：

- ★ **两行共用一个 `now`**（`:121` 只取一次 `LocalDateTime.now()`）：前端的语义里这两条消息是「同一条消息对」（**共享 `createdAt`**），差几毫秒就破坏了它。所以**一轮内的先后只能靠 id 排，不能靠时间**。
- **为什么要事务**：只有 user 行、没有 assistant 行，读起来像「**模型无视了这个问题**」，是假象。**两行必须都在或都不在。**

### 6.2 `settle()`：一条 UPDATE 只写五列

`ChatRecordService.java:154-174`：

```java
ChatMessage patch = new ChatMessage();
patch.setId(assistantId);
patch.setContent(text);
patch.setCharCount(text.length());   // 一眼看出哪些回答是半截的
patch.setStatus(status);
patch.setError(error == null ? "" : error);
patch.setFinishedAt(LocalDateTime.now());
// 其余字段留 null → 不进 SET 子句，所以 topK / created_at / session_id 都不会被动
updateById(patch);
```

**用 `updateById(补丁对象)` 而不是 `lambdaUpdate().set(...)`**：补丁里为 null 的字段**不会**进 SET 子句，所以不会碰到这个方法没打算改的列。

> ⚠️ 这两者的语义**正好相反**，`ingest_task` 那边用的是 `lambdaUpdate().set(...)`（**显式**，连 null 一起写）。**别搞混**——详见 `docs/落库改动清单.md`。

**★ `error` 必须是空串而不是 `null`**：

> MyBatis-Plus 默认不把 null 字段写进 UPDATE，**写 null 等于「这列不动」**——上一次残留的报错会永远挂在这行上。清空只能靠空串。

**★ 取消时 `content` 里有半截回答——这是这个设计最重要的产物**（类注释原话）：

> 用户点「停止生成」之后，**前端刷新就丢的东西**，只有这里留得住。

### 6.3 ★ 为什么这里不做「只能改 STREAMING 行」的条件更新

`ChatRecordService.java:75-77` 有一段对照说明：

| | `ingest_task` | `chat_message` |
|---|---|---|
| 并发场景 | **两个页签会并发轮询同一个 job** | 一次问答只有**一条**流 |
| 防竞态手段 | SQL `WHERE status='INGESTING'`（**数据库**兜底） | `AtomicBoolean`（**内存**兜底） |
| `settle` 要不要条件更新 | 要 | **不要** |

**因为 `RagService` 的闸门已经保证了终态只落一次，这里没有竞态要防。** 多一个 `WHERE` 只是无谓的负担。

> **面试答题点**：被问「你们不用乐观锁吗」，答案是「**这里是刻意不用的**，因为竞态在上一层就被 `AtomicBoolean` 挡掉了；而另一张表 `ingest_task` 有真实的并发轮询，那边就上了条件更新。」——**能说出"哪里用了、哪里刻意没用、为什么"，比无脑全加上要值钱。**

### 6.4 怎么自己验

`ChatRecordService.java:84-93` 给了现成的 SQL：

```sql
SELECT id, session_id, role, status, CHAR_LENGTH(content) len, char_count,
       LEFT(content,30) head, error, top_k, created_at, finished_at
FROM chat_message ORDER BY id DESC LIMIT 10;
```

预期：

- 一问一答两行、`created_at` 相同
- 正常答完 → assistant 行是 `DONE` 且有正文
- 中途点「停止生成」→ `CANCELED` + 半截正文 + `error` 为空串
- 把 FastAPI 停掉再问 → `ERROR` 且正文为空
- 答到一半把 FastAPI 停掉 → `INTERRUPTED` + 有正文

**另外这条应该是空的**（有货就说明有流卡住了）：

```sql
SELECT * FROM chat_message WHERE status='STREAMING' AND finished_at IS NULL;
```

## 7. 五态 × 触发条件 总表

| 状态 | 触发条件 | `content` | `error` | 用户看到 | 谁判的 |
|---|---|---|---|---|---|
| `STREAMING` | 建行/建气泡时的初值 | `null`（库里） | `null` | 「正在生成…」 | `beginExchange` |
| `DONE` | `ON_COMPLETE` | 全文 | **空串** | 正常回答 | `classify` :188-190 |
| `CANCELED` | `CANCEL`，或 `ON_ERROR` + `ClientAbort` | 半截（可能为空） | **空串** | 「已停止」 | `classify` :191-193 |
| `INTERRUPTED` | `ON_ERROR` + 有内容 | 半截 | 原因 | 「回答中断」+ 原因 | `classify` :194 |
| `ERROR` | `ON_ERROR` + 一个字都没收到 | 空串 | 原因 | 「失败」+ 原因 | `classify` :194 |

**注意 `DONE` 和 `CANCELED` 的 `error` 是空串不是 `null`**——`detailOf()`（`:222-232`）专门处理了这个：写 `null` 会清不掉上一次残留的报错。

## 8. 面试追问清单

### Q1 为什么不直接用 HTTP 状态码表示失败？

> 流式响应必须在第一个 token 之前就把响应头发出去（否则浏览器不会开始渲染），**那一刻状态码就锁死成 200 了**。失败发生在 20 秒后，改不了。
> 所以我把两件事分开：**"给用户看的错误"写进流里**（前端从悬空行里捞），**"可追溯的终态"落进数据库那一行**——HTTP 只有两态，五态只能放数据库。

### Q2 五态里哪两个最难分？你怎么分的？

> **`CANCELED` 和 `INTERRUPTED`**。用户点停止会让浏览器 abort 连接，上游挂掉会让读流失败——**两者在 Java 侧都表现为"流没正常结束"，而且都常常是 `IOException`**。
> 我**只认类名里含 `ClientAbort` 的异常**（Tomcat 的 `ClientAbortException`），并且沿 `getCause()` 链找。**不能把 `IOException` 一律当断开**——那样上游挂了会被误记成"用户主动停"，是错误的状态。

### Q3 为什么要 `AtomicBoolean` 闸门？（"你们不是只有一条流吗"）

> 因为 `doFinally` **在边缘情况下可能不止触发一次**（完成与取消都到）。用 CAS 而不是 `if(!settled) settled=true`，是因为后者两次调用**并发**时都会通过。这是一行成本、彻底消灭一类难复现 bug 的防御。

### Q4 为什么不用 `publishOn` 把整条流切到弹性线程池？

> 两点：① 它会在上游和 Spring 的写入器之间插一次调度跳转；② 更要命的是，`publishOn(boundedElastic)` 会为**整个回答**（可能几分钟）**长期占住一个弹性线程**——那是**线程池饥饿**，不是修法。
> **要换线程的是"落库那一件事"，不是流本身。** 流做的只是收字节、解码、转发，全是非阻塞的。

### Q5 `doFinally` 和 `doOnTerminate` 什么区别？

> `doOnTerminate` 只在 `onComplete`/`onError` 触发，**取消时不触发**；`doFinally` 在**所有**终止信号后触发，包括 `cancel`。
> **用错的话，用户点「停止生成」终态永远不落库**——那行会永远是 `STREAMING`。

### Q6 为什么不 `onErrorResume` 掉异常？

> 那会**改掉前端看到的东西**——前端是靠流里的错误信息渲染"生成中断"的，被吞掉它就只看到"流突然没了"。而且这跟 `doOnNext` 是一个手法：**分光镜（tee），抄一份但不改流**。

### Q7 为什么 `chat_message` 的终态更新不做条件更新？你们不是最讲并发吗？

> 因为那边（`ingest_task`）**两个页签会并发轮询同一个 job**，必须靠 `WHERE status='INGESTING'` 兜住；这边**一次问答只有一条流**，而且 `AtomicBoolean` 已经在内存里挡住了重复落库，**没有竞态要防**。
> **差别是刻意的，不是遗漏。**

### Q8 用户点了「停止生成」，那半截回答去哪了？

> **落库了**。前端会把它渲染成"已停止"并保留半截正文，Java 侧 `settle` 把那半截 `content` 和 `CANCELED` 一起写进 `chat_message`。
> **这是这个设计最重要的产物**——前端刷新页面就丢的东西（`session_id` 甚至是刷新即换新），只有库里留得住。

### Q9 前端点停止时为什么不当场把状态改成 CANCELED？

> 因为 `abort()` 是**异步**生效的——当场改状态，可能马上被还在路上的增量改回 `STREAMING`。而且**两处写状态迟早会打架**。
> 所以点停止**只发信号**，由唯一的收尾处（`runStream` 的 `catch`）决定状态。**和 Java 侧"终态只由 `settleAsync` 写"是同一条原则。**
