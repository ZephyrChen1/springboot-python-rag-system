```
(声明SSE但不分帧)         (按字节读，绕开SSE解析)        (按 data: 切帧，兼容裸行)

                      UTF-8 汉字被块边界切开          Spring 不转义换行
```

**30 秒面试版**：

> 上游 RAG 服务的响应头声明 `text/event-stream`，但实际输出的是没有 `data:` 分帧的裸文本。Spring 看到这个 Content-Type 会选用 SSE 解析器，按规范把不带 `data:` 前缀的行当未知字段丢掉，结果解析出 0 个事件——接口返回 200、流是空的、回答静默消失。因为编解码器是**按响应头的 Content-Type** 选的，改请求头 `Accept` 没用，所以我在 WebClient 层绕开 SSE 解析器，自己用 `DataBuffer` 读原始字节，并处理了跨块被切开的 UTF-8 汉字；前端再用 `fetch` + `ReadableStream` 手写增量分帧。

## 2. 问题是怎么产生的（根因链）

### 2.1 SSE 规范要求什么

SSE（Server-Sent Events）的响应体长这样，**每条消息的每一行都要带 `data:` 前缀，消息之间用空行分隔**：

```
data:第一行
data:第二行

data:下一个事件
```

`\n` 这种裸换行必须转义成多条 `data:`（上面第一行和第二行是同一条消息）。

### 2.2 Python 侧为什么吐出裸文本

`rag_api/routers/ai_chat.py`：

```python
return StreamingResponse(gen, media_type="text/event-stream")
```

关键点：**`media_type` 只是写了一行响应头，它不会给内容加分帧。** `gen` 来自
`lightrag_service.py` 的 `stream()`，里面是通过 `queue.Queue` 逐块 `yield` 出来的**纯字符串**。
Starlette 拿到字符串就按 UTF-8 编码成字节直接写进响应体——于是：

- 响应头：`Content-Type: text/event-stream` ✅
- 响应体：`你好！很高兴为你提供帮助……`（纯文本，一个 `data:` 都没有）❌

**这就是"声明 SSE 却不分帧"的来源。** 注意：这是你自己这套系统里的服务，不是第三方——面试被问"上游是谁"，直接说"我系统里的 Python RAG 服务"。

### 2.3 Spring 为什么把回答吃掉了

`RagClient.java:97-103` 的注释写得很清楚，机制是：

1. Spring 的 `WebClient` 在读取响应体时，会**根据响应头的 `Content-Type` 挑选 `HttpMessageReader`**；
2. 看到 `text/event-stream`，它选的是 `ServerSentEventHttpMessageReader`；
3. 这个 reader 严格按 SSE 规范解析：**只认 `data:` / `event:` / `id:` / `retry:` / `:` 开头的行**，其余行按「未知字段」**直接丢弃**；
4. 于是整个响应解析出 **0 个事件** → `Flux` 空 → 接口返回 200、流里什么都没有 → 前端白等。

**症状**：不报错、不 500、前端转圈到超时，什么提示都没有。这就是"回答静默消失"。

### 2.4 ⚠️ 最容易答错的一句：为什么改 Accept 没用

`RagClient.java:105-106` 专门写了这一点：

> 编解码器的选择是**按响应头的 Content-Type** 定的，请求头 `Accept` 改不了它。

也就是说：`RagClient.java:79` 那一行 `.accept(MediaType.TEXT_EVENT_STREAM)` 是**请求方**声明我想要 SSE，
但 Spring 选解析器看的是**响应里回来的那个 `Content-Type`**——那还是 `text/event-stream`。
所以**无论如何都绕不开 SSE 解析器，只能从字节层绕**。这是必须记住的因果，面试问"那你为什么不去掉 Accept 头"就靠这句答。

## 3. Java 侧：字节流解码器

### 3.1 为什么用 `exchangeToFlux` 而不是 `retrieve()`

```java
// RagClient.java:81-91
.exchangeToFlux(response -> {
    if (response.statusCode().isError()) {
        return response.bodyToMono(String.class)
                .defaultIfEmpty("")
                .flatMapMany(body -> Flux.error(RagApiException.fromUpstream(
                        response.statusCode().value(), body, objectMapper)));
    }
    return decodeRawText(response.bodyToFlux(DataBuffer.class));
});
```

`retrieve()` 是"直接拿结果"的便捷 API，它**拿不到同一个响应对象的上下文**。流式响应需要
「在同一个 response 上先看状态码，再决定是读错误体还是读正文」——所以必须用 `exchangeToFlux`。

**另一个知识点**：为什么 `ragWebClient` 这个 Bean 上**故意没有** `defaultStatusHandler`？
`RagClientConfig.java:37-41` 解释了：`defaultStatusHandler` 只在「响应头刚到、body 还没读」时抛异常，
对流式响应**会把连接直接掐掉**；而且它在 `exchangeToFlux` 里拿不到上下文。
所以 SSE 这条路的错误映射写在 `exchangeToFlux` 内部，但**复用同一个** `RagApiException.fromUpstream`
——保证两条路的 detail 翻译是同一份实现。

### 3.2 为什么不能 `bodyToFlux(String.class)`

因为它会走上面 2.3 的编解码器协商，触发 SSE 解析器。所以这里不按"文本"读，而是按**原始字节**读：
`response.bodyToFlux(DataBuffer.class)` —— `DataBuffer` 是 Spring 对「一块字节」的抽象。

### 3.3 `Flux.defer`：每个订阅拿到独立的解码器状态

```java
// RagClient.java:114-120
private Flux<String> decodeRawText(Flux<DataBuffer> chunks) {
    return Flux.defer(() -> {
        CharsetDecoder decoder = StandardCharsets.UTF_8.newDecoder()
                .onMalformedInput(CodingErrorAction.REPLACE)
                .onUnmappableCharacter(CodingErrorAction.REPLACE);
        ByteArrayOutputStream carry = new ByteArrayOutputStream(8);
```

`Flux.defer(...)` 的意思是：**每次有订阅者订阅时，才执行里面的 lambda**。
所以 `decoder` 和 `carry` 是"每个订阅一份"的。

如果不包 `defer`，这两个对象会在**创建 Flux 时**就共享一份——两个用户同时提问（两路并发订阅），
一路的残字节会被另一路读走 → 双方都乱码。这与 `RagService` 里 `Flux.defer` 包 `StringBuilder` 是同一个套路
（见 `RagService.java:112-115`）。

> **规律**：凡是「有状态的累加器 + 会被多次订阅的 Flux」，都要放进 `Flux.defer`。
> 这是 Reactor 里的标准做法，也是很好的面试素材。

`onMalformedInput/onUnmappableCharacter(REPLACE)`：遇到坏字节不要抛异常，替换成 `U+FFFD`（�），
保证解码过程不会因为一个坏字节就把整条流打断。

### 3.4 核心：残字节是怎么跨块保留的

一个 UTF-8 汉字占 **3 字节**，而网络分块是任意切的，所以一个汉字很可能被切成两半：

```
块1: ... E4 BD      ← "你"(E4 BD A0) 的前 2 字节
块2: A0 E5 A5 BD ... ← 剩下的 1 字节 + "好"
```

如果每块各自 `new String(bytes)`，`E4 BD` 单独解就是乱码。看代码怎么处理：

```java
// RagClient.java:122-177（★ 已修正，见下面的警告框）
Flux<String> texts = chunks.map(buf -> {
    try {
        byte[] bytes = new byte[buf.readableByteCount()];
        buf.read(bytes);
        if (carry.size() > 0) {          // ① 先接上上一块留下的残字节
            carry.write(bytes);
            bytes = carry.toByteArray();
            carry.reset();
        }
        ByteBuffer in = ByteBuffer.wrap(bytes);
        // ② ★ 三参重载 + endOfInput=false：解不完的残字节留在 in 里（position 停在它前面）
        CharBuffer out = CharBuffer.allocate(bytes.length + 1); // UTF-8 每字节最多产出一个字符
        CoderResult cr = decoder.decode(in, out, false);
        if (cr.isError()) {              // REPLACE 策略下不该发生，留作防御
            throw new RagApiException(502, "上游返回的内容不是合法 UTF-8");
        }
        if (in.hasRemaining()) {         // ③ 有剩 = 末尾是半截字符
            carry.write(bytes, in.position(), in.remaining());  // ④ 存起来给下一块
        }
        out.flip();
        return out.toString();
    } catch (IOException e) {
        throw new RagApiException(502, "读取上游响应失败：" + e.getMessage());
    } finally {
        DataBufferUtils.release(buf);    // ⑥ 见 3.6
    }
}).filter(s -> !s.isEmpty());            // ⑤ 整块都是残字节时解出空串，别往下游发
```

**逐点理解**：

| 标记 | 做了什么 | 为什么 |
|---|---|---|
| ① | 把上一块的残字节拼到本块**前面** | 让半截字符重新凑齐 |
| ② | **三参 `decode(in, out, false)`**：`false` = 「后面还有输入」，解不完的字节**留在 `in` 里** | 这是「保住残字节」的关键。★ 用单参重载做不到，见下面的警告框 |
| ③ | `in.hasRemaining()` 为真 = 末尾有半截字符 | |
| ④ | `carry.write(bytes, in.position(), in.remaining())` 精确取出那半截 | 用 `position` 而不是猜长度 |
| ⑤ | `filter` 掉空串 | 否则每个"纯残字节块"都会往流里推一个空字符串，下游要处理噪声 |
| ⑥ | 释放 `DataBuffer` | 见 3.6 |

**走一遍**（上游发 `你好世界`，传输层正好切了 3 刀）：

```
上游: 你好世界 = E4 BD A0  E5 A5 BD  E4 B8 96  E7 95 8C
                        ↓ 传输层切
块1 = [E4 BD]          块2 = [A0 E5 A5 BD E4 B8]        块3 = [96 E7 95 8C]

块1: carry 空 → 一个完整字符都解不出 → 输出 ""     → carry=[E4 BD]
块2: 拼成 [E4 BD A0 E5 A5 BD E4 B8] → 解出"你好"，剩 [E4 B8] → carry=[E4 B8]
块3: 拼成 [E4 B8 96 E7 95 8C]       → 解出"世界"，无剩     → carry=空
                                       ────────────────────────
                                三块文本拼起来 = "你好世界" ✅
```

**注意：块的边界和文本的边界完全不同**——块1 单独解出来是空的，块2 解出"你好"，块3 解出"世界"。
这就是为什么不能一块一块直接 `new String(bytes)`。

> ### ⚠️ 为什么必须是「三参重载」——这里踩过一次真坑
>
> JDK 的 `CharsetDecoder` 有两个 `decode`，行为**不一样**：
>
> | 方法 | 输入结束 | 尾部那半截字 | 结果 |
> |---|---|---|---|
> | 单参 `decode(ByteBuffer)` | **隐含 `true`** | **当坏字节，换成 `U+FFFD`** | position 走到末尾 → `hasRemaining()` **恒为 false** |
> | 三参 `decode(in, out, false)` | 你显式说 `false` | **留在 `in` 里** | position 停在残字节处 → `hasRemaining()` 为 true |
>
> 单参那个是**"一次性解完全部输入"的便利方法**：JDK 内部直接按 `endOfInput=true` 调三参版本，
> 最后还会 `flush()`。于是结尾那半截被当成「输入到此结束的坏字节」吃掉了。
>
> **实测**（8 字节 `[E4 BD A0 E5 A5 BD E4 B8]`）：
>
> ```
> 单参      → 解出 你好 + U+FFFD，position=8，remaining=0
> 三参false → 解出 你好，          position=6，remaining=2   ← 残字节 [E4 B8] 保住了
> ```
>
> ★ **这段代码最初写的就是单参**，注释里那句「残字节会留在 `in` 里」是**错的**——
> 后果是 `carry` 变成**死代码**，跨块汉字全解成 `�`：
>
> ```
> 上游发 "你好世界"，切成 3 块（切开了"你"和"世"）
> 单参版   : U+FFFD U+FFFD U+597D U+FFFD U+FFFD U+754C   = ��好��界
> 三参修正 : U+4F60 U+597D U+4E16 U+754C                 = 你好世界
> ```
>
> 这个 bug **不一定会复现**——只有块边界恰好切在汉字中间才出问题，而上游是逐段 `yield` 的，
> 一次 write 通常就是一个完整的 `DataBuffer`。所以本地跑大概率正常，属于**潜伏 bug**。
>
> **面试时这是个好素材**：*「我一开始用单参 `decode(ByteBuffer)`，以为它会把解不完的字节留下，
> 后来实测发现它按 `endOfInput=true` 把尾部当坏字节吃掉了，改成三参 + `false` 才对。」*
> ——体现了「不靠注释、靠实测验证 JDK 行为」。

### 3.5 收尾：最后那半截怎么处理

流结束时，`carry` 里如果还留着字节，说明**最后那个字符真的被截断了**（不是分块问题，是上游没发完）。
`RagClient.java:159-177` 用一个 `Mono` 在流末尾补一次解码：

```java
Mono<String> tail = Mono.fromSupplier(() -> {
    if (carry.size() == 0) return "";
    byte[] rest = carry.toByteArray();
    carry.reset();
    // 输出缓冲给 rest.length + 1 就够：REPLACE 策略下每个坏字节最多产出一个 U+FFFD
    CharBuffer out = CharBuffer.allocate(rest.length + 1);
    // 这两个重载不抛受检异常，改看返回的 CoderResult
    if (decoder.decode(ByteBuffer.wrap(rest), out, true).isError()) {  // true = 输入到此结束
        return "";
    }
    if (decoder.flush(out).isError()) return "";
    out.flip();
    return out.toString();
}).filter(s -> !s.isEmpty());

return texts.concatWith(tail);
```

**两个重载的差别（整节的关键，§3.4 的警告框是同一件事的另一面）**：

- `decode(ByteBuffer in)` —— **一次性解完全部输入**：内部先 `reset()`，再按 `endOfInput=true` 解码，最后 `flush()`。
  尾部那半截因此被当坏字节换掉。返回 `CharBuffer`，**抛** `CharacterCodingException`。
- `decode(ByteBuffer in, CharBuffer out, boolean endOfInput)` —— **可以只解一部分**：「后面还有没有输入」交给你决定。
  **不抛受检异常，返回 `CoderResult`**：`isUnderflow()` = 输入不够了 / `isOverflow()` = 输出缓冲不够 / `isError()` = 真坏字节。

末尾 `endOfInput=true` 的含义是"后面没有更多输入了"，所以解码器会把 `carry` 里那半截按 REPLACE 策略变成 `�`。
`flush(out)` 是把解码器内部可能残留的移位状态吐出来。

> ★ **修正前这段是死代码**：主循环用单参重载时 `carry` 永远是空的，
> `if (carry.size() == 0) return "";` 每次都直接返回。主循环改成三参 + `false` 之后这段才真正会触发
> ——已实测：喂一个末尾是半截字的流（`[E4 BD A0 E5 A5]`），得到 `你` + `U+FFFD`。

### 3.6 `DataBufferUtils.release(buf)` —— 不还回去就是内存泄漏

```java
finally {
    // DataBuffer 可能是 Netty 的池化缓冲区，不还回去就是内存泄漏
    DataBufferUtils.release(buf);
}
```

这是**极易被面试官抓的点**。`DataBuffer` 底层常是 Netty 的**池化**（pooled）缓冲区，
是**引用计数**管理的对象。读完之后必须释放，否则池子里的内存只借不还，
请求量一上来就是 OOM。

两个要点：
1. 放在 `finally` 里——**正常、异常、取消三条路径都要释放**；
2. 注意别"释放两次"或"该释放给别人读的却自己释放了"。这里 `read(bytes)` 已经把数据拷进自己的 `byte[]`，
   所以本方法内释放是安全的。

## 4. 前端：增量分帧

### 4.1 为什么是 `fetch`，不是 `EventSource`，也不是 `axios`

`rag.js:264-271` 的注释给了答案，三点都要记：

| 方案 | 为什么不行 |
|---|---|
| `EventSource` | **只支持 GET**，不能带自定义请求头、不能发 JSON 请求体；而问答是 POST |
| `axios` | 浏览器的 XHR **没有流式读接口**；`onDownloadProgress` 给的是"累积到目前的整段文本"，拿它硬拼增量又笨又容易错 |
| **`fetch` + `ReadableStream`** | ✅ 唯一能一行一行读到字节的方案 |

代价是：错误翻译要自己再做一遍，所以 `rag.js` 复用了 `http.js` 导出的 `toHttpError` / `canceledError`，
**保证两条路的错误文案只有一份**（这是个很好的"代码复用意识"素材）。

### 4.2 `TextDecoder({ stream: true })` —— 和 Java 侧是同一件事

```js
// rag.js:328-329, 355-362
const reader = res.body.getReader()
const decoder = new TextDecoder('utf-8')
...
// stream: true 不能省 —— 一个 UTF-8 汉字占 3 字节，很可能正好被切在
// 两个 chunk 之间。不加这句会把半个字符解码成"�"，而且越界还会把下一个字符也带歪
if (consume(parser.push(decoder.decode(value, { stream: true })))) break read
...
// 收尾：不带 stream 再 decode 一次，把解码器里可能残留的半截字符吐出来
consume([...parser.push(decoder.decode()), ...parser.flush()])
```

**和 Java 侧 `CharsetDecoder` 是同一个问题**：汉字 3 字节被切在分块边界上。
但实现方式不同，这点要能说清：

| | Java（`RagClient.decodeRawText`） | 前端（`chatStream`） |
|---|---|---|
| 谁保留残字节 | **代码手动 `carry`**（`ByteArrayOutputStream`） | **`TextDecoder` 内部保留**（`{stream:true}`） |
| 收尾 | 手动 `decode(...,true)` + `flush()` | `decoder.decode()`（不带 stream） |

### 4.3 分帧器：`createSseParser()`

```js
// rag.js:128
const FRAME_SEP = /\r?\n\r?\n/        // 事件之间用空行分隔，\r\n 和 \n 都会出现
```

```js
// rag.js:176-190
push(text) {
  buffer += text
  const out = []
  let m
  while ((m = FRAME_SEP.exec(buffer)) !== null) {   // 非全局正则，每次从头找
    const frame = buffer.slice(0, m.index)
    buffer = buffer.slice(m.index + m[0].length)
    const data = frameData(frame)
    if (data !== null) out.push(data)
  }
  return out
}
```

**为什么需要 `buffer`**：网络分块和"事件边界"没有任何关系——一个事件可能被切成两块，
一块里也可能有好几个事件。所以必须自己攒一个缓冲区，攒到完整的空行分隔才切一帧。
**这就是"自己实现分帧"的本质。**

`\r?\n\r?\n` 同时兼容 `\n\n` 和 `\r\n\r\n`（注释说"中间换过一手代理就会混"）。

`flush()`（:192-199）处理**最后一个事件没有尾随空行**的情况——很多实现不发尾随空行，不 flush 就会丢最后一帧。

### 4.4 ★ 最不显然的一行：把"裸行"补回正文

```js
// rag.js:144-174
function frameData(frame) {
  const dataLines = []
  let sawData = false

  for (const line of frame.split(/\r?\n/)) {
    if (line.startsWith(':')) continue                  // 注释/心跳
    if (line.startsWith('data:')) {
      dataLines.push(line.slice(5).replace(/^ /, ''))    // 规范：第一个空格是分隔符，不算内容
      sawData = true
      continue
    }
    if (/^(event|id|retry):/.test(line)) continue        // 用不上

    if (sawData) {
      // ⚠️ 本文件最不显然的一行。Java 侧 Spring 的 SseEmitter 写 data: 时
      // **不转义内容里的换行**（这是它的已知问题）：一个含 \n 的文本块会被写成
      //     data:第一行
      //     第二行
      // 而不是规范要求的 `data:第一行\ndata:第二行`。
      dataLines.push(line)                               // ← 裸行其实是正文，必须补回去
    } else {
      stray.push(line)
    }
  }

  return dataLines.length ? dataLines.join('\n') : null
}
```

**这就是亮点里"多格式增量分帧"的含义**——要同时兼容两种输出：

1. **合规的**：每一行都带 `data:`；
2. **不合规的**：`data:` 之后的内容里有裸换行（Spring 的 `SseEmitter` 已知不转义）。

不处理第 2 种，**markdown 回答会只剩第一行**。这是"回答丢字"的第二个来源（第一个是汉字被切开）。

### 4.5 `stray`：被丢弃的行 = 错误信息的来源

`sawData` 还是 `false` 时的裸行，会被塞进 `stray` 数组。它有个关键用途：

> 上游失败时，Java 侧的响应**已经提交成 200 了，状态码改不了了**，
> Spring 只能把错误 JSON 直接写进流里。

这个"错误 JSON 混在流里"的形态，从分帧器的角度看就是"悬空行"。所以：

```js
// rag.js:378
return { text, sawDone, errorDetail: strayDetail(parser.strayText()) }
```

```js
// rag.js:251-262
function strayDetail(stray) {
  if (!stray) return ''
  let detail = ''
  try {
    detail = extractDetail(JSON.parse(stray))    // 先按 JSON 解
  } catch {
    detail = extractDetail(stray)                // 截断/HTML 再退回纯文本
  }
  // 兜底不能放在调用方：调用方只能看到「有没有 detail」，
  // 分不清「没有悬空内容」和「有悬空内容但翻译不出人话」，前者不该报错
  return detail || '生成中断（服务端提前关闭了连接）'
}
```

**这里有个很值得讲的细节**（`rag.js:241-250` 注释）：`extractDetail` 是按 **axios 的形态**设计的——
axios 已经把 JSON 响应体解析成对象了，所以它只把**字符串**当"不是 JSON 的兜底"。
而这里拿到的是流里读出来的**原始字节**，`{"detail":"..."}` 到这儿还是一根字符串，
直接丢给 `extractDetail` 会原样返回，用户就看到一串带花括号和转义的原文。
所以**先按 JSON 解一次**。

### 4.6 三种增量格式都要能吃下：`parseChatChunk`

```js
// rag.js:104-125
const TEXT_KEYS = ['delta', 'content', 'text', 'answer', 'token', 'message', 'response', 'reply']

export function parseChatChunk(raw) {
  const text = String(raw ?? '')
  const trimmed = text.trim()
  if (!trimmed) return ''
  if (trimmed[0] !== '{') return text          // 裸文本，最常见的一条路

  try {
    const obj = JSON.parse(trimmed)
    if (!obj || typeof obj !== 'object') return ''
    for (const key of TEXT_KEYS) {
      if (typeof obj[key] === 'string') return obj[key]
    }
    const nested = obj.choices?.[0]?.delta?.content ?? obj.choices?.[0]?.message?.content
    return typeof nested === 'string' ? nested : ''
  } catch {
    return text                                // 不是完整 JSON（可能被代理截断），当裸文本
  }
}
```

三种格式：**裸文本** / **JSON 信封**（`{"delta":"..."}`）/ **OpenAI 风格**（`choices[0].delta.content`）。

**关键设计决策**（注释里写了，面试好用）：认不出来的 JSON **一律返回空串**，
绝不把 JSON 原文糊进答案——因为上游开始推 `{"sources":[...]}` 这类元数据时，
用户看到的应该是"什么都不多"，而不是屏幕上一串花括号。

> 副作用要承认：`TEXT_KEYS` 是一组**启发式**字段名白名单。契约变了可能要加。
> 这是个诚实的边界，被问到就直说。

### 4.7 `[DONE]` 哨兵与"见过之后不再当正文"

```js
// rag.js:88-94
const DONE_SENTINEL = '[DONE]'
const isDoneSentinel = (data) => String(data ?? '').trim().replace(/^"|"$/g, '') === DONE_SENTINEL
```

注意 `replace(/^"|"$/g, '')`——因为 `[DONE]` 可能**被 JSON 编码过一层**变成 `"[DONE]"`。

```js
// rag.js:334-348
const consume = (frames) => {
  if (sawDone) return true        // 已经见过结束标记：后面剩下的字节一律不当正文
  for (const data of frames) {
    if (isDoneSentinel(data)) { sawDone = true; return true }
    const piece = parseChatChunk(data)
    if (!piece) continue
    text += piece
    onDelta?.(piece)
  }
  return false
}
```

`sawDone` 之后的字节**不再当正文**——因为那很可能是错误体的残渣。

### 4.8 收尾与取消

```js
// rag.js:363-376
} catch (err) {
  if (signal?.aborted) {
    // 中止时缓冲区里那半个没凑齐的帧**故意丢弃**，不 flush：
    // 它最多是最后一个增量（用户已经按了停止，本来就不想要了），
    // 但它也可能是半截 JSON 信封 —— 补进答案里会变成一串花括号，比少一个字难看得多
    throw canceledError()
  }
  // 读到一半连接断了。**已收到的内容不回滚** —— 由调用方决定保留还是丢弃
  throw toHttpError({ rawBody: '连接中断，回答可能不完整' })
} finally {
  // 不管正常结束、提前 [DONE] 还是出错，都主动取消读端，
  // 万一上游还在生成，别让它继续白算
  reader.cancel().catch(() => {})
}
```

**三个要点**：
1. **中止时故意不 flush**——这是个很细的取舍，面试讲这个能体现你想过边界；
2. **已收到内容不回滚**——交给上层（`chatStore`）决定标成 `CANCELED` 还是 `INTERRUPTED`；
3. **`finally` 里 `reader.cancel()`**——主动掐掉读端，避免上游白算。**和 Java 侧 `DataBufferUtils.release` 是同一种"资源必须归还"的意识，可以对照着讲。**

### 4.9 顺带：`Accept: text/event-stream` 引发的第二个坑

`rag.js:303-321` 处理的是另一个同源问题。因为 `chatStream` 发的是
`Accept: text/event-stream`，而接口的 `produces` 也是 `text/event-stream`，
**Java 侧 `GlobalExceptionHandler` 想返回 `ApiErrorResp` 时找不到能写这个对象的转换器**——
结果 5xx 变成"没有 Content-Type、body 为空"的裸响应（实测 `500 ct=null body=""`）。

而"空 body 的 5xx"在 axios 那条路上等价于"Java 没起来"，所以 `toHttpError` 会给出
`请确认后端已在 8080 启动`——**这句话在这里是误导**：Java 明明活着，真相是它后面那一步炸了
（最常见的是 FastAPI 没起）。所以这里**单独改写文案**：

```js
if (!rawBody && res.status >= 500) {
  throw toHttpError({
    status: res.status,
    rawBody: `后端返回了 ${res.status} 但没带错误详情。可能是 Java 没启动，也可能是它调用上游 RAG 服务失败（FastAPI 在 8102 吗？）`,
  })
}
```

**根因的修法在 Java 侧**：`GlobalExceptionHandler` 强制 `.contentType(APPLICATION_JSON)`（见 `docs/rag对接实现说明.md` 第九节坑 1）。
前端这段是**双保险 + 文案纠正**。

## 5. 三层对照表（同一件事的三种实现）

| 问题 | Python | Java | 前端 |
|---|---|---|---|
| 汉字被块边界切开 | 不需要处理（它产出的是完整 str） | 手动 `carry` + **三参 `decode(...,false)`** | `TextDecoder({stream:true})`（解码器内部保留） |
| 输出格式 | `StreamingResponse` 直出裸文本 | 按 `DataBuffer` 读字节，绕开 SSE 解析器 | 手写分帧器，兼容 `data:` 与裸行 |
| 结束标记 | 无（靠连接关闭） | 无 | `[DONE]` 哨兵 |
| 错误传递 | 异常塞进 `queue` 搬到调用线程 | `exchangeToFlux` 里转 `RagApiException`；流已提交时只能写进流 | 从 `stray` 悬空行里捞 `detail` |
| 资源归还 | `aclose()` 关 async generator | `DataBufferUtils.release(buf)` | `reader.cancel()` |

## 6. 面试追问清单（问题 + 答题要点)

**Q1. 为什么会有"回答静默消失"？**
> 上游响应头声明 `text/event-stream`，但体是裸文本无 `data:` 分帧；Spring 按响应头的 Content-Type 选了 SSE 解析器，按规范把无前缀的行当未知字段丢掉，解析出 0 个事件。返回 200、流为空，前端白等。

**Q2. 为什么改请求头的 `Accept` 不行？**
> 编解码器是按**响应头**的 Content-Type 选的，请求头改不了它。所以只能从字节层绕——用 `bodyToFlux(DataBuffer.class)` 自己读字节。

**Q3. 那为什么不干脆让 Python 侧改成合规的 SSE？**
> 可以，那是最干净的修法（并且 Java 侧就不用绕了）。当前在 Java 侧绕是为了不改上游契约就能跑通。**如果重做，我会两边一起改**——这句话能体现你不只会打补丁。

**Q4. 跨块的汉字你怎么处理的？**
> UTF-8 汉字 3 字节，可能被切在分块边界。Java 侧自己维护一个 `carry` 字节缓冲：用 **三参 `decode(in, out, false)`** 让解不完的字节**留在 `ByteBuffer` 里**，再靠 `position`/`remaining` 精确取出，下一块拼到前面再解。前端对应的是 `TextDecoder` 的 `{stream:true}`。
>
> ★ **加分点——我踩过这个坑**：一开始我用的是单参 `decode(ByteBuffer)`，以为它会把解不完的字节留下。**实测发现不是**：它内部按 `endOfInput=true` 调三参并 `flush()`，尾部那半截被换成 `U+FFFD`、position 直接走到末尾——于是 `hasRemaining()` 恒为 false，`carry` 变成**死代码**。改成三参 + `false` 才保住。
> 实测 8 字节 `[E4 BD A0 E5 A5 BD E4 B8]`：单参 → 解出 `你好`+`�`、position=8；三参 → 解出 `你好`、position=6、remaining=2。

**Q5. 两个用户同时提问会不会互相污染？**
> 不会。解码器和 carry 都在 `Flux.defer` 里创建，**每个订阅一份**。同理 `RagService` 里累加回答的 `StringBuilder` 也放在 `Flux.defer` 里。

**Q6. `DataBuffer` 为什么要 release？**
> 底层常是 Netty 池化缓冲，引用计数管理，不还就是内存泄漏。放在 `finally` 里保证正常/异常/取消三条路径都释放。

**Q7. 前端为什么不用 `EventSource`？**
> `EventSource` 只支持 GET，不能带自定义头、不能发 JSON body；问答是 POST。所以只能用 `fetch` + `ReadableStream` 手写分帧。

**Q8. 为什么要自己写分帧？SSE 不是有空行分隔吗？**
> 网络分块和事件边界无关。一个事件可能被切成两块，一块里也可能有多个事件，所以要自己攒缓冲区。另外还要兼容 Spring `SseEmitter` **不转义换行**的非规范输出（`data:` 后的裸行其实是正文），不然 markdown 回答只剩第一行。

**Q9. 上游报错了，前端怎么知道？**
> 两种：①开流前就失败 → HTTP 非 2xx，读 body 走 `toHttpError`；②流已提交后才失败 → Java 只能把错误 JSON 写进流里，前端从"悬空行"（`stray`）里捞出来翻译。

**Q10. 用户点"停止生成"时缓冲区里那半个事件怎么处理？**
> **故意丢弃、不 flush**。它最多是最后一个增量，也可能是半截 JSON 信封——补进答案里会变成一串花括号，比少一个字难看得多。同时 `reader.cancel()` 掐掉读端，别让上游白算。

**② 跑离线单测看分帧器**（不需要任何后端）

这个脚本用 `ReadableStream` 造假上游，专门测十几条边界：**跨块半汉字、CRLF、不转义换行、错误 JSON 混流、abort、空 body 500 文案**。
看完它再回去看 `createSseParser`，会清楚很多。

**③ 故意破坏，看它怎么坏**（最好的理解方式）

两种破坏方式，都能亲手制造出乱码：

- **改回单参重载**：把 `decoder.decode(in, out, false)` 换成 `decoder.decode(in)` —— 就是这次修掉的那个 bug；
- **掐掉 carry**：把 `if (in.hasRemaining())` 改成 `if (false)`。

改完重启 Java、问一个会返回中文的问题，看回答里是否出现 `�`；改回来确认恢复。

> ⚠️ **这两个实验不一定会立刻复现**——只有块边界恰好切在汉字中间才出问题，而上游是逐段
> `yield` 的、一次 write 通常就是一个完整的 `DataBuffer`。想要确定的乱码，用下面这个纯 JDK 复现。

**④ 用 20 行纯 JDK 代码复现（不用启任何服务）**

块边界是"看运气"的东西，直接喂字节最干脆：

```java
byte[] bytes = { (byte)0xE4,(byte)0xBD,(byte)0xA0,(byte)0xE5,(byte)0xA5,(byte)0xBD,(byte)0xE4,(byte)0xB8 };
//                                 ↑ "你好"(6字节)            ↑ "世" 的前 2 字节（半截）

ByteBuffer in = ByteBuffer.wrap(bytes);
CharBuffer out = dec().decode(in);                       // ← 单参：错误示范
System.out.println(in.position() + " / " + in.remaining() + " / " + in.hasRemaining());
// → 8 / 0 / false       解出"你好"+U+FFFD，残字节被吃掉了

ByteBuffer in2 = ByteBuffer.wrap(bytes);
CharBuffer out2 = CharBuffer.allocate(bytes.length + 1);
CoderResult cr = dec().decode(in2, out2, false);         // ← 三参 + false：正确
System.out.println(in2.position() + " / " + in2.remaining() + " / " + in2.hasRemaining());
// → 6 / 2 / true        解出"你好"，残字节 [E4 B8] 保住了
```

（`dec()` 就是 `StandardCharsets.UTF_8.newDecoder().onMalformedInput(REPLACE).onUnmappableCharacter(REPLACE)`；
打印码点用 `U+%04X` 而不是直接 `println`，避开控制台编码的干扰。）
