## 一、依赖（`pom.xml`）

**① 加 `mybatis-plus-spring-boot4-starter:3.5.17`（版本号走 `<mybatis-plus.version>` 属性）**
不是同版本的 `mybatis-plus-spring-boot3-starter` —— Boot 4 的第三方 starter 按主版本分家，用错会以一堆
`NoClassDefFoundError` 收场。传递依赖实测：`mybatis-plus`（core/annotation/spring→extension）+
`mybatis:3.5.19` + `mybatis-spring:4.0.0` + `spring-boot-starter-jdbc:4.1.1`（→ `spring-jdbc:7.0.9`，
HikariCP 一起进来，所以不用单独加）。`mysql-connector-j` 本来就在 pom 里，没动。

**验证**：`.\mvnw.cmd dependency:tree` 看那棵子树；启动时 `--debug` 的条件报告里搜
`MybatisPlusAutoConfiguration` 应该是 `matched`。

## 二、配置（`src/main/resources/application.yaml`）

**② `spring.datasource`：url / username / password / hikari 四项**
- url：`jdbc:mysql://${DB_HOST:localhost}:${DB_PORT:3306}/${DB_NAME:computer_biz}?characterEncoding=utf8&sslMode=DISABLED&allowPublicKeyRetrieval=true`
  —— 后两个参数是 MySQL 8 的 `caching_sha2_password` 在**不加密**连接上的要求，少一个就报
  `Public Key Retrieval is not allowed`；Connector/J 9 里 `useSSL` 已过时，用 `sslMode`。
- `username`/`password` 走 `${DB_USER:computer_biz}` / `${DB_PASSWORD:}`：**密码不进仓库**，
  启动前在终端设环境变量（`start.md` ②）。
- `hikari.pool-name`：日志里认得出是自己的池（`HikariPool-1` 可能是别人的）。
- `hikari.connection-timeout: 3000`：默认 30 秒时，库挂了会让 Tomcat 线程被扣住 30 秒，
  而前端 axios 超时只有 15 秒 —— 结果是**前端先超时、你在日志里什么都看不到**。

**③ `mybatis-plus.configuration.map-underscore-to-camel-case: true`（显式写出来）**
MP 的默认值<b>就是</b> true（和裸 MyBatis 相反），写出来是为了让读的人不用去查版本默认值。
**绝不能改成 false**：`file_name → fileName` 全靠它，关掉会得到一堆 null。

**④ `mybatis-plus.configuration.log-impl: Slf4jImpl`**
SQL 日志走已有的 logback，而不是 MP 默认的 `StdOutImpl`（后者是 `System.out`，
绕过所有日志配置、没有时间戳、没法按环境关掉）。

**⑤ `mybatis-plus.global-config.db-config.id-type: auto`**
主键交给 MySQL 自增，不用 MP 默认的雪花（19 位）。理由不只是「1/2/3 好读」：同一轮问答的两行消息
**靠 id 排序**（它们共享 created_at），自增让这个语义天然成立。以后要分库再换回来，一处改。

**⑥ `logging.level.org.example.computerbizservice.mapper: DEBUG`**
MyBatis 的 logger 名就是 mapper 接口的全限定名，所以这一行 = 打开 mapper 包里每条语句的
`Prepared` / `Updates` 输出。`<== Updates: 1` 是验证写入有没有生效最直接的证据。

## 三、启动与注册

**⑦ `ComputerBizServiceApplication` 加 `@MapperScan("org.example.computerbizservice.mapper")`**
第一次用 MyBatis-Plus 最常翻的车：不写它、接口上又不写 `@Mapper`，启动就报
`NoSuchBeanDefinitionException: ...UserMapper`。**两条路选一条**，都走等于同一个 mapper 注册两次。

**⑧ 新增 `src/test/resources/application.yaml`，把测试指向 `computer_biz_test` 库**
因为启动自检会把 `status='STREAMING'` 的行全部改成 `INTERRUPTED` —— 这一条对着开发库跑是
**破坏性**的（开发库里有正在生成的流时，它会把活的说成死的）。
代价：`mvn test` 需要多一个库（建库语句在 `start.md` ⓿）。本项目的验证靠真实启动，不靠这个测试。

## 四、常量与工具（新增两个类）

**⑨ `common/AppConstants.DEFAULT_USER_ID = 1L`**
本轮没有登录，这是「服务端替用户声明的身份」，所以是常量而不是配置项（登录做完后这里会换成
「从 SecurityContext 取」）。★ 绝不能改成「信任请求里带的 user_id」—— 没鉴权时那是白送的越权。
演示用户由启动自检补写 `user` 表 id=1，两头靠这个常量对齐。

**⑩ `AppConstants.MAX_STORED_ANSWER_CHARS = 100_000`**
一条回答最多攒多少字符入库。**不是给正常回答用的**，是防「上游挂在那儿一直推」把内存和列宽推爆。
超出的部分不再攒，**但流本身照常转发** —— 落库是旁路，这条在这里体现得最直接。

**⑪ `AppConstants.TITLE_SOURCE_CHARS = 30`**
会话标题取第一句提问的前 30 字（列宽 64，所以不用再截断）。

**⑫ `AppConstants.MAX_{FILE_NAME,STAGE,RESULT,ERROR,CONTENT_TYPE}_CHARS`**
就是 `db/schema.sql` 里的列宽，集中在一处（散在各处的话改列宽时会漏）。理由：
MySQL 8.4 跑在严格模式下，超长**不截断而是报** `Data too long for column`，
而轮询那条路上的异常会发生在「必须保持健康」的请求里。
★ 里面**故意没有 job_id / session_id**：业务键不截断（见 ㉟）。

**⑬ `util/TextUtils.truncate(s, maxChars)` 按字符截断、null 原样返回**
按**字符**算正好是 `VARCHAR(n)` 的口径（它数的就是字符）。null 透传是因为调用方靠 null 和空串
区分语义（`error` 列的「没写」和「清空」），这个函数不替它们做决定。

**⑭ `util/TextUtils.isBlank(s)`**：null 和全空白都算空。

## 五、枚举（新增三个）

**⑮ `IngestStatus` / `ChatMsgStatus` 用 `@EnumValue` 存大写字符串**
不依赖 MP「默认枚举处理器」（3.5 里行为变过，不写明就得翻版本才知道存的是枚举名还是序号）。
显式标注后 Navicat 里看到的是 `'DONE'` 而不是 `3`。
验证方法：`SELECT status FROM chat_message` 应该看到字符串；看到数字就说明没生效（设计文档 §10.6）。

**⑯ `ChatMsgStatus` 的五个值 = 前端 `chatStore.MSG` 那五个（大小写不同）**
`STREAMING/DONE/CANCELED/INTERRUPTED/ERROR`。**不要自己造第六个** —— 前端的状态机是这套语义的
另一半，多加一个值它就渲染不出来。

**⑰ `IngestStatus` 只有五个值，缺的正是前端那些「纯客户端状态」**
前端的 `queued/uploading/committing` 是「请求还在网线上」时的显示态，服务端永远看不到。
库里只有 `INGESTING/SUCCESS/SKIPPED/FAILED/UNKNOWN`。

**⑱ `ChatRole` 的 code 是**小写**（`"user"`/`"assistant"`），和上两个相反**
这是**故意的**：列里存的是前端的角色名（前端的 `role` 就是小写），而状态列存的是我们自己的枚举名。
两处大小写不一致是有意的选择，不是笔误 —— 所以 `ChatRole` 的注释专门解释了这一点。

## 六、实体与 Mapper

**⑲ 四个实体都用 `@Data` + `@TableName` + `@TableId(type = IdType.AUTO)`**
**没有** `@Builder` / `@AllArgsConstructor`（★ 硬性约束）：MyBatis 靠**无参构造 + setter** 实例化，
加了全参构造就没了默认构造，症状是「查出来的对象字段全是 null」——这是本项目 Lombok 用得多时
最容易中的一枪，所以每个实体类的注释里都写明了。

**⑳ 时间戳不写 `MetaObjectHandler`，交给数据库默认值**
`created_at DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3)`、`updated_at ... ON UPDATE ...`。
可行的原因就是设计文档里那条 `NOT_NULL` 策略：实体里为 null 的字段不会出现在 INSERT/UPDATE 里。
省掉一个类 + 一处配置，代价是「Java 对象里拿不到刚写入的时间」——本轮只写不读，无所谓。
★ 例外是 `chat_message.createdAt`：那两行必须**共用一个值**，所以那里必须显式赋值。

**㉑ 四个 mapper 都是空的 `extends BaseMapper<T>` 接口**
方法一个都不用写（增删改查都在 `BaseMapper` 上）。空是刻意的，注释里说明了理由，
免得下一个人以为「还没写完」。

## 七、建表脚本（`db/schema.sql`）

**㉒ 四张表：`user` / `ingest_task` / `chat_session` / `chat_message`**
字段和逐列注释都在文件里。三条最容易被改错的写在文件头：状态存大写字符串、`error` 清空只能写空串、
时间列用 `DATETIME` 不用 `TIMESTAMP`。**幂等性：无**（是「空库初始化」脚本，重跑会报表已存在）。

**㉓ 入库任务是「一行一任务、就地更新」，不是流水**
上游的轮询接口返回的是**快照**（stage/result/done），不是事件流；追加的话一次入库会攒下几百行
几乎一样的记录。前端也本来就是按 `job_id` 展示一张卡片。

**㉔ `user_id` 加外键，`chat_message.session_id` 不加**
- 加：演示用户没建起来时写库会**当场报约束冲突**，而不是留下一堆悬空的 `user_id` 谁也发现不了。
- 不加：会话行和它的子行在**同一个事务**里创建，加了也只能抓我们自己的 bug、抓不到外部状态。

**㉕ `original_file_name` 与 `file_name` 并存**
上游会把文件名改名/去空格后回显。`file_name` 存上游回显（用户界面上看到的名字），
`original_file_name` 存用户真正传的 —— 一列的成本，换掉一次「到底哪个名字是用户传的」的考古。

**㉖ `poll_count` / `last_polled_at`**
「任务卡住了」和「页面早就关了」在库里长得一模一样，只有这两个能分开。这是事后最想问的问题。

**㉗ 不要 `seq`（回合序号）、不要 `chat_session.message_count`**
一问一答按 `id` 排就是回合顺序（主键单调自增）；`seq` 每次要 `SELECT MAX+1`，多一次读、多一个竞态。
消息数用 `COUNT(*)` 就有，本轮只写不读，加了就是白写一次。

**㉘ `error` 列的语义：一行里除「入库结论」之外要说的话**
两类内容：① 我们没问到的（网络/502/超时）② 上游说了但不是入库结论的（404 的「任务不存在」、
result 前缀认不出来）。分界是 **`result` 只装上游对「入库这件事」的结论**。
（这条是写代码时才完全定下来的，schema 和实体的注释都跟着改准了。）

## 八、启动自检（新增 `common/PersistenceStartupCheck`）

**㉙ 三件事按依赖顺序跑：① 连上没 ② ORM 接上没有 ③ 补演示用户 + 清扫僵尸流**
① 用 `JdbcTemplate` 查 `SELECT VERSION()`（**完全不碰 MyBatis**）；② 用 mapper 查一次演示用户
（走 mapper 扫描 → 语句生成 → 下划线转驼峰的完整路）。
**①打印了、②炸了 ⇒ 问题在 MyBatis 不在 MySQL** —— 这一句能省掉半小时。

**㉚ ① 的异常不捕获**：库不在 / 密码错 / MySQL 没起来 → **启动直接失败**。
「缺库要吵」：让接线问题在最早、最安静的时刻暴露，而不是等你调接口时撞上一个 500。

**㉛ ② 里两种失败区别对待**（这条注释原来和代码矛盾，一起改准了）：
- 查询本身炸（表不存在/列名对不上/权限不够）→ **抛，启动失败**。最常见成因就是「忘了跑 schema.sql」。
- 查到了「没有这个用户」但补写失败 → **只打 ERROR，服务照常起**。表和接线都是好的，坏的只是这一次写。

**㉜ ③ 清扫僵尸流：开机把 `status='STREAMING'` 的行全改成 `INTERRUPTED`**
一条流不可能活过一次进程重启，所以开机时任何 `STREAMING` 行**必然**是「答案没落下来」的残骸。
这就是助手行「先建后改」多花那一次写换来的东西。**失败也只打 ERROR**：它是一次维护，
不是服务能干活的前提（和 ① 正相反）。

## 九、`RagService` 里挂的三个写入钩子

**㉝ 上传：先调上游、拿到 job_id 之后再落库，顺序不能反**
`job_id` 是上游给的，调之前拿不到；上游失败时异常直接抛给前端，也就没有「任务」可记。

**㉞ 轮询：`catch (RagApiException e)` 里先记一笔、然后 `throw e`（★ 原样抛）**
不吞、不包装。前端看到的状态码必须还是上游的（404 vs 502 对它的重试策略有意义）。

**㉟ 轮询失败只写 error、不改 status（404 除外）**
数据库里的 `status` 只代表「上游说过什么」；我们没问到的东西写进 `error` 才不撒谎。
404 是例外：上游明确回答了「任务不存在」，那是一次**成功的询问**，所以 status 跟着上游走（→ UNKNOWN）。
（另一条路是跟着前端一起标 UNKNOWN —— 没选：前端那个是**客户端显示态**，让数据库跟着 UI 走，
以后做读接口时分不清「上游说未知」和「我们没问到」。）

**㊱ 问答的提问在「订阅之前、请求线程上」同步写**
那时响应还没开始，写库失败还能被抓住记日志；而且上游挂掉的那次提问也留下了痕迹。
放进 `Flux.defer()` 里写的话，落库成了流的一部分 —— DB 一抖会把用户的回答带崩。

**㊲ 攒回答只用 `doOnNext`/`doOnError`/`doFinally` 这类副作用算子，不用 `publishOn`**
副作用算子对流的背压、缓冲、线程都透明。`publishOn(boundedElastic)` 会为整个回答（可能几分钟）
**长期占住**一个弹性线程 —— 那是线程池饥饿，不是修法。要换线程的是「落库那一件事」，不是流本身。

**㊳ 不消费错误**（不用 `onErrorResume`/`onErrorReturn`）
那会改掉前端看到的东西，前端「从悬空行里捞 detail」的逻辑就失效了。

**㊴ 累加器放在 `Flux.defer()` 里，按每次订阅新建**
本服务只会订阅一次，但这一行代价换掉了「多路订阅共用一个缓冲区」这个隐患。

**㊵ 终态只有一个出口：`doFinally` + `AtomicBoolean.compareAndSet`**
完成/出错/取消会以不同时机到达，汇到一个出口才不会两条路都写终态；
`doFinally` 在边缘情况下可能触发不止一次，所以再加一道闸门。

**㊶ 终态落库必须换线程到 `Schedulers.boundedElastic()`**
`doFinally` 是在 **reactor-netty 事件循环**线程上触发的（chunk 由它投递，Spring 写 SSE 也在同一个
线程上干活）。在那里做阻塞 JDBC 会卡住**所有请求共用**的 IO 线程 —— 症状是「平时都好好的，
一并发就整体变慢」，最难查的那类。

**㊷ 终态落库整体 try/catch，只打日志**
一个抛异常的终态回调会把**已经成功返回给用户的回答**变成报错。反过来说，落库失败只配打一行日志。
`answer.toString()` 也放在那个任务里做 —— 在事件循环上拷 10 万字是没理由的开销。

**㊸ `classify` 的五档：`ON_COMPLETE`→DONE、`CANCEL`→CANCELED、
客户端断开→CANCELED、`ON_ERROR`+0 字→ERROR、`ON_ERROR`+有正文→INTERRUPTED**
和前端的五个状态逐条对齐。`INTERRUPTED` 与 `ERROR` 的分界是「有没有收到过内容」。
★ 这里的常量名是 `SignalType.CANCEL` 而不是老例子里的 `ON_CANCEL`（Reactor 3.8 改名了，见 ㊺）。

**㊹ `isClientAbort` 只认类名里有 `ClientAbort` 的异常，不把所有 IOException 当断开**
上游挂掉时读失败同样是 IOException，那种情况是 INTERRUPTED（收到一半被打断），
不是 CANCELED（用户主动停）。★ 一条**待实测**的事：客户端断开到底以 `CANCEL` 还是带
`ClientAbortException` 的 `ON_ERROR` 到达 —— 两种都处理了，验证方法是点一次「停止生成」，
看日志里「问答终态」那行的 signal 和异常类名。

**㊺ 顺手修了我自己写的两个编译错误**（都记在设计文档 §11）：
`ServiceImpl` 在 3.5.17 换了包（`...mybatisplus.spring.service.impl`）；
Reactor 3.8 去掉了 `SignalType.ON_CANCEL`（现在是 `CANCEL`）。

**㊻ `detailOf` 在 DONE / CANCELED 时返回空串而不是 null**
MP 不把 null 字段写进 UPDATE，写 null 等于「这列不动」——上一次残留的报错会永远挂在那行上。
清空只能靠空串。（和 ㊽ 是同一条规则的两处体现。）

**㊼ `safeWrite(what, key, action)`：所有落库调用统一出口，失败只记日志**
这是「落库是旁路」在代码里唯一需要记住的一条：**永远不要让落库的异常跑到调用方**。
尤其是上传那条路 —— 上游没有幂等键，我们自己的文档里就写着「客户端误判会导致同一文档入库两次」，
**一个 DB 抖动绝不能被翻译成 500，那会诱导用户重传**。

## 十、`IngestRecordService` —— 入库任务的落库（新增实现）

**㊽ `begin`：job_id 空就 warn 后直接返回，不写行**
`job_id` 是这张表**唯一的更新目标**，没有它的行以后永远找不回来（而前端本来也会把这次上传当失败）。

**㊾ `begin` 的 `fileName` 取上游回显优先、退回原始名；`originalFileName` 始终存原始名**
两个分开存是为了事后能回答「用户传的到底是哪个名字」（上游可能改名/去空格）。

**㊿ `begin` 只写「upload 那一刻已知的」，其余留 null**
stage/result/elapsedSec 要等轮询；`error` 留 null 就是「没问到」这个语义；时间戳交给数据库默认值。
上游已经 `done=true` 也**不特殊处理**：`FileUploadResp` 里没有 result，拿不到前缀就判不出终态，
而前端无论如何都会轮询至少一次 —— 第一次轮询会写出真相。

**51. `applyPoll` 分三种情况：没这行 → 兜底 INSERT；已终态 → 不写；否则更新**
兜底 INSERT 是「上传那次落库失败」和「应用中间重启过」的恢复路径 —— 正因为它存在，
上传那条路的一次落库失败才不至于让这个任务在库里彻底消失（前端还拿着 job_id 在轮询）。

**52. 兜底 INSERT 不写 `pollCount`，紧跟着的更新把它加到 1**
这样「这一轮只轮询了一次」这个事实正好等于 1，不需要为两条路径各写一套计数逻辑。

**53. ★ 终态只写一次靠的是 UPDATE 的 WHERE 里带 `status='INGESTING'`，不是靠先查一次**
先查再写是 check-then-act：两个页签同时轮询同一个 job 时，两边都可能查到「还在跑」，
后到的那次会把 SUCCESS 改写掉。写进 WHERE 里才是数据库层面的原子判断 ——
`update()` 返回 false 不是错误，是「有人先写了」。
（查那一次留着，是为了打日志说得清，以及区分「没这行」和「已终态」。）

**54. `poll_count = poll_count + 1` 用 `setSql` 让 SQL 自己加**
不能在 Java 里读出来 +1 再写回 —— 两个页签同时轮询会丢计数。

**55. ★ 更新走 `lambdaUpdate().set(...)`，它和 `updateById(补丁)` 的 null 语义正好相反**
`set()` 是**显式写列**（哪怕值是 null 也写进去），`updateById(补丁)` 会**跳过** null 字段。
两套语义都在这一个类里出现（那边是 `ChatRecordService`），改代码前先想清楚用的是哪一套 ——
类注释里专门写了这一条，因为搞反了会静默丢数据。

**56. `done != true` 时 `status` 那一列**不 set**，就是「不改」**
库里的 status 只记录上游说过的话；「轮询成功但还没结束」的实现方式就是不给它赋值。
看起来像漏了赋值，其实是刻意的。

**57. `result` 前缀 → 状态：`[成功]`/`[跳过]`/`[失败]` 各一档，其余（含空）→ UNKNOWN**
★ **认不出来绝不判 FAILED**：判错了用户会重传，而同一份文档入库两次是这个上游没有幂等键导致的
真实事故（`frontend/README.md` 里那条规则的数据库版）。

**58. 认不出前缀 / 说结束了却没给 result 时，把原因写进 `error`**
否则那行 UNKNOWN 以后没人看得懂（「上游说结束了但没给 result」「无法识别的 result 前缀：xxx」）。

**59. `markPollFailed`：没这行 → 什么都不做**
不能凭空造一行：一个我们从没受理过的 `job_id`，不该因为一次失败就在库里冒出来。

**60. `markPollFailed` 里 404 → UNKNOWN + 上游原话；其它 → status 不动 + 带「前端会重试」前缀**
见 ㉟。`e.getDetail()` 已经是 `RagApiException.fromUpstream` 翻好的中文，直接用 ——
**错误详情只能有一份实现**，这里绝不再自己解析一遍上游的 JSON。

**61. 每次轮询都更新 `lastPolledAt` 和 `pollCount`（成功失败都算）**
这两个列就是用来分「任务卡住了」和「页面早就关了」的（见 ㉖）。

**62. `job_id` 故意不截断**
截断一个键会写下一个和上游对不上的值，而它是唯一的对账线索 —— 超长就让那次写入报错
（日志里看得见），比写进一个假键好。这是 ⑫ 里没有 `MAX_JOB_ID_CHARS` 的原因。

**63. 终态时打一行 `log.info("入库任务终态: ...")`**
整个上传+轮询链路在日志里没有别的「一件事完成了」的标志，这一行是给你的锚点（每次入库只打一条）。

## 十一、`ChatRecordService` —— 问答记录的落库（新增实现）

**64. `beginExchange` 一个事务里做三件事：补会话行 → 插 user 行 → 插空的 assistant 行**
为什么必须在一个事务里：只有 user 行、没有 assistant 行，读起来像「模型无视了这个问题」，
是假象。
★ **事务边界：绝不把上游调用包进来** —— 上传可能传 100MB、问答是个可能几分钟的流，
一个事务横跨它们会长时间占住连接池里的连接。写库与调用严格前后排列、不嵌套。

**65. ★ 两行共用同一个 `LocalDateTime now`，各写一次 `now()` 是错的**
前端的语义里这两条消息是「同一条消息对」（共享 createdAt），差几毫秒就破坏了它；
而且一轮之内的先后本来就要靠 `id` 排、不能靠时间。

**66. 请求不合法（req 为 null / sessionId 空 / message 空）→ 返回 null 且什么都不写**
上游反正会 422 拒掉这次请求；留下一行「用户说了话、模型没理他」的记录比不留还坏。
`RagService` 拿到 null 就整条 tee 跳过，问答照常。

**67. user 行的 `status` 直接写 DONE**
提问本身没有流，写进去就是终态。这样「哪些提问没得到回答」用一句
`role='user' AND status <> 'DONE'` 就能查出来。

**68. assistant 行先以 `STREAMING` + `content=null` 建出来，结束时 UPDATE 它**
代价是每次问答多一次 UPDATE，换来两件事：进程被硬杀时能看见「这个提问的回答从没落下来」，
而且 `WHERE status='STREAMING' AND finished_at IS NULL` 是一句现成的「卡住的流」巡检 SQL。
只在结束时写会少一次写，但崩了就什么都没了。（这个取舍也解释了 ㉜ 那次开机清扫为什么存在。）

**69. 会话行按需创建（`ensureSession`），标题只填一次**
前端每次刷新页面/点「重新开始」都会 `newSessionId()`，会话短而多；多余的会话行只会是垃圾。
`title` 用第一句提问的前 30 字是列表页的省事近似 —— 真要做「自动起标题」是另一件事（会多一次上游调用）。

**70. `settle` 用 `updateById(补丁对象)` 而不是 chain update，只写五列**
content / charCount / status / error / finishedAt。补丁里为 null 的字段不进 SET 子句，
所以 `topK`、`created_at`、`session_id` 都不会被动。

**71. `error` 传 null 时强制写成空串**
`error == null ? "" : error` —— 见 ㊻：null 会被 MP 跳过，那样上一次残留的报错永远清不掉。

**72. `settle` 不做「只能改 STREAMING 行」的条件更新（和 53 相反）**
那边两个页签会并发轮询同一个 job，必须靠 WHERE 兜住；这边一次问答只有一条流、
`RagService` 用 `AtomicBoolean` 保证了终态只落一次，没有竞态要防。**两处的差异是有意的**。

**73. `settle` 不自己吞异常**
调用方把它丢在弹性线程池上、并整体 try/catch —— 那一层才有 `assistantId` 这个上下文，
日志打在那边更有用。这里只负责把 `updateById` 的结果记成 debug。

## 十三、已知边界与最该先验的几处

**没有实测过的（按怀疑程度排序）**：

1. **自动配置在 4.1.1 上到底认不认**。静态证据很硬（boot4 starter 里有新的
   `AutoConfiguration.imports`，且 `MybatisPlusAutoConfiguration` 引用的包名是
   `org.springframework.boot.**jdbc.autoconfigure**` = Boot 4 的布局），但没真启动过。
   先跑 `.\mvnw.cmd spring-boot:run "-Dspring-boot.run.arguments=--debug"` 搜 `MybatisPlusAutoConfiguration`。
2. **`@EnumValue` 有没有生效**（㉟）：`SELECT status FROM chat_message` 应该看到字符串而不是数字。
   这一条如果不成立，53 那个 `WHERE status='INGESTING'` 会**静默地匹配不到任何行**（更新报告 0 行），
   症状是「轮询日志有、库里 poll_count 不涨」。
3. **客户端断开以哪种形态到达**（㊹）：点一次「停止生成」，看「问答终态」那行的 signal / 异常类名。
4. **`category` 里的中文和时区**：`SELECT NOW(3)` 对比墙上时钟；`HEX(file_name)` 看是不是真 utf8mb4。

**结构上已知的两处边界（不是 bug，是有意的取舍）**：

- 一轮问答**必然有终态**这个不变量有一个极窄的缝：如果 `ragClient.aiChat(req)` 在 `Flux.defer`
  的 lambda 里**同步抛**（不是以 onError 信号返回），`doFinally` 就不会被挂上，那一行会停在
  `STREAMING`。查过 `RagClient.aiChat` 是纯 lazy 的 WebClient 链（请求在订阅时才发），
  构造期不抛 —— 所以这条路目前走不到。真走到了也有 ㉜ 的开机清扫兜底。
- 兜底 INSERT（51）有竞态：两个页签同时第一次轮询同一个 job，可能各插一次 → 唯一键冲突。
  写入被 `safeWrite` 包着，记一条日志，下一次轮询就正常更新了。**不加 `@Version`**：
  按上游响应做的写入是幂等的。

**明确没做的**（是选择，不是遗漏）：登录/注册/鉴权（只留列）、历史查询接口、前端任何改动、
文件字节落库或落盘、Flyway/Liquibase 迁移工具、分页/审计/逻辑删除、`user` 表的读写业务代码。
