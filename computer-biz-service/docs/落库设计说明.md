# 落库层（MyBatis-Plus + MySQL 8.4）实现说明

> 配套阅读：`db/schema.sql`（列注释本身就是文档）、`docs/rag对接实现说明.md`（上游对接那层）、
> `start.md`（启动命令）。

## 一、这一层做什么

把三样东西写进 MySQL，本轮**只写不读**，不碰前端：

| 写什么 | 表 | 时机 |
| --- | --- | --- |
| 演示用户 | `user` | 应用启动时补一行（id=1） |
| 上传的文件元数据 + 入库任务进度 | `ingest_task` | 上传被受理后 insert；每次轮询 update |
| 一问一答 | `chat_session` + `chat_message` | 提问进来时 insert；流结束时 update 终态 |

不做：登录/鉴权（只留列）、历史查询接口、文件字节落库或落盘、迁移工具（Flyway/Liquibase）、
分页/审计/逻辑删除。

**为什么要落库**：这三个接口原本什么都不存 —— 文件信息、任务进度、聊天记录只活在前端内存里，
刷新页面就没了（`chatStore` 的 `session_id` 甚至是刷新即换新的）。Java 侧一行持久化代码都没有。
上游 FastAPI 也不会把答案回传给我们，所以助手的正文**只能在这里攒**。

## 二、环境准备

### 2.1 MySQL 8.4 LTS

8.0 和 8.4 不能同时占 3306。旧数据不要就：MySQL Installer 里先 Remove Server 8.0，
再 Add → Server 8.4.x LTS，端口仍是 3306。装的时候设的 root 密码只给 Navicat 管理用，
**不给应用用**。

### 2.2 建库 + 建专用账号

见 `start.md` 的 ⓿。两个要点：

- `'computer_biz'@'localhost'` 和 `'computer_biz'@'127.0.0.1'` 在 MySQL 里是**两个不同的账号**，
  两个都建，省得出现「命令行能连、Navicat/JDBC 连不上」这种一半能通的怪问题。
- 密码**不进仓库**：`application.yaml` 里只有 `${DB_PASSWORD:}`，启动前在终端设环境变量。

### 2.3 两个认证插件相关的坑（8.4 上必踩其一）

MySQL 8.0 起默认认证插件是 `caching_sha2_password`，它带来两个独立的问题：

**① Navicat 报 `2059 Authentication plugin 'caching_sha2_password' cannot be loaded`**
（大致 15 及以前的版本不认）。按代价从小到大：升级 Navicat（推荐）；或把账号改成
`mysql_native_password` —— 但 **8.4 默认不加载这个插件**，直接 ALTER 会报
`Plugin 'mysql_native_password' is not loaded`（1524），要先在 `my.ini` 的 `[mysqld]` 加一行
`mysql_native_password=ON` 再重启服务。

> ⚠️ 不要用 `default_authentication_plugin=mysql_native_password`：**8.4 已经删掉了这个参数**，
> 写了**服务起不来**。

**② Java 侧报 `Public Key Retrieval is not allowed`**（这条最容易漏，因为它跟 Navicat 无关）。
`caching_sha2_password` 在不加密的连接上需要客户端能取服务端公钥，本机连接直接用 JDBC URL 参数解决：

```
sslMode=DISABLED&allowPublicKeyRetrieval=true
```

（Connector/J 9 里 `useSSL` 已过时，用 `sslMode`。本机 Connector/J 是 9.7.0。）

## 三、四张表

完整 DDL 和逐列注释在 `db/schema.sql`。这里只讲**取舍**——都是「为什么不那样做」比「是什么」值钱的地方：

| 取舍 | 决定 | 为什么 |
| --- | --- | --- |
| 入库任务是流水还是就地更新 | **一行一任务，随轮询更新** | 前端就是按 `job_id` 展示一张任务卡片。追加流水只会让我们以后再写一个聚合视图 |
| 状态列存什么 | **大写枚举名字符串**（`'DONE'`） | 不依赖 MP 的枚举处理器（行为随版本变过）；显式 `@EnumValue`。Navicat 里直接可读，存 `3` 得回头查代码 |
| `created_at` / `updated_at` | **交给数据库默认值** | Java 侧不写 `MetaObjectHandler`。可行的原因见第八节第 1 条 |
| 回合序号 `seq` | **不要** | 一问一答按 `id` 排就是回合顺序（主键单调自增）。`seq` 每次要 `SELECT MAX+1`，多一次读还多一个竞态 |
| `user_id` 外键 | **加** | 演示用户没建起来时写库会**当场报约束冲突**，而不是留下一堆悬空的 `user_id` 谁也发现不了 |
| `chat_message.session_id` 外键 | **不加** | 会话行和它的子行在**同一个事务**里创建，加了也只能抓我们自己的 bug，抓不到外部状态 |
| `original_file_name` | **加**（与 `file_name` 并存） | 上游会把文件名改名/清空格后回显。`file_name` 存上游回显（用户看到的），`original_file_name` 存用户真正传的（事后考古要的） |
| `poll_count` | **加** | 「任务卡住了」和「页面早就关了」在库里长得一样，只有轮询次数能分开 |
| `session_id` 加 FK 到会话表？ | 不加，只建普通索引 | 同上 |
| 时间列类型 | `DATETIME(3)` 不用 `TIMESTAMP` | `TIMESTAMP` 每次读写都过一遍会话时区，还有 2038 问题；`DATETIME` + `LocalDateTime` 两边都不转换 |
| 表名 `user` | 复用这个关键字名 | MySQL 里 `user` 是关键字但**非保留字**，`FROM user` 合法；我们的语句都由 MP 加反引号 |

### 3.1 同一轮问答的两行共享 `created_at`

`chat_message` 里，一轮问答的 user 行和 assistant 行用**同一个 `created_at` 值**（对齐前端
「两条消息共享 `createdAt`」的语义）。所以**一轮内的先后只能靠 `id` 排，不能靠时间**。
这也是本层唯一需要 `@Transactional` 的地方（下一节）。

## 四、依赖与配置

### 4.1 依赖（`pom.xml`）

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-spring-boot4-starter</artifactId>
    <version>3.5.17</version>
</dependency>
```

**必须是 boot4 那个 starter**，boot3 版是给 Boot 3 用的，用错了会以一堆 `NoClassDefFoundError` 收场。
实测的传递依赖（`mvn dependency:tree`）：

```
com.baomidou:mybatis-plus-spring-boot4-starter:3.5.17
├─ com.baomidou:mybatis-plus:3.5.17
│  ├─ mybatis-plus-core / mybatis-plus-annotation
│  ├─ mybatis-plus-spring:3.5.17 ── mybatis-plus-extension:3.5.17
│  └─ org.mybatis:mybatis:3.5.19
├─ org.mybatis:mybatis-spring:4.0.0        ← 对齐 Boot 4 的那个版本
├─ mybatis-plus-spring-boot-autoconfigure + -native-image
└─ org.springframework.boot:spring-boot-starter-jdbc:4.1.1 ── spring-jdbc:7.0.9
com.mysql:mysql-connector-j:9.7.0 (runtime)
```

`spring-boot-starter-jdbc` 是传递进来的，所以 HikariCP 不用单独加。

### 4.2 自动配置在 Boot 4 上到底认不认（本轮最大的未知数，已静态验证）

Boot 4 把 autoconfigure 拆了模块、挪了包名（`...autoconfigure.jdbc.*` → `...jdbc.autoconfigure.*`），
而 MP 3.5.17 是照 `spring-boot-dependencies:4.0.1` 编的，本项目是 4.1.1。**已经确认没问题**，证据两条：

1. `mybatis-plus-spring-boot4-starter-3.5.17.jar` 里有
   `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
   （新格式，Boot 3+ 才读；只有老格式 `spring.factories` 的 jar 在 Boot 4 上**什么都加载不了**），
   内容列了 5 个自动配置类，其中就有 `MybatisPlusAutoConfiguration`。
2. `MybatisPlusAutoConfiguration.class` 里引用的包名是
   `org/springframework/boot/**jdbc/autoconfigure**/DataSourceAutoConfiguration`
   —— **Boot 4 的包名**，不是 Boot 3 的 `autoconfigure/jdbc/`。

设计上还挺巧：boot4 starter 的 jar 里**只**装了 `MybatisPlusAutoConfiguration`，
其余四个类仍在共享的 `mybatis-plus-spring-boot-autoconfigure` 里 —— 也就是「只重编了需要改的那一个」。
两个 jar 没有重复类，不会打架。

启动时想再确认一次，用 `.\mvnw.cmd spring-boot:run "-Dspring-boot.run.arguments=--debug"`，
在条件报告里搜 `MybatisPlusAutoConfiguration`，应该显示 `matched`。

### 4.3 配置（`application.yaml`）

见文件里的注释，四条关键的：

- `map-underscore-to-camel-case: true` —— MP 默认就是 true（和裸 MyBatis 相反），显式写出来，
  **绝不能改成 false**：`file_name → fileName` 全靠它，关掉会得到一堆 null。
- `log-impl: Slf4jImpl` —— SQL 日志走 logback，而不是 StdOutImpl（后者是 `System.out`，
  绕过所有日志配置、没有时间戳、没法按环境关掉）。
- `id-type: auto` —— MySQL 自增，不用 MP 默认的雪花。
- `hikari.connection-timeout: 3000` —— 默认 30 秒时，库挂了会让 Tomcat 线程被扣住 30 秒，
  而前端 axios 超时只有 15 秒，结果是**前端先超时、你在日志里什么都看不到**。

## 五、三处写入钩子

都在 `service/RagService`（它本来就是唯一的编排层）。

### 5.1 上传被受理后

```java
FileUploadResp resp = ragClient.upload(file, extra);   // 先调上游，拿 job_id
ingestRecordService.begin(resp, file);                 // 再落库
```

顺序不能反：`job_id` 是上游给的，调之前拿不到；上游失败会直接抛给前端，也就没有「任务」可记。
起点只有 `job_id`、文件名、大小、MIME —— 终态此时**还未知**（入库是 FastAPI 后台异步干的），
所以 `status` 初值是 `INGESTING`。

### 5.2 每次轮询

```java
try {
    resp = ragClient.queryTask(jobId);
} catch (RagApiException e) {
    ingestRecordService.markPollFailed(jobId, e);      // 只记 error，不动 status
    throw e;                                           // ★ 原样抛给前端
}
ingestRecordService.applyPoll(resp);
```

**★ 轮询失败 ≠ 入库失败**（前端 README 里那条最关键规则的数据库版）。网络抖动 / 502 / 上游 4xx /
404（上游只保留最近一个任务）时，**只写 `error` 文案，不改 `status`**。理由：数据库里的 `status`
只能代表「上游说过什么」，Java 这边没问到的东西写进 `error` 才不撒谎。反过来说，`status` 会停在
上次上游说过的那一档，配合 `error` 和 `last_polled_at` 才读得懂。

（另一条路是跟着前端一起标 `UNKNOWN`，没选：前端那个 `UNKNOWN` 是**客户端显示态**，
让数据库跟着 UI 走，以后做读接口时会分不清「上游说未知」和「我们没问到」。）

例外是 404：上游明确回答「这个任务不存在」了，那是一次**成功的询问**，所以写 `UNKNOWN`。
详见 `IngestRecordService` 的类注释。

每次轮询实际动的列（成功那一支）：

| 列 | 值 | 备注 |
| --- | --- | --- |
| `stage` / `elapsed_sec` | 上游回显 | 每次覆盖，只留最后一次 —— 它们描述的是「当前状态」不是历史 |
| `error` | 空串 | ★ 用来**抹掉上一次的报错**。空串不是 null：null 会被 MP 跳过，抹不掉 |
| `poll_count` | `poll_count + 1`（`setSql`，SQL 里自增） | 不能在 Java 里读出来 +1 再写回，两个页签会丢计数 |
| `last_polled_at` | Java 侧 `now()` | 失败那一支也更新（它是「我们问过」的证据） |
| `status` / `result` | 只在 `done=true` 时写 | `done != true` 时**不给这两列赋值** = 不改，看起来像漏了赋值，是刻意的 |

**★ 终态只写一次靠的是 UPDATE 的 `WHERE status='INGESTING'`**，不是靠先查一次：
先查再写是 check-then-act，两个页签同时轮询同一个 job 时后到的那次会把 `SUCCESS` 改写掉；
写进 WHERE 里才是数据库层面的原子判断（`update()` 返回 false 不是错误，是「有人先写了」）。
查那一次留着，是为了打日志说得清、以及区分「没这行」和「已终态」。
同理，没查到行时**兜底 INSERT 一行**（上传那次落库失败、或应用中间重启过），
这是唯一能让「一次落库失败不至于让任务在库里彻底消失」的路径。

### 5.3 问答（本轮唯一的难点）

```java
// ① 提问：在请求线程上、响应开始之前同步写（一个事务：会话行 + 两行消息）
Long assistantId = chatRecordService.beginExchange(req, AppConstants.DEFAULT_USER_ID);
if (assistantId == null) return ragClient.aiChat(req);      // 落库失败 → 原样放行

// ② 攒回答：只用副作用算子，对流透明
return Flux.defer(() -> {
    ...
    return ragClient.aiChat(req)
        .doOnNext(piece -> 攒进 StringBuilder)     // 纯内存，不做 IO
        .doOnError(failure::set)                   // 只记录，不消费
        .doFinally(sig -> 只落一次终态);
});
```

每一处的代价都很具体：

- **提问为什么在订阅之前写**：那时响应还没开始，写库失败能被抓住记日志；而且**上游挂掉的那次提问
  也留下了痕迹**。放进 `Flux.defer()` 里写的话，落库就成了流的一部分 —— DB 一抖会把用户的回答带崩。
- **为什么只用 `doOnNext` / `doOnError` / `doFinally`**：这类副作用算子对流的背压、缓冲、线程都透明。
  **不用 `publishOn`** —— 那会在上游和 Spring 的写入器之间插一次调度跳转，而且
  `publishOn(boundedElastic)` 会为整个回答（可能几分钟）**长期占住**一个弹性线程，那是线程池饥饿，
  不是修法。要换线程的是「落库那一件事」，不是流本身。
- **为什么不消费错误**：`onErrorResume` / `onErrorReturn` 会改掉前端看到的东西，
  前端那套「从悬空行里捞 detail」的逻辑就失效了。
- **终态为什么要换线程**：`doFinally` 是在 **reactor-netty 事件循环**线程上触发的
  （chunk 由事件循环投递，Spring 写 SSE 也在同一个线程上干活）。在那里做阻塞 JDBC 会卡住
  **所有请求共用**的 IO 线程 —— 症状是「平时都好好的，一并发就整体变慢」，最难查的那类。
  所以统一 `Schedulers.boundedElastic().schedule(...)`。
- **终态为什么要吞异常**：一个抛异常的终态回调会把**已经成功返回给用户的回答**变成报错。
- **为什么要一个开关**：`doFinally` 在边缘情况下可能触发不止一次，用
  `AtomicBoolean.compareAndSet` 兜住，只落一次库。
- **助手行为什么先建后改**：`beginExchange` 里先插一行 `status=STREAMING, content=NULL` 拿到 id，
  结束时 UPDATE 它。代价是每次问答多一次 UPDATE，换来的是：进程被硬杀时能看见「这个提问的回答
  从没落下来」，而且下面这句就是现成的巡检 SQL。只在结束时写会少一次写，但崩了就什么都没了。

  ```sql
  SELECT id, session_id, created_at FROM chat_message
  WHERE status='STREAMING' AND finished_at IS NULL;
  ```

- **存的是上游原始流文本**，和用户屏幕上看到的**未必一致**（前端 `parseChatChunk` 会丢掉它不认识的
  JSON 帧，比如 `{"sources":[...]}`）。在 Java 侧再实现一遍那个过滤 = 制造**第二份前端契约**，
  正是这个项目一贯拒绝的事（错误翻译「只能有一份实现」同理）。所以照原样存，差异写进列注释。
  哪天真要过滤，是加一列存「解析后的」，不是覆盖原始列。
- **正文长度上限**（`MAX_STORED_ANSWER_CHARS`，10 万字符）：不是给正常回答用的，是防「上游挂在那儿
  一直推」把内存和列宽推爆。超出的部分不再攒，**但流本身照常转发** —— 落库是旁路，这条在这里体现得
  最直接。

## 六、状态映射

**数据库存大写枚举名，前端用小写**。不是笔误，是各自的命名习惯。

### 6.1 入库任务（`ingest_task.status`）

前端 `ingestStore.STATUS` 里的 `queued` / `uploading` / `committing` 是**纯客户端状态**，
服务端永远看不到，所以库里只有这五个：

| 前端 `STATUS` | 库里 `ingest_task.status` | 何时写 |
| --- | --- | --- |
| `ingesting` | `INGESTING` | 上传受理时；`done != true` 的每次轮询 |
| `success` | `SUCCESS` | `done = true` 且 `result` 以 `[成功]` 开头 |
| `skipped` | `SKIPPED` | `done = true` 且 `result` 以 `[跳过]` 开头 |
| `failed` | `FAILED` | `done = true` 且 `result` 以 `[失败]` 开头 |
| `unknown` | `UNKNOWN` | `done = true` 但前缀不认识（**不给它扣「失败」的帽子**），或轮询时上游 404 |

★ **前缀认不出来时绝不能判 `FAILED`**：判错了用户会重传，而同一份文档入库两次是这个上游
没有幂等键导致的真实事故。

### 6.2 问答（`chat_message.status`）

| 流的结束方式 | 落库 `status` | 前端对应 |
| --- | --- | --- |
| `ON_COMPLETE` | `DONE` | `done` |
| `CANCEL`（订阅被取消） | `CANCELED` | `canceled` |
| `ON_ERROR` + 异常是客户端断开（`ClientAbort*`） | `CANCELED` | `canceled` |
| `ON_ERROR` + 一个字都没收到 | `ERROR` | `error` |
| `ON_ERROR` + 收到过内容 | `INTERRUPTED` | `interrupted` |

- **取消时 `content` 里有半截回答，这是这个设计最重要的产物**：前端刷新就丢的东西，只有这里留得住。
- `INTERRUPTED` 与 `ERROR` 分开：已经有正文才出错 = 回答被从中间切断；一个字都没有 = 压根没收到。
- ★ 客户端断开到底以哪种形态到达（`CANCEL` 还是带着 Tomcat `ClientAbortException` 的 `ON_ERROR`）
  两种都处理了，但**本地还没实测过**。验证方法是前端点一次「停止生成」，看日志里那行
  「问答终态」打的 signal 和异常类名。

## 七、一条贯穿的设计原则：落库是旁路

主链路是「浏览器 → Java → FastAPI」，落库挂在旁边。

- **启动期：缺库要吵。** 库不存在 / 密码不对 / MySQL 没起来 → 启动直接失败，日志里就是答案。
  这正是想要的：让接线问题在最早、最安静的时刻暴露。
- **运行期：写库失败要静音。** 所有落库调用都走 `RagService.safeWrite` 或 `settleAsync` 里的 try/catch，
  失败**只打日志**（带业务键，方便去库里对账）。尤其是上传那条路：上游没有幂等键，我们自己的文档里
  就写着「客户端误判会导致同一文档入库两次」—— **一个 DB 抖动绝不能被翻译成 500，那会诱导用户重传。**

## 八、三条机械规则（会反复用到）

1. **★ MyBatis-Plus 默认的字段策略是 `NOT_NULL`：值为 null 的字段不会出现在 INSERT/UPDATE 语句里。**
   三条推论，两条正好被我们用上，一条必须绕开：
   - *用上*：轮询时只 `set` 变化的那几个字段，别的列不会被 null 覆盖掉。
   - *用上*：「轮询失败不改 status」的实现方式就是**不给 `status` 赋值** —— 它压根不进 `SET` 子句，
     原值自然保留。这行代码看起来像漏了赋值，**代码里必须写注释**，否则下一个人会热心地补上。
   - **绕开**：既然是 null 不进语句，那就**没法用 null 清空一列**。所以「这次轮询成功了，把上次残留的
     错误文案抹掉」只能写 `error = ""`，写 null 什么都不发生 —— 一行成功的任务会永远挂着一句过期的报错。
     这条在 `db/schema.sql`、`IngestTask` 的注释、`IngestRecordService` 的行为清单里各写了一遍，
     因为它后果隐蔽、症状离原因远。
   - 附带好处：时间列交给数据库默认值就够了（Java 侧不用给 `createdAt` 赋值），少一个
     `MetaObjectHandler` 类 + 少一处配置。代价是「Java 对象里拿不到刚写入的时间」——本轮只写不读，无所谓。
2. **★ 所有写库的字符串都要先截断。** MySQL 8.4 跑在 strict 模式下，超长**不截断而是报错**
   `Data too long for column 'xxx'`。而轮询那条路上的异常会发生在「必须保持健康」的请求里。
   所以 `util/TextUtils.truncate(s, maxChars)`，列宽常量都在 `common/AppConstants`（按**字符**算，
   正好是 `VARCHAR(n)` 的口径）。
3. **★ 事务绝不跨一次 HTTP 调用，也绝不跨一条流。** `upload` 可能传 100MB、`aiChat` 的流可能几分钟。
   写库与调用严格前后排列、不嵌套。单条 insert/update 不需要事务（那只会多绑一次连接、多一次提交往返）。

## 九、启动自检与僵尸流清扫

`common/PersistenceStartupCheck`（`ApplicationRunner`）干三件事，顺序就是它们的依赖顺序：

| 步骤 | 怎么做的 | 它证明了什么 | 失败了怎么办 |
| --- | --- | --- | --- |
| ① 连接 | `JdbcTemplate` 查 `SELECT VERSION()` | 池 + 账号 + 库名 OK。**完全不碰 MyBatis** | **抛，启动失败**（库不在/密码错就该起不来） |
| ② ORM | `userMapper.selectById(1)` | mapper 扫描 + 语句生成 + 下划线转驼峰，整条路通 | 查询炸了 → **抛**（见下）；只是查不到 → 补写，补写失败 → **只打 ERROR** |
| ③ 补写演示用户 + 清扫僵尸流 | `insert` / `UPDATE ... WHERE status='STREAMING'` | 见下 | **只打 ERROR**，服务照常起 |

**①打印了、②炸了 ⇒ 是 MyBatis 的接线问题，不是 MySQL 的问题** —— 这一句能省掉半小时。

② 这里有个需要说清楚的分界，因为它同时是「诊断」和「业务」：

- **查询本身就炸**（表不存在 / 列名对不上 / 权限不够）→ 让它抛，启动失败。这最常见的原因就是
  「忘了跑 `db/schema.sql`」—— 那时候起不来才是对的，也是上面那句话能成立的前提。
- **查到了「没有这个用户」，但补写失败** → 吞掉只打 ERROR。说明表和接线都是好的，坏的只是这一次写；
  服务照常起来，问答和上传都能用（只是落库会撞 `user_id` 外键写不进去）。这就是「落库是旁路」。

③ 的僵尸流清扫：一条流不可能活过一次进程重启，所以开机时任何 `STREAMING` 行**必然**是
「答案没落下来」的残骸。这就是助手行「先建后改」那笔多出来的写换来的东西 —— 崩了也看得出
哪条回答没落下来，而不是让它永远挂在 `STREAMING` 上，和「正在生成」混在一起分不清。
清扫失败也不拦启动：那是一次维护，不是服务能干活的前提（和 ① 正相反）。

> 注意这条语句是**破坏性**的，所以 `src/test/resources/application.yaml` 让测试连另一个库
> （`computer_biz_test`）：对着开发库跑测试会把正在生成的流误判成僵尸。

演示用户**不在** `db/schema.sql` 里，由代码在启动时补 —— 它是「服务端替用户声明」的运行期约束，
属于代码；附带好处是手工建库时少一条要记得执行的语句。找不到时**不中断启动**：
问答和上传本身还能用（只是落库会撞 `user_id` 外键而写不进去，每次打 ERROR 日志）。
这时候一个能跑的服务比一个起不来的服务有用。

## 十一、这个版本（3.5.17 / Reactor 3.8.7）上的三个坑

抄网上例子最容易中的三个，都已经踩过了，记在这里免得再找：

1. **`ServiceImpl` 的包名变了。** 老路径
   `com.baomidou.mybatisplus.extension.service.impl.ServiceImpl` 在 3.5.17 里**是空的**，
   直接抄会报「程序包不存在」。现在在
   `com.baomidou.mybatisplus.spring.service.impl.ServiceImpl`，继承链是
   `ServiceImpl → CrudRepository → AbstractRepository`，方法体大部分在 `mybatis-plus-extension`
   的 `...extension.repository.IRepository` 上。**可用方法没变**：
   `save / saveOrUpdate / updateById / update / getById / getOne / list / count / remove* /
   lambdaQuery / lambdaUpdate` 都在；`baseMapper` 仍是 `CrudRepository` 上的 `@Autowired` 字段。
2. **Reactor 里 `SignalType.ON_CANCEL` 已经没了**，现在叫 **`CANCEL`**（3.8.7 实测）。
   抄老例子写 `ON_CANCEL` 编译不过。
3. **不要给 JDBC URL 加 `useAffectedRows=true`。** Connector/J 默认（false）让 UPDATE 返回**匹配**
   行数，正好够「这行到底在不在」的判断；改成 true 后，每次「什么都没变的轮询」都会长成「行不见了」，
   把兜底 INSERT 撞到唯一键上。

顺带两条别踩的：**别用 MP 的 `JacksonTypeHandler` 存 JSON 列**（3.5.17 里确实有
`Jackson3TypeHandler` 了，但要确认它绑的是 Jackson 3 —— 本项目已经是 `tools.jackson`）；
**实体上别加 `@Builder` / `@AllArgsConstructor`**（MyBatis 靠无参构造 + setter 实例化，
加了全参构造就没了默认构造，症状是「查出来的对象字段全是 null」）。
以后加分页（`PaginationInnerInterceptor`）时，MP 3.5.9+ 把 JSqlParser 拆出去了，
必须同时加 `mybatis-plus-jsqlparser`，否则 `ClassNotFoundException`。
