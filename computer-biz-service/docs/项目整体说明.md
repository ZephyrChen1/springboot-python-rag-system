# 项目整体说明（包结构与依赖关系）

> 读这份文档的目标：合上之后你能在白板上画出三层架构、说出 Java 侧每个包的职责、
> 以及「为什么某个类放在这个包而不是那个包」。
>
> 只讲 Java 侧。Python 服务一句话带过（§9）、前端只列目录（§8），
> 这两块各有专门文档：`前端工程说明.md`、`rag对接实现说明.md`。

---

## 1. 这个项目是什么

**企业知识库 + 大模型问答平台**：用户上传文档 → 后台异步入库（切片、向量化、抽实体关系）→
然后基于知识库做流式问答（RAG 检索增强生成），答案逐字吐出来。

三个进程，Java 在中间当 BFF（Backend For Frontend）：

```
浏览器 (React 18 + Vite, :5173)
      │  /api/rag/*
      ▼
Java BFF (Spring Boot 4, :8080)          ← 本文档的主角
      │  /ai/chat  /v1/kb/*
      ▼
Python RAG 服务 (FastAPI + LightRAG, :8102)
      │
      ├── MySQL 8.4  (:3306)   业务数据（用户/任务/会话/消息）
      └── Qdrant     (:6333)   向量库（知识库索引，Java 不直接碰）
```

**Java 这一层存在的理由**（不是多余的中转）：

1. **协议适配**——上游流式响应是非标准 SSE（裸文本），前端 `EventSource` 吃不下，
   需要一层把字节流翻译成前端能用的分帧格式；
2. **数据落库**——上游不留痕（答案只流一次、job 只保留最近一个），业务记录只能在这一层攒；
3. **统一错误契约**——把上游的 422 校验错误、404、502 都翻译成前端认识的 `{"detail":"..."}`；
4. **对前端隐藏上游**——前端只认 `/api/rag/*`，上游换端口/换实现不影响前端。

## 2. 技术栈

| 层 | 技术 | 备注 |
|---|---|---|
| 前端 | React 18 + Vite | :5173；无 UI 框架，手写 CSS |
| BFF | **Spring Boot 4.1.1**、Java 21 | 注意 Boot 4 的坑，见 §7 |
| Web | Spring MVC（servlet，Tomcat）+ **WebFlux 的 WebClient** | 同一个应用里混用：MVC 当服务端，WebClient 当流式客户端 |
| ORM | **MyBatis-Plus 3.5.17**（`mybatis-plus-spring-boot4-starter`） | 版本必须对上 Boot 4 |
| 数据库 | MySQL 8.4（严格模式） | utf8mb4 / InnoDB |
| 上游 | FastAPI + LightRAG + Qdrant + DashScope Qwen | 向量库、LLM 都在 Python 侧 |

> **一个容易看不懂的点**：`pom.xml` 里同时有 `starter-webmvc` 和 `starter-webflux`，
> 但这是个**servlet 应用**。WebFlux 在这里只用来提供 `WebClient`（流式 HTTP 客户端），
> 不是用来当服务端的——WebFlux 的服务端自动配置被
> `@ConditionalOnWebApplication(REACTIVE)` 挡住了，不会生效。

## 4. 每个包的职责

### ① `controller/` —— 接口入口

| 类 | 职责 |
|---|---|
| `RagController` | 三个接口，把 HTTP 参数交给 `RagService`，把返回值交给 Spring 序列化 |

暴露给前端的三个接口都在 `/api/rag` 前缀下（`@RequestMapping("/api/rag")`）：

| 方法 | 路径 | 入参 | 返回 |
|---|---|---|---|
| `upload` | `POST /api/rag/documents` | `multipart/form-data`（文件 + `FileUploadReq`） | `FileUploadResp`（含 job_id） |
| `queryTask` | `GET /api/rag/tasks/{jobId}` | 路径变量 | `TaskQueryResp` |
| `aiChat` | `POST /api/rag/chat` | `AiChatReq`（JSON） | `Flux<String>`（SSE 流） |

**三个值得注意的设计**：

- **这里的路径 `/api/rag/*` 和上游 FastAPI 的 `/ai/chat`、`/v1/kb/*` 是两套独立命名**——
  故意不一样，Java 可以自由重组 API 形状，不用跟着上游改（`RagController:16` 的注释写了这点）。
- **controller 里没有任何业务逻辑**——不查库、不调上游、不判状态。它薄到只剩三行转发。
  这是分层的意义：业务规则集中在 `service`，改起来只有一个地方。
- **`aiChat` 返回的是 `Flux<String>` 而不是 `ResponseEntity`**——Spring MVC 认识 Reactor 类型，
  会自动接上异步流式写回（`produces = TEXT_EVENT_STREAM_VALUE`）。**这是全项目唯一一个
  「响应式类型跨出 service 层」的地方**。

### ② `service/` —— 业务编排（项目的中枢）

这个包是**整个项目的重心**，三个类分工明确：

**`RagService` —— 主链路编排 + 落库的总闸门**

它是唯一同时持有 `RagClient` 和两个 record service 的类，也就是唯一知道「一次业务操作
要按什么顺序做哪些事」的地方：

- `upload()`：先调上游拿 job_id → 再落库（**顺序不能反**，job_id 是落库的前提）
- `queryTask()`：调上游 → 成功则 `applyPoll` 落库，失败则 `markPollFailed` 落库后**原样再抛**
- `aiChat()`：提问先同步落库 → 把上游流 `doOnNext` 攒正文 → 终态 `doFinally` 落库

它身上有三个贯穿全项目的**设计原则**，都写在这个类的注释里：

| 原则 | 含义 |
|---|---|
| **落库是旁路** | 运行期写库失败一律吞成日志（`safeWrite`），绝不能让 DB 抖动变成用户看到的 500 |
| **不消费错误** | 不用 `onErrorResume`/`onErrorReturn`，错误要原样留给前端那套「从悬空行捞 detail」的逻辑 |
| **副作用算子要透明** | 只用 `doOnNext`/`doFinally` 这类不改背压的算子，**不用 `publishOn`**（会长占弹性线程） |

另外它有一个 `classify()` 方法把「流的结束方式」翻译成落库状态（五档），
以及 `settleAsync()` 把阻塞的 JDBC 甩到 `boundedElastic`（**不能在 reactor-netty 事件循环上做阻塞 IO**）。

**`IngestRecordService` / `ChatRecordService` —— 两个落库服务**

它们**只负责写库，不含业务判断的入口**（谁调用、什么时候调用由 `RagService` 决定）：

| | `IngestRecordService` | `ChatRecordService` |
|---|---|---|
| 对应表 | `ingest_task`（一行一任务，**就地更新**） | `chat_session` + `chat_message`（**追加**） |
| 写入时机 | 三个：`begin`（受理）/ `applyPoll`（轮询）/ `markPollFailed`（轮询失败） | 两个：`beginExchange`（流的开头）/ `settle`（流的终态） |
| 并发防线的关键 | `WHERE status='INGESTING'` 写进 UPDATE → **终态只写一次** | 无（一次问答只有一条流，`AtomicBoolean` 已够） |
| 为什么这样 | 两个页签会**并发轮询同一个 job**，必须靠数据库原子判断 | **无竞态**，条件更新是多余的 |

两个类都 `extends ServiceImpl<Mapper, 实体>`——这样不用自己注入 mapper 就能拿到
`save / updateById / lambdaQuery / lambdaUpdate`。
⚠️ **包名是 `com.baomidou.mybatisplus.spring.service.impl.ServiceImpl`**，
3.5.17 重构过，网上教程写的 `extension.service.impl` 在这个版本里是空的。

两个类里各写了一大段「自己怎么验」的 SQL，改这两个类之前先读那两段。

### ③ `client/` —— 上游调用（只做协议转换）

| 类 | 职责 |
|---|---|
| `RagClient` | 一个方法对应一个上游接口，只做「拼请求 + 反序列化」。**业务规则（重试、轮询、落库）不放这里** |

三个方法，两个 HTTP 客户端：

| 方法 | 客户端 | 上游路径 | 特点 |
|---|---|---|---|
| `upload` | `RestClient`（同步） | `POST /v1/kb/upload` | 表单上传，直接 `retrieve().body(...)` |
| `queryTask` | `RestClient`（同步） | `GET /v1/kb/ingest/{jobId}` | 同上 |
| `aiChat` | **`WebClient`（流式）** | `POST /ai/chat` | 返回 `Flux<String>`，见下面 |

**为什么问答必须用另一个客户端**：Spring 的 `RestClient` 是同步阻塞的，拿不到「流」；
要流式读必须用 WebClient（响应式栈）。这就是 `pom.xml` 里那个 WebFlux 依赖的唯一用途。

`aiChat` 里最重的是 `decodeRawText()` ——**自研的字节流解码器**，
绕开 Spring 的 SSE 解析器、自己处理 UTF-8 汉字跨块截断。
这一块是简历亮点①，单独一份文档：**`流式问答链路详解.md`**。

### ④ `config/` —— Bean 装配

| 类 | 职责 |
|---|---|
| `RagClientProperties` | `@ConfigurationProperties(prefix="rag")`，把 yaml 里的 `rag.base-url` 绑成对象 |
| `RagClientConfig` | 提供两个 Bean：`ragRestClient`、`ragWebClient` |

**`RagClientConfig` 里最重要的一行差异**：

```
ragRestClient  →  有 defaultStatusHandler（任何非 2xx 自动抛 RagApiException）
ragWebClient   →  故意没有（流式请求不能用它，会把连接掐掉）
```

所以流式那条路的错误映射写在 `RagClient.aiChat` 的 `exchangeToFlux` 里，
但**复用同一个 `RagApiException.fromUpstream`**——保证两条路的错误翻译只有一份实现。

### ⑤ `dto/` —— 对外数据形状

DTO 是**纯数据**：只有字段 + 注解，没有逻辑、不依赖任何业务包。

```
dto/
├── request/rag/         进 Java 的（前端发来的）
│   ├── AiChatReq            问答请求；★ 类上 @JsonInclude(NON_NULL) 是必需的（见下）
│   ├── FileUploadReq        上传的额外文本参数 —— 目前是**空类**（占位，留着以后加 kbId）
│   └── TaskQueryReq         ★ **未被使用**（controller 用的是 @PathVariable，不是请求体）
└── response/            出 Java 的
    ├── ApiErrorResp         {"detail":"..."} —— 全局错误体，对齐 FastAPI 的形状
    └── rag/
        ├── FileUploadResp   上游 upload 的返回（job_id / file_name / done）
        ├── TaskQueryResp    上游轮询的返回（+ result / stage / elapsed_sec）
        └── AiChatResp       ★ **空类，未被使用**（问答直接返回 Flux<String>）
```

**为什么是两套 DTO 而不是直接复用上游的**：Java 的 `/api/rag/*` 契约和上游契约是**独立**的。
比如前端传 `user_id` 是我们自己决定忽略的（见 §5 安全那条），上游契约变了也不该直接漏给前端。

**`AiChatReq` 上 @JsonInclude(NON_NULL) 的坑**（面试/排错都用得上）：
Jackson 默认把 null 字段也序列化出去，而 FastAPI 的 `user_id: int = 0` 是**非 Optional 的 int**，
收到显式 `null` 直接 422。**「字段缺失 = 用上游默认值」**，所以空值必须整个不发。
`topK` 用包装类型 `Integer` 而不是 `int` 是同一个理由（基本类型会发出 `top_k: 0`，范围校验过不去）。

### ⑥ `entity/` —— 数据库表映射

四个类对应四张表，字段与列一一对应（`map-underscore-to-camel-case: true` 负责 `file_name` ↔ `fileName`）。

| 实体 | 表 | 一句话 |
|---|---|---|
| `User` | `user` | 只有一条演示数据（id=1），**没有登录** |
| `IngestTask` | `ingest_task` | 一行一入库任务，随轮询**就地更新** |
| `ChatSession` | `chat_session` | 会话，按需创建（该 session 第一次提问时插一行） |
| `ChatMessage` | `chat_message` | 一次问答**两行**（user + assistant） |

**`User` 的类注释是全项目的重灾区警告，两个 Lombok/MP 的坑**：

1. **不要加 `@Builder` / `@AllArgsConstructor`**——MyBatis 靠「无参构造 + setter」把结果集
   变成对象，加了全参构造就没有默认构造了。症状是「查出来的对象字段全是 null」**且不报任何错**。
   四个实体都重复写了这句警告。
2. **时间列不加 `@TableField(fill=...)`**——值交给数据库的 `DEFAULT CURRENT_TIMESTAMP(3)`。
   可行的原因是 **MP 默认字段策略是 NOT_NULL：值为 null 的字段压根不进 INSERT 语句**，
   数据库默认值才有机会生效。

> **`entity` 不出 service 层**：`password_hash` 这类字段一旦被序列化出去就是事故。
> 将来要返回给前端的形状放 `vo/`（那个包现在还是空的，就是留给它的）。

### ⑦ `mapper/` —— 数据库访问

四个接口**全是空的**：

```java
public interface UserMapper extends BaseMapper<User> { }
```

**空接口是故意的**，不是没写完：`BaseMapper` 已经把这轮要用的增删改查全给了
（`insert` / `updateById` / `selectById` / `selectOne`…），单表 DML 一行都不用手写。

两个约定：

- **接口上不写 `@Mapper`**——扫描在启动类上用 `@MapperScan("org.example.computerbizservice.mapper")`
  统一做。两条路都走 = 同一个 mapper 注册两次。
- **要加方法时再写**——加一条方法通常意味着「单表表达式不够用了」。

### ⑧ `common/` —— 常量、枚举、启动自检

| 类 | 职责 |
|---|---|
| `AppConstants` | 落库常量：`DEFAULT_USER_ID`、回答最大字符数、各列宽上限 |
| `PersistenceStartupCheck` | 启动自检（`ApplicationRunner`） |
| `enums/IngestStatus` | 入库任务状态（5 值：INGESTING/SUCCESS/SKIPPED/FAILED/UNKNOWN） |
| `enums/ChatMsgStatus` | 消息状态（5 值：STREAMING/DONE/CANCELED/INTERRUPTED/ERROR） |
| `enums/ChatRole` | USER / ASSISTANT |

**三个枚举都带 `@EnumValue`**，存库时存 `code` 字段而不是 `name()` 或 `ordinal()`：

```java
public enum IngestStatus {
    INGESTING("INGESTING"), ...
    @EnumValue                        // ← 写库时存这个
    private final String code;
}
```

不显式写的话，「到底存枚举名还是序号」得翻 MP 版本才知道。写出来后 Navicat 里看到的
是可读的 `'INGESTING'` 而不是 `3`。

⚠️ **`ChatRole` 的 code 是小写 `'user'/'assistant'`，另两个枚举是大写**——
这不是笔误：role 的取值在前端和接口上本来就是小写，数据库跟着写小写，**跨层 grep 才搜得到**。

⚠️ **枚举值和前端状态机是一一对应的，不要自己加第六个**：
`ChatMsgStatus` 那五个 ↔ 前端 `chatStore.MSG`；`IngestStatus` 那五个 ↔ 前端
`ingestStore.STATUS` 的**后五个**（前端还有 `queued`/`uploading`/`committing` 三个
纯客户端状态，服务端永远看不到，所以枚举里没有它们）。

**`PersistenceStartupCheck` 值得单独说**——它是「落库是旁路」这个原则的**反面**：

```
① 用 JdbcTemplate 查版本号      → 不碰 MyBatis。失败就让它抛，启动直接失败（缺库要吵）
② 用 mapper 查演示用户          → 走完整的 ORM 链路。①过了②炸 = 问题在 MyBatis 不是 MySQL
③ 补写演示用户 + 清扫僵尸流     → 失败只打 ERROR，服务照常起
```

第①步**故意不捕获异常**：库不存在/密码不对/MySQL 没起来都会让启动失败，日志里那句话就是答案。
第③步清扫的是「上次进程退出时还停在 STREAMING 的助手行」——**一条流不可能活过一次进程重启**，
所以它们必然是「答案没落下来」的残骸，开机全部改成 `INTERRUPTED`。

> **这是全项目唯一「缺库要吵」的地方，和运行期的静音是有意的对照**：
> 启动期起不来还硬撑 = 你不知道自己在跑一个半死的服务；运行期写库失败还报错 = 把 DB 抖动
> 翻译成用户的 500。

### ⑨ `util/` —— 无状态工具

`TextUtils` 只有两个静态方法，都在**写库前**用：

| 方法 | 用途 |
|---|---|
| `truncate(s, maxChars)` | 按**字符**截断（正好是 `VARCHAR(n)` 的口径）。MySQL 8.4 严格模式下超长**不截断而是报错** `Data too long for column` |
| `isBlank(s)` | null 和全空白都算空 |

**★ 业务键故意不截断**：`job_id` / `session_id` 超长就让那次写入报错，
因为截断一个键会写下一个**和上游对不上的值**，而它是唯一的对账线索——**假键比没键更坏**。
（所以 `AppConstants` 里没有 `MAX_JOB_ID_CHARS` / `MAX_SESSION_ID_CHARS`。）

`truncate` 对 null 原样返回，也是故意的：调用方有时靠 null 和空串区分语义
（比如 `error` 列的「没写」和「清空」），工具方法不替它们做决定。

### ⑩ `exception/` —— 异常与全局错误出口

| 类 | 职责 |
|---|---|
| `RagApiException` | 「上游返回了非 2xx」这个事实 → 带 `status` + `detail` 的运行时异常 |
| `GlobalExceptionHandler` | `@RestControllerAdvice`，把异常翻译成 `{"detail":"..."}` |

**`RagApiException.detailOf()` 是全项目最值得读的一段 JSON 处理代码**，
它要认出 FastAPI 的**两种错误体**：

```jsonc
// 1) 业务错误 —— detail 是字符串
{"detail":"任务不存在(仅保留最近一个任务)"}

// 2) 参数校验失败 —— detail 是数组！（422）
{"detail":[{"type":"int_type","loc":["body","user_id"],
            "msg":"Input should be a valid integer","input":null}]}
```

第二种如果不特殊处理，`ApiErrorResp(String detail)` 反序列化会直接抛异常，
结果就是「整段原始 JSON 被当成错误文案丢给用户」。
所以这里把数组摊平成 `user_id: Input should be a valid integer`（`loc` 只留最后一段字段名）。

**`fromUpstream` 是唯一的翻译入口**，两个 HTTP 客户端都走它：

> ★ 两个客户端都要走这里，**detail 只能有一份翻译实现**：
> 各写一份的话，早晚有一条路先腐烂，而它偏偏是排查问题时唯一的线索。

**`GlobalExceptionHandler` 的三个 `@ExceptionHandler`**：

| 捕获 | 状态码 |
|---|---|
| `RagApiException` | 透传上游状态码（解析不出才退回 502） |
| `IllegalArgumentException` | 400 |
| `Exception` | Spring 自带的 web 异常（415/400/405）→ 用它自己带的码；其余 → 500 |

**★ `error()` 里 `.contentType(APPLICATION_JSON)` 那一句是必需的，不是装饰**：
`/api/rag/chat` 的 `produces` 是 `text/event-stream`，浏览器那条请求的 `Accept` 也是它，
于是想写 `ApiErrorResp` 时**找不到能把 POJO 写成 text/event-stream 的转换器**，
Spring 只能吐一个「没有 Content-Type、body 为空」的裸响应：

```
Accept: text/event-stream → 500  ct=null  body=""     ← 前端只能瞎猜
Accept 用通配符           → 500  {"detail":"..."}     ← detail 明明在这儿
```

显式指定后就不再走 Accept 协商（详见 `流式问答链路详解.md` §4.9）。

## 5. 包之间的联系

### 5.1 依赖关系图

```
                    ┌──────────────┐
                    │ controller   │  RagController
                    └──────┬───────┘
                           │ 只用 service
                    ┌──────▼───────────────────────────┐
                    │            service               │
                    │  RagService ◄─────────────┐      │
                    │    │  │  │                │      │
                    │    │  │  └──────────┐     │      │
                    │    │  └─── IngestRecordService  │
                    │    └────── ChatRecordService    │
                    └────┬──────────────────┬─────────┘
              client调用 │                  │ mapper调用
                    ┌────▼─────┐      ┌─────▼──────┐
                    │  client  │      │   mapper   │
                    │ RagClient│      │  (4个空接口)│
                    └────┬─────┘      └─────┬──────┘
                         │ config 装配       │ 返回
                    ┌────▼─────┐      ┌─────▼──────┐
                    │  config  │      │   entity   │
                    └──────────┘      └────────────┘

      横向被所有层依赖：common（常量/枚举/自检）、util、exception
      纯数据、被 client 和 controller 依赖：dto
```

### 5.2 五条铁律

| # | 规则 | 违反了会怎样 |
|---|---|---|
| 1 | **依赖单向**：`controller → service → client/mapper`，不许反向 | mapper 里注入 service → 循环依赖，启动报错；或分层失效，改一处崩一片 |
| 2 | **`entity` 不出 service 层** | `password_hash` 被序列化给前端 = 事故（所以要返回的形状放 `vo/`，目前为空） |
| 3 | **`client` 只做协议转换**，业务规则在 service | 重试/轮询/落库逻辑写进 client → 换个调用方就得复制一遍 |
| 4 | **错误翻译只有一份实现**（`RagApiException.fromUpstream`） | 两条路各写一份，早晚一条腐烂，而它偏偏是排查时唯一的线索 |
| 5 | **落库是旁路**：所有落库调用走 `RagService.safeWrite` / `settleAsync` | DB 抖动变成用户的 500 → 诱导用户重传 → 同一份文档入库两次（上游没有幂等键） |

### 5.3 三个「唯一」——记住这些就抓住了骨架

1. **`RagService` 是唯一同时依赖 `RagClient` + 两个 record service 的类** → 它是业务编排的唯一场所。
   要知道「一次操作做了哪些事」，只读这一个类。
2. **`RagController` 是全项目唯一的 HTTP 入口**，`GlobalExceptionHandler` 是唯一的**异常**出口。
   两个出口，没有第三个。
3. **`RagClient` 是全项目唯一碰上游 HTTP 的地方**。
   要换上游、加超时、加鉴权头，都只在这一个文件里。

### 5.4 两条链路串起来看

**链路 A：上传 + 轮询**（同步、请求-响应）

```
前端 POST /api/rag/documents
  → RagController.upload
      → RagService.upload
          → RagClient.upload              ← RestClient，同步
              → 上游 POST /v1/kb/upload → 返回 job_id
          → safeWrite → IngestRecordService.begin     ← insert 一行，status=INGESTING
      ← 返回 FileUploadResp(job_id)

前端定时 GET /api/rag/tasks/{jobId}
  → RagController.queryTask
      → RagService.queryTask
          → RagClient.queryTask           ← 上游 GET /v1/kb/ingest/{job_id}
          ├─ 成功 → safeWrite → IngestRecordService.applyPoll     ← 就地 UPDATE
          └─ 失败 → safeWrite → IngestRecordService.markPollFailed → 再 throw 给前端
```

**链路 B：流式问答**（异步、长连接）

```
前端 POST /api/rag/chat
  → RagController.aiChat
      → RagService.aiChat
          ① ChatRecordService.beginExchange      ← 请求线程同步写：会话行 + user 行 + 空 assistant 行
          ② return Flux.defer(...)
                 ragClient.aiChat(req)            ← WebClient，返回 Flux<String>
                     exchangeToFlux → decodeRawText   ← 自研字节流解码器
                 .doOnNext(攒正文)
                 .doOnError(记异常)
                 .doFinally → settleAsync         ← 甩到 boundedElastic，再写 assistant 行终态
  ← Flux 经 Spring MVC 写成 SSE 回前端
```

**注意 ① 和 ② 的分界**：①在**请求线程上同步写**（那时响应还没开始，写库失败能被抓住记日志，
而且上游挂掉的那次提问也留下了痕迹）；②里的一切都是**流的一部分**。
这个分界不能挪——把 ① 放进 `Flux.defer` 里，落库就成了流的一部分，DB 一抖会把用户的回答带崩。

## 7. Spring Boot 4 / MyBatis-Plus 3.5.17 的坑（踩过的）

抄教程时最容易翻车的四点，都在 `pom.xml` 和代码注释里写明了：

1. **`RestClient` / `WebClient.Builder` 要单独加 starter**——Boot 4 把各 HTTP 客户端的
   自动配置拆成了独立模块。只有 `starter-webflux` 拿不到 `WebClient.Builder`
   （那只带 WebFlux 的**服务端**，而且被 `@ConditionalOnWebApplication(REACTIVE)` 挡住了）。
2. **MyBatis-Plus 必须是 `mybatis-plus-spring-boot4-starter`**——同版本的
   `-spring-boot3-starter` 在 Boot 4 上会以一堆 `NoClassDefFoundError` 收场
   （Boot 4 挪了 autoconfigure 的包名）。
3. **`ServiceImpl` 的包名变了**：`com.baomidou.mybatisplus.spring.service.impl.ServiceImpl`，
   老路径 `extension.service.impl` 在 3.5.17 里是**空的**。
4. **Jackson 升到 3（`tools.jackson` 包）**，但 DTO 上仍用 Jackson 2 的注解
   （`com.fasterxml.jackson.annotation.*`）。

## 10. 数据库四张表

| 表 | 写入方 | 形态 |
|---|---|---|
| `user` | `PersistenceStartupCheck`（启动补写） | 1 行演示数据，**无登录** |
| `ingest_task` | `IngestRecordService` | 一行一任务，**就地更新**（上游返回的是快照不是事件流） |
| `chat_session` | `ChatRecordService.ensureSession` | **按需创建**，无外键约束 |
| `chat_message` | `ChatRecordService` | 一次问答**两行**（user + assistant） |

**两个反直觉的设计**：

- **同一轮问答的两行 `created_at` 完全相同**（共用一个 `now`）——对齐前端「两条消息共享
  createdAt」的语义。所以**一轮之内的先后只能靠 `id` 排，不能靠时间**。
- **清空 `error` 只能写空串，不能写 null**——MP 默认不把 null 字段写进 UPDATE，
  写 null 等于「这列不动」，上一次的报错会永远挂在那行上。
  ⚠️ 反过来，`lambdaUpdate().set(...)` 是**显式写列**（null 也会写进去），
  **两套语义正好相反**，改代码前先想清楚用的是哪一套。
